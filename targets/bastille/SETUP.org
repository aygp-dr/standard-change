* This document describes the PRE-CORRECTION port scheme

The addresses below say =:9200 production / :9201 staging=. That pairing was
reversed by the 2026-09-13 port correction: =9200= is *staging*, production is
the front on =9230= over blue =9210= and green =9220=, and =environments.tsv=
is the declaration. They are left as written because this target was built
against them, and rewriting them would claim a jail estate that has been
re-addressed when it has not.

Do not copy an address out of this file into anything on the node path.
=change/activate.sh= did exactly that and pointed the *authorizing* e2e run at
:9201 — one app replica rather than the router front — so the gate refused a
healthy estate. See =README.org= §Environments for the current scheme.


*Port tiers.* The number says what an environment is and whether it can
promote (=spec.org= §The port map):

| range       | tier        | can promote? |
|-------------+-------------+--------------|
| 9000–9099   | *dev*       | no — disposable worktree blocks |
| 9100–9199   | *team*      | *no* — real, and a dead end by construction |
| 9200–9299   | *protected* | *yes* — the path to production |

*Every jail listens on port 80.* Each has its own IP, so ports cannot collide,
and the deployed config is byte-identical across environments — there is no
port number for staging and production to differ in. The =9000 + 10n= blocks
remain correct for dev worktrees, which share hydra's namespace. Two different
problems, two different answers.

* Why the front router exists

Two jobs, and it would be needed for either alone:

1. *Bridge.* Jails are on =10.0.0.0/24=; laptops are on =192.168.86.0/24= and
   =pf= passes only =8000:9999= inbound. The front router is the only thing on
   both.
2. *The blue/green switch.* =upstream production= names exactly one estate, so
   at any instant production is one build — never two.

* Why blue/green makes guard 5 easy

This is the payoff, and it is the inverse of the gradual-rollout case:

| strategy            | is a mixed fleet possible? | what guard 5 must do                 |
|---------------------+----------------------------+--------------------------------------|
| blue/green          | *no* — atomic cutover      | sample once; there is nothing to converge |
| rolling replicas    | yes, transiently           | sample until one build answers       |
| gradual / canary    | *yes, by design*           | *cannot be answered by sampling* — needs the platform's declared split (§C6) |

An atomic cutover has *no convergence window*, so =UNCONVERGED= is
unreachable rather than merely unlikely. Rollback is the same command with the
other colour, which makes the previous build a *reachable rollback target* —
the property =spec.org= says =non_fast_forward= protects and GitHub Pages
cannot offer.

* Setup, as performed

#+begin_example
bastille create -T sc-staging 14.3-RELEASE 10.0.0.60      # and .61, .62
# ABI: jails are 14.3 userland, pkg serves 14.4 builds (host is 14.4-p6)
echo 'IGNORE_OSVERSION=yes' >> <jail>/usr/local/etc/pkg.conf
echo 'FreeBSD-kmods: { enabled: no }' > <jail>/usr/local/etc/pkg/repos/kmods.conf
jexec <jail> pkg install -y python311 nginx                # 465M per jail
#+end_example

Python, not node: the apps are fixtures and the pipeline is the product, so the
deployed app is stdlib-only =targets/bastille/app.py= serving the same JSON
contract. =gates/e2e.sh= therefore asserts identically against a jail and a dev
worktree.

* What this target does and does not give

| capability                          | status |
|-------------------------------------+--------|
| C6 — platform-attested record       | *yes* — =jls= is the host's own statement; the host runs the jails |
| guard 5 — served build identifiable | *yes* — both =x-build-sha= and =/version.json= |
| reachable rollback target           | *yes* — the idle colour still holds the previous build |
| promote the tested artifact         | *no* — deploy rebuilds from source per environment; weaker than a digest |
| route ownership enforced            | *no* — see below |

** Two honest defects [E]

- *Non-VNET jails remap =127.0.0.1= to the jail IP.* The apps bind loopback
  intending to be unreachable, but =curl http://10.0.0.60:8002/= returns 200.
  Route ownership is a convention here, not a network fact. VNET jails would
  make it real.
- *Promotion is not by identity.* =deploy.sh= installs a commit into a jail, so
  staging and production build separately. §Cloud mirror requires promoting the
  artifact staging tested; this target cannot, and Workers versions can (§C6).
