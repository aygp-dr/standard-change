* What this is

Change enablement and deployment management, demonstrated end to end. Four mock
storefront apps (=core=, =plp=, =pdp=, =checkout=) behind one router. The apps
are fixtures; *the product is the gate sequence* — the labels that drive it, the
environment model underneath it, the change-schedule integration, and the
guards that make "you cannot skip staging" a structural fact rather than a
convention.

=spec.org= governs. This file is derived and orients; where they disagree,
=spec.org= wins. =scenarios.org= is the test plan, =tla/= the formal model of
the promotion guards.

*** The estate is a thing you can close

Top left. =freeze= and =emergency= are properties of *the world*, not of any
change, so they live on an **issue** — not a pull request. PR #48 found why: a
pull request carrying =itil:emergency= is a change, and the same write that
closes the estate to everyone else exempts *its own carrier*. The carrier
becomes the remedy by construction, whatever it contains. An issue cannot be
deployed, so there is no exemption it could be handed.

The two buttons are the break-glass. Freeze is blue — a planned, reversible
gate, nothing on fire. Emergency is red — something is wrong now. Lifting is
white, because the control that *removes* a freeze must not look like the one
that *imposes* it. =gates/preflight.sh= reads the same issue: toggle here and
the next change is refused with exit 3.

Note what is NOT here: =itil:emergency=. That is a *classification on a change*
— this one is an emergency, here is its exemption — and it passes both a freeze
and an estate emergency. Two namespaces, two subjects. Folding them into one
flag makes the flag meaning "stop everything" look identical to routine hotfix
traffic.

*** Booked windows: the reservation, not the deployment

Reserving is not deploying. A window is an entitlement to the one path to
production, and the guards checked when it was booked are stale by the time it
opens — which is why activation re-runs them.

=CLOSES= shows *seconds remaining*, not just a wall-clock time, and turns amber
when less than one soak-plus-walk is left. A five-minute hold against a window
with four minutes on it is a change that will fail at the very end, after the
deploy and the entire hold. Printing only the end time made the operator do
that subtraction; #38 is what happens when nobody does.

=GROUPS= is the blast radius — one app or five.

*** Environments: the number tells you what it is

Sorted by port descending, so reading order matches blast radius.

- =front= 9230, red, the only address a customer reaches. It is never deployed
  to; it reads the live colour *per request*, which is why =BLUE LIVE= here is
  the one non-lying report of what the next request will get.
- =production-blue= 9210 / =production-green= 9220 — the two replicas.
- =staging= 9200, orange, the one protected environment that is *not*
  production. This repo once shipped a port map calling 9200 production; the
  colour exists so that mistake is visible.
- =9100-9199= team tier. =staging-{app}-1= are *reservations*: declared in
  =environments.tsv=, ports held so nothing else takes them, =activated=no=.
  They read =declared=, not =dark=, because a reservation is not expected to
  answer. They also *cannot promote* — nothing downstream reads a team verdict.
- =9000-9099= dev blocks, grey, disposable.

Every row is an HTTP request to that port. Nothing is read from a manifest or a
deployment record — a dashboard fed by the thing it reports on is the same
defect as a gate whose oracle comes from the runner's tree.

** One label starts a change

A person adds *=change:requested=* and that is the whole of their part.
Everything after is the system acting or observing, and the *name shape* says
which:

| shape                | kind        | example               | added by hand? |
|----------------------+-------------+-----------------------+----------------|
| =change:requested=   | request     | someone asked         | *yes*          |
| =release=            | *request*   | someone said go now   | *yes*          |
| =hold:<env>=         | *hold*      | someone said not yet  | *yes*          |
| =deploy:<env>=       | action      | work is in flight     | no             |
| =<subject>:<state>=  | observation | *a check came back*   | no             |

=production:healthy= reads as a check result because that is what it is.
=deploy:staging= is not a way to ask for a deployment — it marks that the
workflow is deploying, right now.

Three things this picture claims, each checked elsewhere:
*reserving is not deploying* (guards are re-evaluated when the window
arrives), *production promotes the digest staging tested* rather than
rebuilding, and *converged is not alive* — guard 5 samples until one build
answers, or refuses.

** Passing the gates is what moves a change, not a person

*A standard change that passes its gates goes to production without anyone
moving it.* That is the decision in =docs/adr/0001-automatic-promotion.org=,
and it is the reason the gates are worth what they cost: a gate nobody trusts
enough to promote on is a report, not a gate.

So there is no "promote" button, and adding =deploy:production= by hand is not
one either — it is an *action* label, and asserting it claims the workflow is
deploying right now.

*** Change control owns the cleanup, and the deployment annotation

When a change completes, *change control* — =change/settle.sh= — does three
things in order, and the order is the content:

1. *sets =change:complete=* — validation is done
2. *merges*, then *posts the PIR*
3. *clears the deployment labels and writes the deployment annotation*

Step 3 is the part worth naming. Clearing =deploy:staging= is not tidying: it
is the *release of the berth*, and a change that completes without clearing it
holds the path to production forever. Every other =staging:*= and
=production:*= label goes at the same time, because they described where this
change sat in the process and it is no longer in the process.

*The deployment annotation is written here too, and only here.* Not when the
deploy starts. The deployer used to open a record =in_progress= and resolve it
later — GitHub's own model — and every record it opened resolved to *failure*,
because =deploy-staging= dies at =queue.sh= before deploying (issue #25). PRs
read "1 failed deployment" while the estate served that build perfectly: the
record described the *workflow run*, not the environment.

By settlement, production has been observed serving the build. There is nothing
left to intend, so the annotation is written from a fact. It is keyed to the
*SHA*, never the branch, because settlement deletes the branch and a record
tied to a branch name cannot outlive it.

*What that costs, stated rather than discovered*: the history shows no failed
deployments, because a failed deploy never reaches settlement. "No failures"
will read as "nothing ever failed". And "is a deploy in flight right now?"
cannot be answered from the records — that question belongs to the berth.

*** Two namespaces: annotations, and the record

| namespace                    | what it is                                | lifetime                        |
|------------------------------+-------------------------------------------+---------------------------------|
| =staging:*=, =production:*=  | build/deploy *annotations* — a fact about a BUILD in an ENVIRONMENT | ephemeral; cleared per change   |
| =change:*=                   | the *record* — a fact about the CHANGE    | durable; never cleared          |

*Two namespaces, and they are different kinds of fact.* Mixing them is the
defect that made "a PR has at most one =change:*=" impossible to state, because
=change:standard= plus =change:complete= was a legitimate pair:

| namespace  | kind             | members                                              | cardinality |
|------------+------------------+------------------------------------------------------+-------------|
| =itil:*=   | *classification* | =itil:standard= · =itil:normal= · =itil:emergency=   | exactly one |
| =change:*= | *lifecycle*      | =change:requested= → =change:scheduled= → =change:complete= | one active |

=itil:*= is the ITIL change type and says *what kind of change this is*.
=change:*= says *where the change record has got to*. A change is classified
once and moves through the lifecycle many times.

=change:complete= is the terminal state of *validation*: set when every guard
has passed and production is observed serving the build, *before* the merge,
because the merge follows completion rather than constituting it. Cleanup then
clears it — once the forge records =MERGED=, the label restates a fact the
platform owns, and two records of one fact can disagree while the platform's
cannot.

*Neither namespace is a blocker.* A freeze, a held berth and an emergency in
flight are facts about the *estate*, not about any change — see below.

=production:healthy= is not terminal, and neither is =staging:uat=. Neither is
about the change; both are about a build that happens to be the change's head
at this moment. Push once and both are lies — which is why the labeller
withdraws every one of them on =synchronize=.

It also settles what may be cleared at completion. Annotations are cleared,
because the record summarises them and the PR timeline keeps every add and
remove with actor and timestamp. The record is not.

*** Adding a label and removing it are different acts

Who may *add* a label is not the same question as who may *remove* one, and
the two labels a person adds are opposites in both directions:

| label | added by | removed by |
|----------------+---------------------------+--------------------------------|
| =release=      | *a person only* — intent  | *automation* — the scheduler consumes it |
| =hold:staging= | *a person only*           | *a person only*                |

A person must add =release= because it is the intent to ship and no machine
may infer it. Automation must remove it because a trigger that stays on
re-fires, and the second firing deploys a change that is already live.

=hold:staging= is the mirror. A person must lift it, because the entire
content of a hold is that a human has not looked yet — and only that human
knows when they have. A hold a machine can clear is not a hold, it is a delay.

*** How to stop a change

*=hold:staging= is rejected semantics* as of 2026-09-13
(=docs/precedence-and-locks.org=). It was a per-change hold and the only human
stop the pipeline modelled, which made it look necessary. The human stops were
always there and they are earlier:

| to stop                   | do this                        | scope |
|---------------------------+--------------------------------+-------|
| it should not go at all   | *do not add =change:requested=* | that change |
| it is not fit to ship     | *do not approve*                | that change |
| nothing should go now     | *=freeze=*                      | the estate |
| this outranks everything  | *=itil:emergency=*              | the estate's ordering |

A change nobody wants promoted is simply not requested and not approved.
=hold:staging= added a fourth way to stop a deploy at a fifth scope, with no
rule for which applied when two were present — the two-writers-one-fact defect
that =itil:*= and =change:*= were split to remove.

What is lost: *"I approve this, and I want to look at staging first"* is now
expressed by not approving until after looking. Strictly slower, and honest —
the approval then means what it says.

*** Superseded: the old text on =hold:staging=

[The original description follows, kept because the reasoning it records is still worth reading.]

Sometimes you want to look at staging yourself. =hold:staging= is how, and it
is the only human stop in the pipeline:

| | |
|---------------------+--------------------------------------------------------|
| *what it does*      | the change stops after =staging:passed=; production is untouched |
| *who adds it*       | a person, at any time, including mid-run                |
| *who removes it*    | *a person.* Never the workflow                          |
| *when it is read*   | at the instant of promotion — guard 4c — not at the staging pass |
| *on expiry*         | *forfeit*, never promote                                |

Four properties, and each is load-bearing:

1. *Only a person lifts it.* A hold the machine can clear on your behalf is
   not a hold, it is a delay. The workflow may read this label and may refuse
   on it; it may never remove it.

2. *It is read at promotion, not at the staging pass.* You can add it while
   the authorizing e2e is still running and it will still be honoured. This is
   the same law as guard 4b — *a guard whose subject can change after it is
   checked must be re-checked at the moment it is relied on* — applied to a
   person rather than to trunk.

3. *Releasing it re-runs the guards.* A hold is time, and time is exactly what
   guard 4b watches. A hold long enough to be worth taking is long enough for
   =main= to move underneath you, so removing the label does not resume a
   half-finished deployment; it re-enters the guards.

4. *It expires to forfeit, never to ship.* The berth is a singleton, so a hold
   wedges every other change in the repo — it cannot be indefinite. But the
   safe direction on timeout is *down*: release the berth, withdraw the
   staging pass, make the change ask again. A hold that timed out into a
   production deployment would be the most dangerous label in this repository,
   because it would ship precisely the change someone had said to look at.

*It is deliberately atypical.* Reaching for it often is a signal about the
gates, not about the change — it means the suite is not trusted to authorize a
promotion, and the thing to fix is the suite. The label exists so that
distrust has somewhere to go that is *visible and counted*, rather than being
expressed as a pipeline nobody turns on.

*What it costs, stated plainly.* Holding claims the path to production and
then does nothing with it. Every other change queues behind a human reading a
page. That is a real price and it is the argument for using it rarely.

* Environments

Three kinds of environment, and conflating them is the mistake this model
exists to prevent. *Team environments are for developing a change; staging is
the path to production.* They are not the same resource, they are not checked
out the same way, and a team environment can never promote.

losing one costs a re-checkout. Staging is scarce, singular, and *queued*,
because holding it is holding the only path to production.

* The updated check, and why it is containerized

The *updated check* is guard 0 plus guard 4b: a change may only reach the path
to production while it contains the current tip of =main=, and that must be
true *at the moment it is relied on*, not merely when it was requested.

Neither treats every merge alike. =change/divergence.sh= classifies what landed:

| class      | what moved on main                        | effect                       |
|------------+-------------------------------------------+------------------------------|
| =inert=    | docs, notes, the model                     | nothing — you are not stale  |
| =pipeline= | =targets/=, =gates/=, =.github/=           | re-verify; how you ship changed |
| *=artifact=* | *=apps/=*, =router/=                     | *blocked* — you would revert it |
| *=hotfix=* | any merge carrying =Change-Type: emergency= | *blocked* — you would revert a fix |

*=apps/**= is the deployable entity*, so any change to it blocks — not just a
change to the same app. That coarseness is a property of the monorepo, and
=docs/adr/0001-automatic-promotion.org= is where the options that
remove it live.

Containers are what make this checkable rather than hopeful. One image per app,
built once, tagged by the *commit SHA*, promoted by digest:

Three properties fall out, and each is a scenario in =scenarios.org=:

1. *Only the changed groups come from the PR.* The untouched three run the
   current production image. Staging therefore tests /this change against
   current production/, which is what makes the cross-app journeys mean
   something (scenario D2).
2. *Production promotes the digest staging tested.* It never rebuilds. A
   rebuild between staging and production is a different artifact, and every
   assurance staging bought is void.
3. *=x-build-sha= is served by the container*, so =gates/health.sh= can assert
   that the thing we deployed is the thing answering. A 200 alone passes
   through a deploy that silently did nothing (scenario D6).

The local worktree topology is the same graph with =nginx= and =node= processes
instead of containers — same router, same ports, same four upstreams. That
correspondence is the point: what you run at =:9010= is what staging runs at =:9201=.

* Interfaces, and the scheduler

The pipeline is driven by a small set of operations — reserve a window,
activate when it is due, settle with evidence (=docs/idp-api.org=). *How a
person reaches those operations is an interface concern and carries no
semantics.* An API call, an MCP server, the IDP's own UI, a chat command and a
label added by hand are all the same three verbs with different ergonomics.

Keeping that boundary is what stops the model acquiring a dependency on any one
of them. The guards live behind the API; a client that could bypass them would
not be an interface, it would be a second implementation.

** The scheduler is not an interface

Activation is the one operation *no client calls*. The scheduler invokes it
when a window comes due, and it re-evaluates every guard at that moment. That
is deliberate: if a change could activate itself, the re-check would be a
convention someone remembers rather than something the system does.

** What exists, and what is work

| Piece                                   | State                                    |
|-----------------------------------------+------------------------------------------|
| Label vocabulary and guards             | specified, formally checked              |
| Guard logic in TLA+ and =sim/=          | *verified* — both directions             |
| =queue.sh=, =health.sh=, =release.sh=   | written, never run against a live forge  |
| The three-verb API                      | designed (=docs/idp-api.org=), unbuilt   |
| Change schedule integration             | *unbuilt* — no account or calendar chosen |
| Any interface at all                    | *unbuilt*                                |

The scheduler work splits in two, and they are different problems:

- *Change windows* are a /record/. Writing one is fire-and-forget and nothing
  blocks on it.
- *Freezes and emergencies* are a /control/. The pipeline blocks on reading
  them, which makes that read a dependency in the deployment path — and a read
  failure must fail closed. That is the correct direction and still an outage,
  which is why the =EMERGENCY_CHANGE= override exists.

One word runs in two directions and is worth stating plainly: an =EMERGENCY:=
*calendar event* blocks the estate, while an =itil:emergency= *label* exempts
one change. The calendar governs everyone; the label governs one.

* Status

Nothing is built. =spec.org= is at 0.3, the scenarios are written, and the TLA+
model is checked. Every matrix cell in =spec.org= is a hypothesis: no gate has
run, because no gate exists. The one thing actually verified end to end is the
guard logic, and only as a model.
