#+TITLE: GitHub Environments, and what they can and cannot enforce here
#+DATE: 2026-09-13

* What changed

A =production= environment was created on the repository. There are now two:

: staging      protection_rules = 0   deployment_branch_policy = none
: production   protection_rules = 0   deployment_branch_policy = none

=gates/audit-conformance.py= now reports =environments  2 defined=, up from 1.

* What they could carry

GitHub Environments are the platform's own change-control primitive, and they
carry three things this repository currently implements by hand:

| protection rule            | what it does                       | what we do today                |
|----------------------------+------------------------------------+---------------------------------|
| *required reviewers*       | a named person must approve *the deployment*, separately from approving the PR | =staging:uat=, a label a person adds |
| *wait timer*               | N minutes between trigger and deploy | the change window, =change/schedule.sh= |
| *deployment branch policy* | only these branches may deploy here | nothing                         |
| environment secrets        | scoped credentials                 | n/a for this estate             |

*Required reviewers is the interesting one.* It is a deployment approval
distinct from a code approval, which is precisely the distinction the ADR
argues for and the label taxonomy encodes as =staging:uat= being a different
kind of fact from a PR review. GitHub already models it.

* Why it enforces nothing here, today

*Nothing that deploys this estate runs in GitHub Actions.*

Environment protection rules bind a *workflow job* that declares
=environment: production=. They gate the job and nothing else. Every
deployment in this repository is performed by =targets/node/deploy.sh= on
hydra, invoked by hand or by =change/watch.sh=, because no GitHub runner can
open a socket to =192.168.86.0/24= or the jails on =10.0.0.0/24=.

So a required reviewer on =production= would be satisfied -- or bypassed -- 
without anything actually deploying, and a deployment that actually happened
would never encounter it. Same reachability gap as
=research/findings/label-ownership.org= rule 2, and the same reason
=merge-on-healthy.yml= must abstain rather than falsify.

*This is not an argument against setting them.* It is an argument for knowing
what a green environment gate would mean. An unenforced control that reads as
enforced is worse than no control, which is the whole of
=research/findings/changing-the-pipeline.org=.

* What they would enforce, and it is not nothing

Two things bind regardless of where the estate lives:

1. *Deployment branch policy.* Restricting =production= to =main= is checked by
   GitHub when the deployment record is created, not when a job runs. Since
   =change/activate.sh= creates deployment records via the API, this *would*
   bite -- and it would have caught #9, which deployed to production from
   =feat/checkout-pink= before merging.
2. *The environment on the deployment record itself.* =production= existing
   means =gh api repos/../deployments -f environment=production= now lands in a
   declared environment rather than creating one implicitly. The records
   become enumerable per environment, which is the first half of C6: *a
   platform can attest to what is running only if it runs it* -- it still does
   not run it, but it can now at least hold the claim in a named place.

* The honest summary

Creating the environment is a *precondition*. It controls nothing. It gives the
platform somewhere to put deployment records and somewhere to hang rules that
would apply if a runner ever performed a deployment.

Until then the enforcement lives in =gates/production-first.sh=,
=change/guard4.sh= and =change/settle.sh=, all of which run on the host that
can see the estate -- and all of which are bypassable by a person with a shell,
which is recorded rather than hidden.

*Trigger to revisit*: a self-hosted runner on hydra. That single change would
move required reviewers, wait timers and branch policies from advisory to
enforced, and would close most of what ADR 0001 Option 0 is working around.
