#+TITLE: What CI can validate, and what it cannot
#+DATE: 2026-09-14

* The short answer

*We already run the code directly on GitHub.* =.github/workflows/gate.yml=
allocates a port block inside the runner, starts every app with
=change/ports.sh run-apps=, and runs the e2e journeys against
=http://127.0.0.1:$BASE_PORT=. That is why =lint=, =test=, =e2e= and
=gate-selftest= are green on every pull request: they are measured on a real
estate, just an *ephemeral* one that lives for the length of one job.

What CI cannot do is validate the *persistent* estate. It is on
=192.168.86.29=, a private address, and a GitHub runner cannot reach it.

* Two estates, and they are not the same claim

| | ephemeral (in the runner) | persistent (hydra) |
|-+---------------------------+--------------------|
| address | =127.0.0.1:900n= | =192.168.86.29:9200= / =:9230= |
| lifetime | one job | until redeployed |
| reachable from CI | yes | *no* |
| what it proves | this build's journeys work | this build is what is SERVING |
| which guards | 2 (gates green) | 4, 5, 6 |

The distinction is the one =spec.org= §Targets already draws between the
deployed thing and the tested thing. An ephemeral estate answers /does this
code work/. It cannot answer /is this code what production is running/, because
it is not production.

Guards 5 and 6 read the SERVED build. No ephemeral estate can stand in for
that, which is why =scenarios.org= D18 puts "production unobservable" at 0/100
under every policy.

* The placeholder variables

Set 2026-09-14 as repository *variables*, not secrets:

| name | value | why |
|------+-------+-----|
| =STAGING_URL= | =http://127.0.0.1:9200= | placeholder |
| =PRODUCTION_URL= | =http://127.0.0.1:9230= | placeholder |

*They are variables because a URL is not a credential.* Putting a hostname in
=secrets= masks it in the logs, which buys nothing and makes a failing health
check unreadable — and these are expected to fail. A secret is for a value
that would cause harm if read; the harm here would be from a value that can be
*reached*, which is a network property, not a logging one.

They point at loopback, so a runner evaluating them will probe its own
localhost, find nothing on 9200/9230, and guard 5 will report =UNHEALTHY= or
abstain. *That is the correct failure*: the workflow is written correctly
against an estate it cannot see. Repointing them at a reachable address is the
only change needed when one exists.

** =DEPLOY_TARGET= is deliberately NOT set

=deploy-production.yml:42= interpolates it into =./targets/${{
vars.DEPLOY_TARGET }}/deploy.sh=. Unset, that expands to =./targets//deploy.sh=
and the step dies — which is why the workflow has failed safely 249 times
rather than deploying.

Setting it would ARM a production deploy that fires on a label, against an
estate the runner cannot reach, with =./targets/<t>/rollback.sh= — a script
that *does not exist for any target* — as its failure path. It stays unset
until the deploy workflows are either fixed or removed (PR #83 proposes
removal).

* If the persistent estate must be validated from CI

Three options, in increasing order of what they give up:

1. *A tunnel to a read-only view.* The health and e2e gates need only HTTP GET.
   Exposing a read path is a much smaller claim than exposing the dashboard,
   which has unauthenticated writes (=spec.org= §Exposure). The existing
   =cloudflared= ingress on hydra already demonstrates the pattern: it publishes
   the demo page and never the PTY socket.
2. *A self-hosted runner on the LAN.* The runner reaches the estate directly and
   no address is published at all. It also means repository workflows execute on
   a host inside the network, which is a larger trust decision than a read-only
   tunnel and should be argued as one.
3. *Push instead of pull.* The estate reports its own served build outward to a
   collector; CI reads the collector. This is what =change/marker.sh= already
   does to the beacon. Weakest attestation — a self-report is not an
   observation — and =spec.org= is explicit that the jail's =jls= is evidence
   while a self-report is not.

None is free, and the current state is honest: the gates that can run in CI do,
and the guards that need a production say so rather than pretending.
