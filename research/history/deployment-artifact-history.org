#+TITLE: Before the artifact/gate split: Zope, OpenACS, and what serverless changed
#+DATE: 2026-09-25
#+PROPERTY: header-args :mkdirp t

* Why this note exists

=research/history/pipeline-history.org= already covers microservices
("you build it, you run it," Amazon 2006) and container-based deploys.
Four earlier and later systems were missing entirely: Zope, OpenACS,
Erlang/OTP, and the serverless/FaaS shift. All four answer the same
question this repo's own model turns on -- *is the deployable thing a
versioned artifact, and is there a gate between publishing it and it going
live* -- and they answer it in four different shapes, one of which
(Erlang's) does not fit the two-axis table cleanly at all, which is the
most interesting result of adding it.

* Zope: edit-time and deploy-time are the same act

Zope (a Python application server, late 1990s) stores application objects
in ZODB, a live transactional object database, "not files on a file
system, as is usual with most web servers" [[https://en.wikipedia.org/wiki/Zope][Wikipedia: Zope]]. Two deploy
paths, both real, neither involving a versioned artifact:

- *Product Refresh.* Extension code ("Products") were filesystem Python
  packages under =Products/=. From Zope 2.4 on, a =refresh.txt= marker plus
  a ZMI button called Python's =reload()= on the product's modules and
  cleared ZODB's class cache, live, no restart [[https://zope.readthedocs.io/en/2.12/INSTALL.html][Zope INSTALL docs]]; [[https://engineering.purdue.edu/Control_Panel/Products/OFSP/Help/Product_Refresh.stx][Product
  Refresh help page]]. No numbered-release discipline found for this path --
  edit the file, click refresh, that *is* production.
- *Through-the-web (TTW) editing.* DTML templates and Python Scripts were
  written directly in the ZMI browser and persisted straight into ZODB.
  Zope's own current docs: TTW code "lived in the database with no version
  control" [[https://zope.readthedocs.io/en/latest/zopebook/ZopeArchitecture.html][Zope Architecture docs]]. There is no artifact in this path at all
  -- the thing being edited and the thing being served are the same ZODB
  object.

Neither path has anything resembling review or staged promotion. This is
the zero point on the axis this repo's whole model lives on: no artifact,
no gate, because there was never a moment where "written" and "live" were
two different states of the world.

* OpenACS: a versioned artifact, a convention instead of a gate

OpenACS (built on AOLserver/NaviServer, descended from ArsDigita's ACS) is
closer to a modern release than Zope, but the gap is instructive. Numbered
release tarballs are real and current -- =openacs.org='s [[https://openacs.org/projects/openacs/download/][download page]]
ships e.g. 5.10.1 Final. The documented *non-CVS* upgrade path is a literal
overwrite onto a live tree: =tar xzf openacs-5-1.tar.gz= then
=cp -r openacs-5-1/* openacs-4= [[https://openacs.org/doc/upgrade-openacs-files][upgrade-openacs-files]]. A CVS-based path
(freeze, import, stage, apply) is documented too, for production use.

Package-level versioning has a real name and a real mechanism: *APM*, the
Application Package Manager [[https://openacs.org/doc/apm-design][apm-design]]; [[https://openacs.org/doc/tutorial-upgrade-scripts][tutorial-upgrade-scripts]]. APM tracks
installed packages in database tables, enforces a version grammar, and runs
numbered SQL upgrade scripts (=upgrade-OLDVERSION-NEWVERSION.sql=) when it
finds them. The documentation states the direction of causality plainly:
"upgrades work by first changing the filesystem and then using the APM to
scan the filesystem, find upgrade scripts, and execute them" -- the file
lands, and the database migration follows automatically, unconditionally,
the moment APM next scans.

*This is the finding worth keeping.* OpenACS has half of the split this
repo cares about -- the tarball is a versioned artifact -- but the other
half is procedural, not mechanical: APM's scan-and-execute has no gate
built in. The documentation's own safety advice (freeze first, stage, test,
then apply) is human discipline layered on top of a tool that will run
unconditionally the moment files land. Merge and deploy are decoupled by
*convention*, never by a required check -- which is exactly the gap a
label the labeller re-derives, rather than a person remembering to follow
a runbook, is meant to close.

* Erlang/OTP: no artifact, but a formally scripted gate anyway

Erlang breaks the pattern the first two sections set up. It has *no*
versioned deployable artifact in the OpenACS or Lambda sense -- and yet it
has the most mechanically rigorous transition-gate of anything in this
note, scripted module by module. Both things are true because of how the
BEAM VM manages code in memory, confirmed directly against Erlang/OTP's own
documentation:

*Two versions of a module can be resident at once, on purpose.* "The code
of a module can exist in two variants in a system: current and old...
Fully qualified function calls always refer to current code. Old code may
still be evaluated because of processes lingering in the old code."
[[https://www.erlang.org/doc/system/code_loading.html][Compilation and Code Loading -- erlang.org]]. =code:purge/1= kills any
process still lingering in old code and removes it; =code:soft_purge/1= is
the non-destructive variant that only succeeds once nothing is still
running the old version -- the primitive that makes an upgrade *safe*
rather than merely forced.

*The gate is a file, and it is a script, not a convention.* A =.appup=
file names, per module, exactly what an upgrade does:
={load_module, Module}=, ={add_module, Module}=, ={delete_module, Module}=,
or ={update, Module, {advanced, Extra}}= -- the last of these triggers the
module's own =code_change/3= callback to transform *live process state* in
place. A =.relup= file, generated from a whole release's =.appup= files via
=systools:make_relup/3,4=, sequences this across every module in the
release, with order enforced (new modules load before the supervisors that
depend on them update; a downgrade reverses the sequence exactly)
[[https://www.erlang.org/doc/system/appup_cookbook.html][Appup Cookbook -- erlang.org]]; [[https://www.erlang.org/doc/system/release_handling.html][Release Handling -- erlang.org]].

So Erlang sits in a cell the OpenACS/Lambda framing doesn't have room for:
no separate versioned artifact to publish (the two module versions live in
the same running VM), but the most formally specified transition gate of
any system in this note -- expressed as an actual file format the tooling
parses and sequences, not a runbook a person is trusted to follow.

*Origin, with a caveat stated as one.* Joe Armstrong's PhD thesis, /Making
reliable distributed systems in the presence of software errors/ (KTH,
December 2003), is the primary source
[[https://erlang.org/download/armstrong_thesis_2003.pdf][full text, erlang.org]]. Ericsson's AXD301 ATM switch (announced 1998, ~2M
lines of Erlang) is the standard example cited for hot-upgrading a live
telephone switch without dropping calls, and for the famous "nine nines"
availability claim -- but a 2010 Erlang Factory talk by Mats Cronqvist
treats that specific number as closer to a repeated design target than a
systematically measured field result
[[https://www.erlang-factory.com/upload/presentations/243/ErlangFactorySFBay2010-MatsCronqvist.pdf][Cronqvist, "The Nine Nines," Erlang Factory SF Bay 2010]]. Cite the
mechanism as [E]; cite "nine nines" specifically as [H]. A second,
non-Ericsson production example of the same *hot-loading* lineage (not
image-dumping -- see the Common Lisp correction below): Naughty Dog's
GOAL, a Lisp built on Allegro CL for their game engines, let engineers
"compile and download code without interrupting or restarting the game"
(Wikipedia: Game Oriented Assembly Lisp).

*The lineage's root.* Erlang's in-memory, two-versions-coexisting model,
and Zope's through-the-web live editing above, both descend from an older
idea: Smalltalk-80's persistent, live-editable virtual image (Xerox PARC,
Kay/Ingalls/Goldberg). Alan Kay's own retrospective is the primary source
-- "The Early History of Smalltalk," HOPL 1993, ACM SIGPLAN Notices 28(3)
[[https://dl.acm.org/doi/10.1145/155360.155364][dl.acm.org]], freely readable at
[[https://worrydream.com/EarlyHistoryOfSmalltalk/][worrydream.com/EarlyHistoryOfSmalltalk]].

** Common Lisp: a real artifact, and honestly, nothing more than that

The obvious sixth member of this lineage -- named in an earlier pass of
this note and left unexplored -- is Common Lisp's own image-dumping
tradition: =sb-ext:save-lisp-and-die= (SBCL), =ccl:save-application=
(Clozure CL), =SAVEINITMEM= (CLISP). It is inherited from the Lisp
Machine tradition directly: MIT's CADR machines (from 1973) ran a
persistent OS-level "world," commercialized by Symbolics as Genera --
"saving a world" was an OS-integrated act there, not a library call.
Common Lisp's standardization (ANSI CL, 1994) preserved the idea but not a
portable primitive; each implementation kept its own descendant of the
saved world.

*The mechanism, confirmed against SBCL's own manual*
([[https://www.sbcl.org/manual/#Saving-a-Core-Image][sbcl.org/manual, Saving a Core Image]]). =save-lisp-and-die= writes global
heap state to a core file -- the stack is unwound first, so in-flight
continuations do not survive, only heap/global state does.
=:executable t= fuses the runtime and the core into one standalone binary;
without it, a =.core= file still needs a separately invoked runtime.
Three caveats the manual states plainly: on threaded platforms, "only a
single thread may remain running" when the dump happens -- CCL differs
here, supporting a =persistent= process argument so some threads can be
recorded and restarted
([[https://ccl.clozure.com/manual/chapter7.7.html][ccl.clozure.com/manual]]), so this is an SBCL-specific constraint, not a
universal ANSI CL one; the call is destructive to the calling process,
which is why the documented pattern is to fork a subprocess to perform the
dump; and open streams cannot survive -- "the OS won't let us preserve a
stream across save and load," the manual's own words for what happens to
file handles and foreign pointers. No binary compatibility is promised
across runtime versions.

*Real artifact, no deployment discipline -- checked, not assumed.* A
dumped image genuinely is a single, versioned, standalone artifact -- more
so than Zope's live ZODB or Erlang's in-memory code, neither of which
produces an exportable artifact at all. But every source found treats the
dump purely as a build/startup-time optimization -- shipping a warm,
pre-loaded executable instead of reloading source on every launch -- and
*none* describe a gate, a promotion process, or a numbered-image release
discipline built around it. Grammarly's own account of running Lisp in
production is explicit that the language-agnostic CI/CD layer supplies
whatever gating exists, not the dump itself: "the application is tested
and bundled by Jenkins, put on the servers by Rundeck, and run there as a
regular Unix process by Upstart"
([[https://www.grammarly.com/blog/engineering/running-lisp-in-production/][Grammarly Engineering, "Running Lisp in Production"]]). No citable
convention -- spec, vendor doc, or engineering blog -- describes "image
N+1 promoted over image N" as a discipline analogous to this note's own
artifact/gate question. Record this as a confirmed negative result, the
same discipline as Solaris Live Upgrade's corrected date above: Common
Lisp closes the lineage's artifact question cleanly, and answers its gate
question with a plain no.

*A correction to the lineage, not an addition to it.* Naughty Dog's GOAL
(Game Oriented Assembly Lisp, built on Allegro CL) is often reached for as
Lisp-in-production evidence, and it is real production evidence -- but for
the *wrong* half of this lineage. GOAL let engineers "compile and download
code without interrupting or restarting the game" (Wikipedia: Game
Oriented Assembly Lisp) -- that is hot code loading, the Erlang/OTP
pattern above, not image-dumping. Filed here as a correction rather than a
citation for this section.

* Serverless: the first with a versioned artifact and a mechanical gate together

AWS Lambda's model has both an immutable artifact and a mechanically
enforced gate between publishing it and routing traffic to it:

- *Versions* are immutable code+config snapshots with their own ARN;
  =$LATEST= is the only mutable pointer [[https://docs.aws.amazon.com/lambda/latest/dg/configuration-versions.html][configuration-versions]].
- *Aliases* are named pointers (e.g. =prod=) that callers actually invoke --
  "going live" is a pointer update, not a redeploy [[https://docs.aws.amazon.com/lambda/latest/dg/configuration-aliases.html][configuration-aliases]].
- *Weighted aliases* split traffic by percentage across two versions, the
  primitive under canary and blue/green rollout
  [[https://docs.aws.amazon.com/lambda/latest/dg/configuring-alias-routing.html][configuring-alias-routing]].
- *CodeDeploy for Lambda* builds a real gate on top of the pointer:
  =Canary10Percent5Minutes=, =Linear10PercentEvery10Minutes=,
  =AllAtOnce=, with alarm-triggered automatic rollback
  [[https://docs.aws.amazon.com/codedeploy/latest/userguide/deployment-configurations.html][deployment-configurations]]. AWS's own Well-Architected serverless lens
  names this pattern "immutable infrastructure" explicitly
  [[https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_tracking_change_management_immutable_infrastructure.html][rel_tracking_change_management]]. Cloudflare Workers ships a near-identical
  versions/deployments split [[https://developers.cloudflare.com/workers/versions-and-deployments/][versions-and-deployments]].

Two sources make the comparison to git-gated promotion explicit rather than
leaving it inferred -- [[https://github.com/clowdhaus/trunk-based-artifact-promotion][clowdhaus/trunk-based-artifact-promotion]] and
[[https://blog.inflection.com/gradual_deployments_with_serverless/][Inflection Engineering's "Gradual Deployments with Serverless"]] both argue
"build once, deploy many": CI builds one immutable artifact per merge, and
promotion (the alias move) is a separate, later, independently-gated act.
That is structurally the same split this repo makes -- merge is not deploy;
a label authorizes promotion -- but it is worth being honest that these are
blog-tier sources, not an established consensus, and that AWS's own
documentation states the mechanism without drawing the git-gating analogy
itself.

* The line across all five

| system | versioned artifact? | mechanical gate before "live"? |
|--------+----------------------+----------------------------------|
| Zope (Product Refresh / TTW) | no -- edit *is* deploy | no |
| OpenACS (tarball + APM) | yes | no -- convention, not mechanism |
| Common Lisp (=save-lisp-and-die=) | yes -- one standalone core/executable | no -- a build step, not a release discipline |
| Erlang/OTP (hot code loading) | no -- two versions coexist in one VM | yes -- =.appup=/=.relup=, module-scripted |
| Lambda / Workers (versions + aliases) | yes | yes -- CodeDeploy / gradual rollout |

Zope and OpenACS both predate, and structurally reject, the split between
"artifact published" and "artifact live." Zope collapses it entirely.
OpenACS has the artifact half but not the gate half -- the closest thing in
this survey to this repo's own starting complaint about a repository with
no tracking layer at all: a real, versioned, deployable thing, and nothing
mechanical standing between "it exists" and "it is what's running." Common
Lisp lands in exactly the same cell as OpenACS, by a completely different
route -- a dumped image is a cleaner, more self-contained artifact than a
tarball, and still has no gate discipline built around it anywhere this
note could find. Erlang is the system that breaks the table's implicit
assumption that the two columns move together -- no artifact at all, yet
the most formally specified gate of the five, because the gate lives in
the VM's own code manager rather than in anything published externally.
Lambda is the first system here with *both* halves in the shape this
repo's own model expects (a published, versioned thing, and a separate,
later, mechanically gated act that makes it live), which is also the first
point in this history where the comparison to a label-gated promotion
model is apt rather than anachronistic -- Erlang got the gate right
decades earlier, just built into a different place than an artifact
registry.

* What's unverified, stated plainly rather than smoothed over

- No formal, numbered-release discipline was found for Zope Products
  specifically (as opposed to Zope core itself) -- the refresh mechanism is
  documented, a changelog'd release *practice* for third-party Products is
  not. A zope-dev mailing list thread exists on this exact question
  ("Refresh ZEO interactive python when changing product's code?") but was
  not read for content; a lead, not a citation.
- No atomic or rollback-safe cutover mechanism was found documented for
  OpenACS's non-CVS upgrade path -- the documented instruction is a direct
  in-place =cp -r= overwrite, not a symlink swap or equivalent.
- No citable production account of ITA Software/QPX's actual deployment
  mechanics at the image level was found, despite ITA being one of the
  best-known large production Common Lisp systems -- the sources found
  (a 2009 ILC talk on their build tooling) describe build pain, not
  deployment. Left out of the Common Lisp section entirely rather than
  cited on the strength of the system being well-known.
- The AXD301 "nine nines" availability figure is cited everywhere Erlang's
  origin story is told, but a 2010 Erlang Factory talk treats it as a
  repeated design target rather than a systematically measured field
  result -- cited here as [H], not [E], on purpose.
- The Smalltalk lineage note is confirmed real and correctly sourced (Kay's
  own HOPL 1993 retrospective) but deliberately not developed -- it is
  named as the root of the Zope/Erlang live-image lineage, not analyzed on
  its own terms in this pass.
- The explicit serverless-vs-git-gating comparison rests on two engineering
  blog posts, not AWS's own documentation or a peer-reviewed source. Treat
  it as suggestive, not established.
