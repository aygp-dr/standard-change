* Seven kinds of progression, one word

Every row is called a progression and most of them are called environments in
conversation. They are seven different subjects. What moves from left to
right is different in each, and so is what "promote" means.

| kind                    | what moves            | promote means                                       | rows                                                                                   |
|-------------------------+-----------------------+-----------------------------------------------------+----------------------------------------------------------------------------------------|
| place (environment)     | the artifact          | install the same build somewhere more real          | itil, sap, twelve-factor, google, flux, gcp-cloud-deploy, kargo, pypi (two registries, uploaded twice), this estate |
| runtime mode            | nothing               | pick a config; the word names a switch, not a place | frameworks-general, rails, django, aspnet-core, symfony, laravel, elixir, node         |
| deploy target           | the artifact          | as place, but the target is a product feature       | capistrano, vercel, netlify, cloudflare-pages, azure-app-service                       |
| pipeline stage          | control               | the next stage may run                              | heroku, amazon, aws-codepipeline                                                       |
| audience (population)   | the users             | let more people see what is already installed       | google-populations, microsoft-rings, traffic-exposure                                  |
| channel / suite / line  | the label on a build  | re-tag; the bits do not move                        | windows-insider, chrome, firefox, rust, debian, ubuntu, freebsd, linux-kernel, node-release-lines, npm, maven, semver, cloud-vendors, kubernetes |
| record status           | a claim about a change | someone asserts the next thing is true              | redhat-bugzilla, mozilla-bugzilla                                                      |

Three observations follow.

*The framework rows are not environments at all.* =RAILS_ENV=, =NODE_ENV=,
=APP_ENV= select a configuration inside one process. Rails' "staging added by
convention" and Django's "convention not built in" say it plainly: the
framework has a switch, and the place is something the operator invents.
Reading a runtime mode as a place is how "we deployed to staging" comes to mean
"we ran with the staging config on a laptop".

*Audience and place are orthogonal, and the big shops separate them.* Amazon's
row is places ending in "prod split into waves"; Google's row is places and
its second row is audiences over the same places; Microsoft's rings are
audiences with no place named at all. Blue-green (the =traffic-exposure= row)
is an audience model too: both colours are the same place, and promotion moves
the front, not the build.

*The channel rows promote by re-labelling.* A Chrome build reaches stable by
being called stable; a Debian package reaches testing by ageing; =npm dist-tag
add= moves =latest= without publishing. The artifact is immutable and the
progression is a pointer. That is the model closest to a label-driven
pipeline, and it is also the one in which "where is it" has no answer beyond
"which pointer names it".

* Where the label namespaces sit in this

The seven kinds are the boundary question from the rebuild
(issue on namespace boundaries, filed 2026-09-15) seen from outside.

- =app:*=, =itil:*= are the record's *classification*: what the change is.
  No row in the survey has this axis, because every row is about a build or an
  audience and none is about a change. ITIL is the source of the word and the
  survey's ITIL row is its environments, not its change types.
- =deploy:staging=, =deploy:production=, =staging:deployed=,
  =production:deployed= are *place*: the artifact is installed at a tier. The
  estate's tiers are places with ports, not runtime modes, which is why a
  worktree block and staging can serve the same build and still be different
  things.
- =staging:e2e=, =staging:smoke=, =staging:uat=, =production:healthy= are
  *record status* in Mozilla's sense: a per-build flag ("verified on this
  train") that says nothing about any other build. The labeller's synchronize
  withdrawal exists because a flag with no build attached is Bugzilla's
  =verified= with no version.
- =change:start=, =change:scheduled=, =change:complete=, the closure codes are
  *pipeline stage* and *record status*: control, then a claim.
- The idle colour and the front are *audience*: blue-green. Promotion to
  production in this estate is two acts the survey keeps apart, install on the
  idle colour (place) and swap the front (audience), and =production:healthy=
  is observed after the second.
- There is no *channel* in this estate. The artifact is a sha and nothing
  re-tags it; a change reaches production by being installed, not by being
  called production. The merge to =main= is the nearest thing to a channel
  move, and it is the record catching up with the place, which is why it comes
  last.

* This estate

The survey row reads =dev-block, staging, idle-colour, front=. The ports as
=spec.org= §Port tiers states them on 2026-09-13: dev blocks =9000 + 10n= for
n ≤ 9, staging =9200=, production blue =9210=, green =9220=, the front =9230=.
The row's "100N0" is the older e2e default (issue #84) and not a tier.

Two things the survey makes visible about the estate. It has every kind but
channel and audience-by-population, and its one audience mechanism, the
colour swap, is not a label; it is a fact about the front that
=production:healthy= reports. And its "staging" is a place in the ITIL sense
and a deploy target in the Capistrano sense at once, which is the ambiguity
the port tiers were written to remove: the number says which.

| itil | development, test, staging, live | environments; ITIL names live/testing/staging, the sit/uat/pre-prod chain is practitioner convention |
The vendor's own statement of the practice is to "move new or changed hardware, software, documentation, processes, or any other component to live environments, and ... deploy components to other environments for testing or staging" -- three named environments, one of them "live" rather than "prod". ** node
:PROPERTIES:
:CUSTOM_ID: pm-node
:VERIFIED: 2026-09-15 citation-auditor
:VERDICT: disputed
:SOURCE: https://nodejs.org/en/learn/getting-started/nodejs-the-difference-between-development-and-production
:FINDING: Node.js docs: "There is no difference between development and production in Node.js"; only "development" and "production" are named as NODE_ENV values; Express names "(usually, development or production)"; neither primary source names "test"
:END:
| node | development, production | runtime mode; convention, no fixed set |
Node.js itself documents no environments: the runtime says there is no development/production distinction and that some npm libraries read =NODE_ENV=, defaulting to =development=, so one should "Always run your Node.js with the NODE_ENV=production set".
