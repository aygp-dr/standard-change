#+TITLE: How would an agent verify a change to the rules?
#+SUBTITLE: Speculation -- the control plane cannot be its own test subject
#+DATE: 2026-09-13
#+OPTIONS: toc:2 num:t

* The circularity

An agent changing =apps/pdp= is verified by the gates. An agent changing *the
gates*, the labels, or the guards is verified by... the gates it is changing.

#+begin_quote
The thing that decides whether a change is safe is the thing being changed.
#+end_quote

That is not solvable by adding a check, because the new check is inside the
boundary too. It is only solvable by finding something *outside* -- and this
repo has three such things, two gaps where it does not, and one honest limit.

* What is already outside the boundary

** 1. The formal model does not run on GitHub

=tla/Concurrent.tla= states the guards as predicates over abstract state. It
knows nothing about labels, workflows, or GitHub, so a rule change can be
expressed there *first* and checked before any YAML moves:

: change the predicate -> ./tla/check.sh -> six checks, three of them negative

This has already caught a guard change that looked fine: splitting deploy from
merge exposed that *guard 4 had guard 0's flaw* -- a change marked
=itil:emergency= after its pass was withdrawn could merge with neither a pass
nor an approval. TLC found it; no workflow would have.

*Limit, and it is a real one:* the model does not model *labels*. It has
=stagingPass= as a boolean, not =staging:passed= as a name. So it verifies a
change to what a guard *means*, and is blind to a change in what a label is
*called*. A rename is invisible to it.

** 2. The exhaustive implementation model

=gates/pbt-pipeline.py --exhaustive= enumerates every ordering of the
operations against an executable model, including the divergence classes TLA+
abstracts away. Same property: it does not call GitHub, so GitHub cannot lie to
it.

Its negative run is the part that matters -- =GUARD_4B=0= must still reproduce
scenario D4. *A rule change that makes the model unable to fail is the failure.*

** 3. The offline labeller oracle

=gates/labeller-test.py= replays the scenario catalogue against
=.github/labeler.yml= with no PR and no forge. It is the only thing here that
verifies a *label* change, and it was itself wrong once: it modelled
=itil:standard= as derived while the config never implemented it, so PRs got
=app:*= and no =change:*= for four iterations.

That is the shape of the danger. *An oracle for the control plane can encode
the intended behaviour rather than the actual one, and then agree with itself.*

* The two gaps

** Gap 1 -- the label vocabulary has no single source of truth

Fifteen files name labels. They disagree:

| source                        | labels declared |
|-------------------------------+-----------------|
| the repo itself (=gh label=)  |              22 |
| =spec.org= §Labels            |              22 |
| =gates/audit-conformance.py=  |               9 |
| =.claude/skills/_shared/=     | prose           |
| five workflows, four docs     | scattered       |

So an agent renaming =deploy:staging= must find and update fifteen places, and
*nothing tells it when it has missed one*. The conformance auditor would not
notice, because its own list is one of the fifteen.

*The fix is mechanical and not yet done:* one machine-readable file -- say
=labels.yml= -- with kind, description and colour, from which the auditor, the
skills' shared vocabulary, =gh label sync= and the spec table are all generated
or checked. Then a rename is one edit and a diff.

** Gap 2 -- GitHub's semantics are assumed, never asserted

The pipeline depends on behaviours nothing here checks:

- =sync-labels: true= *removes* labels the diff no longer justifies
- =pull_request_target= runs with *no checkout*
- a =labeled= event fires a workflow, and =skipped= means the =if:= was false
- check-run *names* match =^(gate-selftest|lint|test|e2e)$=
- label writes are *not* immediately readable back

Every one of those was learned by *being broken by it*: the missing =--repo=,
the labeller race, the hardcoded port, the four iterations of =itil:standard=.
An agent changing the rules inherits all of them and has no list.

*The fix:* a =gates/forge-contract.sh= that asserts each assumption against a
scratch repo -- apply a label, read it back, assert the delay; push without a
checkout, assert =gh= fails without =--repo=. Turn folklore into a gate.

* The answer

An agent should verify a rule change in this order, cheapest and most external
first:

1. *Change the TLA+ predicate.* If an invariant breaks, stop. Costs seconds,
   runs nowhere near GitHub.
2. *Run the exhaustive model*, both directions. If the negative run stops
   failing, the change removed the model's ability to detect the defect.
3. *Run the labeller oracle* for anything touching labels -- and check whether
   the oracle asserts the config or merely restates the intent.
4. *Run the conformance auditor against a scratch repo* with the new rules
   applied. This is the only step that touches real GitHub semantics.
5. *Replay =scenarios.org= Part B* against that scratch repo.

Steps 1–3 are available now. *Steps 4 and 5 need a second repository*, and that
is the real recommendation:

#+begin_quote
*A control-plane change must be verified somewhere the control plane does not
govern.* One repo cannot be both the subject and the instrument.
#+end_quote

Which is the same argument as §C6 -- /a platform can attest to what is running
only if it runs it/ -- applied one level up. A rule cannot attest to itself, and
=itil:normal='s required approval is a *procedural* answer to a *structural*
problem: it asks a human to notice what no gate checks.

* What this does not solve

Even with all five steps, an agent cannot verify that a rule change is
*desirable*. The gates can show that the guards still hold, that the model
still fails when it should, and that GitHub still behaves as assumed. They
cannot show that the new rule is the rule you wanted -- which is the one job
§Approval as a gate reserves for a second judgement, and the reason an agent
review is worth something only insofar as it *re-derives* rather than agrees.
