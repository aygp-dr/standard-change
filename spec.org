* Purpose

The repo demonstrates change enablement and deployment management on a mock ecommerce monorepo. The apps are fixtures. The product is the gate sequence, the labels that drive it, the change-schedule integration, and the checklists.

Two pre-conditions gate every production deployment:
1. No other deployment is in progress (deployment lock).
2. No emergency change or change freeze is active on the change schedule.

* What this model gets wrong, on purpose

*The architecture being simulated here is a bad one, and the pipeline is the
cost of it.* Stating that plainly is load-bearing: everything downstream —
the singleton berth, the queue, guards 0, 1 and 4b, the rebase loop, the
preemption rules — is machinery for surviving a missing contract, not a
pattern to copy.

The defect: four apps share one reverse proxy and one mock backend with *no
enforced interface between them*, and there is a single path to production. So
any change to any app might break any other, and the only available remedy is
to serialize: one change at a time, tested against current production, promoted
whole. The queue is not a design, it is what you are left with when nothing
else can tell you whether two changes compose.

What the right shape would be [I]:

- *Hard contracts at the router.* Route ownership declared and enforced, with
  versioned, consumer-driven contracts between apps rather than an implicit
  agreement that the storefront hangs together. Contract tests then answer
  "do these compose?" statically, per app, in seconds.
- *A path to production per team.* Each team owns its own production
  deployment for its own app, gated by its own contract tests. No shared berth,
  so no queue, so no guard 0, no guard 1, no guard 4b, no preemption rules, no
  rebase loop. Scenario D4 becomes unstateable rather than defended against.
- *Staging stops being scarce*, because it stops being the only place where
  cross-app truth is discovered.

So read the guard sequence as a /faithful model of a common failure/, not as a
recommendation. Organizations really do run this way, the coordination costs
really do land where this spec puts them, and the reason to build it carefully
is that the machinery is load-bearing exactly as long as the contracts are
missing. A reader who takes the pipeline home without noticing the note has
taken home the wrong artifact.

*Non-goal:* fixing it. This repo demonstrates change enablement under a shared
path to production. Replacing that with per-team contracts would be a different
repo, and a shorter one.

* Domain model

*The workflow is generic; the semantics are the product.* This section states
the model without reference to GitHub, because a guard that can only be
expressed in one vendor's vocabulary is a guard we have not understood. The
label names elsewhere in this document are one /encoding/ of what follows, not
the thing itself.

** Entities

| Entity                | Definition                                                                 | GitHub encoding                    |
|-----------------------+----------------------------------------------------------------------------+------------------------------------|
| *change*              | a unit of intent, with an author, a base, and a head                        | pull request                       |
| *manifest*            | the set of deployable components a change touches; /derived/ from the diff  | =app:*= labels, labeller-owned     |
| *gate*                | a function from a content hash to a verdict in {pass, fail}                 | a check run                        |
| *suite*               | all gates; green iff every member is green /and/ the self-test is green     | the required-checks set            |
| *berth*               | an exclusive, deadline-bearing lease on the path to production              | the =deploy:staging= label + lock  |
| *path to production*  | the ordered environments a change traverses: staging → production           | environments                       |
| *divergence*          | the classified relation between a change's base and the trunk tip           | computed by =divergence.sh=        |
| *authorization*       | normal (earned by gates) or emergency (granted by a person)                 | =change:emergency=                 |
| *deployment record*   | platform-attested statement that artifact X reached environment Y           | the Deployments API                |

Two of these are load-bearing and routinely got wrong:

- *manifest is derived, never asserted.* It is a function of the diff, owned by
  automation, and a human edit to it must not survive. If it can be asserted,
  it is not a manifest — it is a wish, and the build ships whatever someone
  typed. (Scenario L10.)
- *deployment record is attested, not self-reported.* The difference is who
  says it happened: the platform, or the job that wanted it to. A job claiming
  its own success is not evidence.

  *And GitHub's Deployments API does not meet this bar* [E, 2026-09-13]. A
  deployment is created by a caller (=creator= is a user or app) and its status
  is POSTed to =statuses_url= by that same caller; with Actions environments
  the state mirrors *the job's* status. GitHub never contacts the target. So
  the row above records intent, exactly like a Release does — it is a
  self-report with good provenance about *who claimed it*, not evidence about
  *what is running*. Capability C6 is therefore *unmet on GitHub*, not merely
  awkward, and guard 4 rests on guard 5's sampling instead.

** The guards as predicates

Let =H(c)= be a change's head hash, =B(c)= its base, =T= the trunk tip,
=merges(x,y)= the merges on trunk in =(x, y]=, and =class(m)= the divergence
class of a merge.

| Guard | Predicate                                                              | Evaluated                 |
|-------+------------------------------------------------------------------------+---------------------------|
| *0*   | =B(c) = T=                                                             | at berth claim            |
| *1*   | =|{x : holds_berth(x)}| ≤ 1=                                           | continuously              |
| *2*   | =∀g ∈ suite : g(H(c)) = pass=, and =selftest(H(c)) = pass=             | at promote *and* at deploy |
| *4*   | =staged(H(c)) ∨ (emergency(c) ∧ approved(c))=                          | at deploy                 |
| *4b*  | =∀m ∈ merges(B(c), T) : class(m) ∈ {inert, pipeline}=                  | *at reliance*, not request |
| *5*   | =served_build(production) = H(c)=                                      | after deploy              |

Guard 2 appears twice on purpose (§Emergency — the only bypass). Guard 4b's
"at reliance" is the whole content of the rule: *a guard whose subject can
change after it is checked must be re-checked at the moment it is relied on.*

** Conformance — what a platform must provide

The guards reduce to six capabilities. This is the checklist for any platform,
and the thing to confirm early in a rollout:

| # | Capability                                                        | Needed by     | Rarity                      |
|---+-------------------------------------------------------------------+---------------+-----------------------------|
| C1 | mutable, queryable state on a change, *owned by automation*      | manifest, all | common                      |
| C2 | verdicts bound to a *content hash*, not a branch or a change id  | guard 2       | common, often misconfigured |
| C3 | an *exclusive lease* with owner and deadline, readable by others  | guard 1       | uncommon                    |
| C4 | an *event when the trunk moves*                                   | guard 4b      | *rare*                      |
| C5 | verdicts that are *revocable after issue*                         | guard 4b      | *rare*                      |
| C6 | a *platform-attested* deployment record                           | guard 4       | uncommon                    |

C4 and C5 are the expensive ones, and they are both guard 4b's — which is
consistent with §strict does not protect production, where no ruleset rule
could express it either. *If a platform gives you only one thing, take C2;
if it gives you two, take C2 and C5.* A verdict you cannot revoke is a
verdict that outlives its own truth.

C2's failure mode deserves naming because it is silent: bind a verdict to a
branch or a change id instead of a hash and everything still appears to work,
right up until the head moves and a stale pass authorizes a deploy. That is
scenario D4's mechanism with a different cause.

** What this buys

Stating the model this way is what makes the rest portable. =spec.org='s
labels, =scenarios.org='s cases, =tla/='s invariants and
=gates/pbt-pipeline.py='s model all reduce to the predicates above; the
GitHub-specific parts are the /encoding/ column of the first table and nothing
else. A port is then a conformance exercise — check C1–C6, encode the six
predicates — rather than a rewrite.

** Simulated changes

=make simulate app=<group>= appends a line to =apps/<group>/src/CHANGELOG.txt= and bumps =version= in =package.json=. The diff is enough for the labeller to attach =app:<group>=. No behavior changes; the point is exercising the pipeline.

* Router and ports

** Port block model

Each git worktree owns a contiguous block of ten ports. The router (nginx) listens on the block base; apps listen on base + offset.

| Worktree              | Block | nginx | core  | plp   | pdp   | checkout | mock backend |
|-----------------------+-------+-------+-------+-------+-------+----------+--------------|
| main (stable)         |     0 | 10000 | 10001 | 10002 | 10003 |    10004 |        10005 |
| first branch worktree |     1 | 10010 | 10011 | 10012 | 10013 |    10014 |        10015 |
| second                |     2 | 10020 | 10021 | 10022 | 10023 |    10024 |        10025 |
| n-th                  |     n | 10000+10n | +1 | +2   | +3    | +4       | +5           |

Ports 10006–10009 (and the same offsets in each block) are unallocated.

** Reaching a block from another host

Ports bind to =127.0.0.1= by default; =BIND=0.0.0.0= opts a block into the LAN.
That is necessary but *not sufficient* on hydra, where =pf= is enabled and
passes =192.168.86.0/24= only to ssh, 2812, 3000, =7000:7699= and =8000:9999=
[E, 2026-09-13]. *The default base of 10000 falls outside every open range*, so
a correctly-bound block is still refused — and the refusal is immediate, which
reads exactly like nothing listening.

=PORT_BASE= therefore selects the base: =PORT_BASE=9000= puts block =n= at
=9000 + 10n=, inside the range =pf= already allows, with no firewall change.
The blocks are otherwise identical.

: PORT_BASE=9000 ./change/ports.sh alloc
: BIND=0.0.0.0  ./change/ports.sh run-apps      # -> router on 9000 + 10n

Observed: blocks 1 and 2 serving on =:9010= and =:9020=, each reporting its own
build sha, =gates/e2e.sh= green against both over the LAN address.

** nginx template

The template is rendered once per worktree from =router/routes.json= and =.env.ports=. Each route prefix proxies to the owning app's port. A worktree that has not built an app falls back to the stable app on block 0, which is the local equivalent of a staging slot that deploys only the changed group.

#+begin_src nginx :tangle router/nginx.conf.tmpl
# rendered per worktree: BLOCK, and per app PORT_<APP> (falls back to block-0 port)
worker_processes 1;
events { worker_connections 64; }
http {
  server {
    listen ${NGINX_PORT};
    location = /            { proxy_pass http://127.0.0.1:${PORT_CORE}; }
    location /login         { proxy_pass http://127.0.0.1:${PORT_CORE}; }
    location /account       { proxy_pass http://127.0.0.1:${PORT_CORE}; }
    location /cart          { proxy_pass http://127.0.0.1:${PORT_CORE}; }
    location /search        { proxy_pass http://127.0.0.1:${PORT_PLP}; }
    location /c/            { proxy_pass http://127.0.0.1:${PORT_PLP}; }
    location /p/            { proxy_pass http://127.0.0.1:${PORT_PDP}; }
    location /checkout      { proxy_pass http://127.0.0.1:${PORT_CHECKOUT}; }
    location /api/          { proxy_pass http://127.0.0.1:${PORT_MOCK}; }
  }
}
#+end_src

The =location= lines are generated from =routes.json=; the block above is the expected output, not the source. A gate (=gates/lint.sh=) fails when the rendered file and =routes.json= disagree.

** Cloud mirror

A staging slot =staging-<group>-<n>= is the same topology: one router in front of four app upstreams. The changed group points at the PR build; the other three point at the current production build. The Cloudflare target implements the router as a Worker with a service binding per app; the GitHub target implements it as a GitHub Environment per slot whose deployment payload records the four upstream SHAs (Pages serves the static builds; the router is simulated by =routes.json= plus per-app base paths).

* Labels

Supersedes the per-group staging-slot model sketched in §Router and ports
§Cloud mirror: *staging is a single environment, held by one PR at a time*, not
=n= slots per group. Which apps deploy is decided by the =app:*= labels on the
PR that holds it. Slots may return later as an optimization; they are not in
0.2. [P]

| Label                  | Set by      | Removed by        | Meaning                                                      |
|------------------------+-------------+-------------------+--------------------------------------------------------------|
| =app:<group>=          | labeller    | labeller          | The diff touches =apps/<group>/=. *Owned* by the labeller     |
| =change:standard=      | labeller    | labeller          | Diff limited to =apps/**=                                     |
| =change:normal=        | labeller    | labeller          | Diff touches =router/=, =gates/=, =change/=, =targets/=, =.github/= |
| =change:emergency=     | human       | human             | Authorizes the staging bypass. The only such authorization    |
| =deploy:staging=       | human       | promote / release | Requests the staging lock. At most one open PR may carry it   |
| =staging:in-progress=  | workflow    | workflow          | Staging deploy or its e2e run is live                        |
| =staging:passed=       | workflow    | push to PR        | Authorizing e2e passed *on the current head SHA*              |
| =staging:failed=       | workflow    | push to PR        | Staging deploy or e2e failed; fix and re-request              |
| =deploy:production=    | *promote*   | release           | Added by automation on =staging:passed=; by a human only with =change:emergency= |
| =production:healthy=   | workflow    | release           | Post-deploy health check passed; merge is unblocked           |
| =deployed:production=  | workflow    | —                 | Set after the PIR comment is posted                          |
| =blocked:queue=        | queue guard | queue guard       | Another open PR holds =deploy:staging=                        |
| =blocked:lock=         | preflight   | preflight         | Another deployment holds the deployment lock                 |
| =blocked:freeze=       | preflight   | preflight         | A freeze or emergency event covers the requested window      |

*Ownership matters.* The labeller runs with =sync-labels: true=, so it both adds
and removes =app:*= — a PR that stops touching =apps/pdp/= loses =app:pdp= and
stops deploying it. A human hand-adding =app:*= is overwritten on the next
push; this is intended, and it is why the =app:*= set can be trusted as the
build manifest.

*=labeler:skip= is the declared exception.* It stops the labeller entirely, so
=app:*= becomes hand-maintained — for forcing a build across apps the diff does
not touch. State the cost plainly, because it is the one the model cares about:
§Domain model says the manifest is *derived, never asserted*, and that if it can
be asserted "it is not a manifest — it is a wish, and the build ships whatever
someone typed". =labeler:skip= makes that true on purpose.

So it is a *declared deviation in label form*: visible on the PR, carried into
the PIR, and surfaced by =./status=. It does not disable any guard — the gates,
the berth and guards 4b and 5 are unaffected — it only moves the manifest from
derived to asserted, and says so where a reviewer can see it.

*=staging:passed= is bound to a SHA.* Any push to the PR removes it (and
=staging:failed=). A pass observed on an earlier commit authorizes nothing.

#+begin_src yaml :tangle .github/workflows/labeller.yml
name: labeller
on: [pull_request_target]
permissions: {contents: read, pull-requests: write}
jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/labeler@v5
        # labeler:skip hands the manifest back to a human -- for forcing a build
        # across apps the diff does not touch. See the note below: this converts
        # a DERIVED artifact into an ASSERTED one, and the PR wears the label
        # saying so.
        if: "!contains(github.event.pull_request.labels.*.name, 'labeler:skip')"
        with:
          sync-labels: true          # the labeller OWNS app:* and change:{standard,normal}
      # change:standard is the COMPLEMENT of change:normal, which actions/labeler
      # cannot express -- it matches globs, it cannot say "matched no other rule".
      # The offline oracle modelled this as derived and the config never
      # implemented it, so PRs got app:* and no change:* at all. Third time the
      # model and the implementation have diverged; the implementation was wrong
      # here, and only a live run showed it.
      - name: classify standard vs normal
        if: "!contains(github.event.pull_request.labels.*.name, 'labeler:skip')"
        env: {GH_TOKEN: "${{ github.token }}"}
        run: |
          R=${{ github.repository }}
          labels=$(gh pr view "${{ github.event.number }}" --repo "$R" --json labels -q '[.labels[].name]')
          has_app=$(echo "$labels" | jq 'map(select(startswith("app:")))|length')
          is_normal=$(echo "$labels" | jq 'index("change:normal")//empty')
          if [ "$has_app" -gt 0 ] && [ -z "$is_normal" ]; then
            gh pr edit "${{ github.event.number }}" --add-label change:standard \
              --remove-label change:normal || true
          elif [ -n "$is_normal" ]; then
            gh pr edit "${{ github.event.number }}" --repo "$R" --remove-label change:standard || true
          fi

      - name: drop stale staging verdicts on a new push
        if: github.event.action == 'synchronize'
        env: {GH_TOKEN: "${{ github.token }}"}
        run: |
          gh pr edit "${{ github.event.number }}" \
            --remove-label staging:passed --remove-label staging:failed || true
#+end_src

The second step is the SHA binding: a new push invalidates any staging verdict,
so =deploy:production='s guard can never see a pass from an older commit.

* Gates

Three gates run on every PR for every =app:*= group. Each gate exits non-zero on any finding; there is no warning tier.

| Gate | Script           | Scope                                                                         |
|------+------------------+-------------------------------------------------------------------------------|
| lint | =gates/lint.sh=  | eslint per app; =routes.json= schema; rendered nginx matches =routes.json=      |
| test | =gates/test.sh=  | =node --test= per app                                                         |
| e2e  | =gates/e2e.sh=   | Playwright: the group's journeys plus every =tests/e2e/= journey that touches it |

The e2e gate runs against a worktree-style router inside the runner (block 0 ports, all four apps built from the PR SHA). The same gate reruns against the staging slot URL after =deploy-staging=; the second run is the one that authorizes production.

** Negative tests for the gates

Each gate script has a fixture under =gates/fixtures/<gate>/fail/= that the gate must reject and =gates/fixtures/<gate>/pass/= it must accept. =make gate-selftest= runs both and fails if either outcome is wrong. This is a separate workflow job, required before the gates' own results count.

* Change enablement

** Preflight (=gates/preflight.sh=)

Runs before any staging or production deployment.

1. Lock: read the =deployment-lock= GitHub Discussion (or issue #1) body. If it names a PR other than this one and the run is under 60 minutes old, exit 2 and set =blocked:lock=. A lock older than 60 minutes is stale; preflight clears it and records the clearance in the PIR of the stale run.
2. Freeze: query the change schedule for events in the next 30 minutes with title prefix =FREEZE:= or =EMERGENCY:=. Any match: exit 3, set =blocked:freeze=. Repo variable =EMERGENCY_CHANGE=1= has the same effect and is the fallback when the calendar is unreachable.
3. Concurrency: production workflows use =concurrency: production= with =cancel-in-progress: false=; staging workflows use =concurrency: staging-<group>-<n>=.

Exit codes: 0 proceed, 2 lock, 3 freeze, 4 calendar unreachable and no repo variable set (treated as blocked).

** Change schedule (=change/schedule.sh=)

- =schedule.sh block <pr> <group> <minutes>= creates a calendar event =CHANGE: standard-change#<pr> <group>= on the agentic account's calendar with the owner as attendee and notifications on. The event description holds the PR URL, the SHA, and the staging slot.
- =schedule.sh check <window>= returns the freeze/emergency events overlapping the window.
- =schedule.sh close <event-id> <result>= appends the result (pass/fail/cancelled) to the event description at the end of the run.

The skill wraps these three commands. Deployment workflows call =block= before deploying and =close= in an =always()= step.

** Deployment lock (=change/lock.sh=)

=acquire <pr> <target>= writes =pr, target, run-id, started_at= to the lock body; =release= empties it. Release runs in an =always()= step. The 60-minute stale rule in preflight covers a runner that dies without reaching =release=.

* Promotion pipeline

One PR at a time owns staging; passing there promotes it automatically; a
healthy production deploy merges it and releases the queue.

** State machine

#+begin_src mermaid :eval never-export
stateDiagram-v2
    [*] --> Open: PR opened
    Open --> Gated: labeller sets app:*, gate.yml green on head SHA
    Gated --> Queued: human adds deploy:staging
    Queued --> Open: G0..G3 fail -> label removed, blocked:* set
    Queued --> Staging: guards pass, staging lock acquired
    Staging --> Gated: e2e fails -> staging:failed, lock released
    Staging --> Promoted: authorizing e2e passes -> staging:passed@SHA
    Promoted --> Production: promote.yml adds deploy:production
    Gated --> Production: change:emergency + approval (bypasses staging)
    Production --> Unhealthy: health check fails -> rollback + PIR
    Unhealthy --> Gated: labels released
    Production --> Healthy: health check passes -> production:healthy
    Healthy --> Merged: auto-merge, or a human merges
    Merged --> [*]: release -> all deploy:* labels removed, queue freed

** The guards

Each is a hard precondition. None is skippable except where stated, and the
only thing that can state it is =change:emergency=.

| # | Guard                    | Checked by             | On failure                          | Emergency bypass |
|---+--------------------------+------------------------+-------------------------------------+------------------|
| 0 | Up to date with =main=   | =change/queue.sh=      | remove =deploy:staging=, comment    | yes              |
| 1 | Staging held by no other PR | =change/queue.sh=   | =blocked:queue=, label removed      | n/a (skips staging) |
| 2 | Gates green on head SHA  | =promote.yml=          | refuse to promote                   | *no*             |
| 3 | No lock, no freeze       | =gates/preflight.sh=   | =blocked:lock= / =blocked:freeze=   | freeze only      |
| 4 | =staging:passed@head SHA= | =deploy-production.yml= | refuse to deploy                   | yes, with approval |
| 4b | Head still contains main's tip | =main-moved.yml=, =deploy-production.yml=, =release.sh= | withdraw pass; hold the berth | yes |
| 5 | Production health check  | =gates/health.sh=      | roll back, PIR, release             | *no*             |

*Guard 2 and guard 5 have no bypass at all.* An emergency may skip the staging
/environment/; it may not ship code whose unit and lint gates are red, and it
may not leave an unhealthy production deploy standing.

*Guard 2 is therefore evaluated twice*, in =promote.yml= and again in
=deploy-production.yml=. This is not belt-and-braces: =promote.yml= is gated on
the =staging:passed= label, so the emergency path never reaches it. A single
evaluation there would have given guard 2 precisely the bypass this paragraph
denies. [E — the omission was real and shipped; see §Open items.] Note the TLA+
model had it right all along: =Promote= and =DeployAndMerge= both require
=gated[p]=. The workflow, not the model, had drifted.

** Guard 0 — up to date with main

A standard or normal change must contain the current tip of =main= before it
may take staging. This is not tidiness: staging and production deploy the PR
head, so a PR that is /behind/ main would deploy a tree missing whatever merged
since — silently reverting the previous deployment. The guard is the thing that
makes "we don't lose the previous deployment" true rather than hoped-for.

It also drives the queue. When the holder merges and releases the labels, every
other open PR is now behind =main= by exactly that merge, so the next claimant
must rebase first. The rebase is not busywork — it is the re-verification that
the two changes compose, and it happens before staging rather than after
production.

: gh pr view <pr> --json mergeStateStatus -q .mergeStateStatus

=BEHIND= fails the guard. =BLOCKED= and =DIRTY= (conflicts) also fail. =CLEAN=
and =UNSTABLE= pass — =UNSTABLE= means checks are still running, which guard 2
catches properly at promote time with SHA binding.

** Guard 1 — staging is a singleton

#+begin_src bash :tangle change/queue.sh :shebang "#!/bin/sh"
# queue.sh claim <pr>   -- guards 0 and 1. Exit 0 claim, 5 queue busy, 6 behind main.
set -eu
pr="$2"
repo="${GH_REPO:-$GITHUB_REPOSITORY}"

emergency=$(gh pr view "$pr" --repo "$repo" --json labels \
  -q '[.labels[].name] | index("change:emergency") // empty')

# Guard 0: up to date with main (standard and normal changes only)
if [ -z "$emergency" ]; then
  state=$(gh pr view "$pr" --repo "$repo" --json mergeStateStatus -q .mergeStateStatus)
  case "$state" in
    BEHIND|BLOCKED|DIRTY)
      gh pr edit "$pr" --repo "$repo" --remove-label deploy:staging
      gh pr comment "$pr" --repo "$repo" --body \
        "Staging refused: branch is \`$state\` relative to \`main\`. Rebase onto \`main\` and re-add \`deploy:staging\` — deploying a tree behind main would revert the previous deployment."
      exit 6 ;;
  esac
fi

# Guard 1: no other open PR holds staging
holder=$(gh pr list --repo "$repo" --state open --label deploy:staging \
  --json number -q "[.[].number] | map(select(. != $pr)) | first // empty")
if [ -n "$holder" ]; then
  gh pr edit "$pr" --repo "$repo" --add-label blocked:queue --remove-label deploy:staging
  gh pr comment "$pr" --repo "$repo" --body \
    "Staging is held by #$holder. Re-add \`deploy:staging\` once it merges; you will need to rebase onto \`main\` first."
  exit 5
fi

gh pr edit "$pr" --repo "$repo" --remove-label blocked:queue || true
echo "claimed"
#+end_src

The label query is the authority, not the workflow concurrency group:
=concurrency= serializes /runs/, but a PR that deployed and is sitting in
production verification still /holds/ staging with no run in flight. The label
is the lock; =concurrency: staging= is only the anti-collision on top of it.

** Guard 4b — why a request-time guard expires

*Amendment, 0.2 → 0.3. Scenario D4 in =scenarios.org= refuted 0.2 and forced
this; the spec tracks observed reality.*

Guard 0 is evaluated once, when staging is claimed. =staging:passed= is
invalidated when the /PR/ moves. Neither covers =main= moving underneath a PR
that has already passed staging and is holding =deploy:production=. That PR
would deploy a tree predating whatever just merged — silently reverting it,
with every gate green, because the gates were green on a SHA that no longer
composes with main.

The emergency path makes this the normal case rather than a rare race: an
emergency /is/ a merge to main that jumps the queue.

#+begin_src yaml :tangle .github/workflows/main-moved.yml
name: main-moved
on:
  push:
    branches: [main]
permissions: {contents: read, pull-requests: write}
jobs:
  invalidate:
    runs-on: ubuntu-latest
    env: {GH_TOKEN: "${{ github.token }}"}
    steps:
      - uses: actions/checkout@v4
      - name: expire staging verdicts that main has outrun
        run: |
          for pr in $(gh pr list --state open --label staging:passed --json number -q '.[].number'); do
            state=$(gh pr view "$pr" --json mergeStateStatus -q .mergeStateStatus)
            case "$state" in
              BEHIND|BLOCKED|DIRTY)
                gh pr edit "$pr" --remove-label staging:passed \
                                 --remove-label deploy:production \
                                 --remove-label deploy:staging
                gh pr comment "$pr" --body "\`main\` moved (${{ github.sha }}). Your staging pass described a tree that no longer composes with main, so it has been withdrawn along with the staging claim. Rebase onto \`main\` and re-add \`deploy:staging\`."
                ;;
            esac
          done
#+end_src

Guard 4 additionally re-checks =mergeStateStatus= at production time, because a
guard evaluated at request time expires:

: gh pr view "$PR" --json mergeStateStatus -q .mergeStateStatus   # must not be BEHIND

*The general rule, worth more than the instance:* any guard whose subject can
change after it is checked must be re-checked at the moment it is relied on.
Guard 0 at claim time is a convenience that gives fast feedback; guard 4b is
the one that is load-bearing. Note the amendment also drops =deploy:staging=,
which frees the queue — an expired claimant must not keep holding it.

** The berth, and four ways to lose it

A change occupies one of four positions. Only the last two are at risk from
=main= moving, and they are at risk /differently/.

| # | Position    | Means                                       | Labels                             |
|---+-------------+---------------------------------------------+------------------------------------|
| 1 | =scheduled= | window booked, no claim on the path         | =CHANGE:= event; no =deploy:*=     |
| 2 | =berthed=   | holds the path to production, deploying     | =deploy:staging=, =staging:in-progress= |
| 3 | =verified=  | authorizing e2e passed on this head         | + =staging:passed=                 |
| 4 | =cleared=   | promoted, about to ship                     | + =deploy:production=              |

=scheduled= is a record and nothing blocks on it. =berthed= is the scarce
resource. *Being verified is not being safe*: positions 3 and 4 are precisely
where a change looks finished and can still be wrong, because everything about
them was established against a =main= that has since moved.

** Guard 4b — classify the divergence, do not collapse it

=change/divergence.sh= classifies what landed under a berthed change. The
distinction is the whole guard: /"you are behind main"/ and /"you are about to
ship an image missing a hotfix"/ are different facts, and treating them alike
fails in both directions — a README merge forcing a full re-verify teaches
people the guard is noise, and a hotfix merge not forcing one is scenario D4.

| Class      | What landed                                | Berth | Staging pass | Message                                    |
|------------+--------------------------------------------+-------+--------------+--------------------------------------------|
| =inert=    | docs, =.meta=, =scenarios=, =experiments=, =tla= | kept  | *kept*       | informational only                         |
| =pipeline= | =gates/=, =change/=, =.github/=, =Makefile= | kept  | kept, re-run gates | "how you are verified changed"        |
| =artifact= | =apps/=, =router/=, =targets/=             | kept + extended | *withdrawn* | "rebase and re-run staging"       |
| =hotfix=   | any merge carrying =Change-Type: emergency= | kept + extended | *withdrawn* | "you would ship without the fix"    |

*The berth is never taken away by someone else's merge.* This is the correction
scenario D4's first fix got wrong: withdrawing =deploy:staging= freed the queue,
which is right when a claimant goes stale on its own, and wrong when it was
invalidated by someone jumping ahead of it. A change that was preempted keeps
its position and gets an extension (=change/state.sh extend=) to rebase and
revalidate. Losing your berth because someone else had an emergency is a
punishment for being in the queue at the wrong moment.

Staleness and preemption are therefore separated:

- *self-inflicted* — you pushed, or your lease simply expired → release the
  berth, rejoin the queue.
- *preemption* — =artifact= or =hotfix= landed under you → keep the berth,
  =.revalidate = true=, deadline extended, and the pass must be re-earned.

The two messages a =verified= change can receive, verbatim, because the
difference is what the reader needs:

#+begin_example
[artifact] main moved and it touched what you ship.
  merged: apps/pdp/src/price.js
  Your staging pass described an image that is no longer what you would
  deploy. Berth held until 14:20Z. Rebase onto main and re-add deploy:staging.

[hotfix] an emergency landed under you.
  CHG-20260912-0007 (#312) shipped apps/checkout/src/session.js
  Deploying your current image would REVERT it. This is not a staleness
  warning. Berth held until 14:35Z; the pass is withdrawn until staging
  re-runs on a tree containing the fix.
#+end_example

An =inert= divergence prints nothing beyond a note on the PR. A change that is
behind =main= only on documentation is behind in a way that cannot affect the
artifact, and guard 0 at the /next/ claim will make it rebase anyway.

** Promotion — staging pass to production

#+begin_src yaml :tangle .github/workflows/promote.yml
name: promote
on:
  pull_request:
    types: [labeled]
permissions: {contents: read, pull-requests: write, checks: read}
jobs:
  promote:
    if: github.event.label.name == 'staging:passed'
    runs-on: ubuntu-latest
    env: {GH_TOKEN: "${{ github.token }}", PR: "${{ github.event.pull_request.number }}"}
    steps:
      - uses: actions/checkout@v4
      # Guard 2: every gate green on THIS head SHA. No bypass, emergency included.
      - name: require gates green on head SHA
        run: |
          sha="${{ github.event.pull_request.head.sha }}"
          bad=$(gh api "repos/${{ github.repository }}/commits/$sha/check-runs" \
                 --jq '[.check_runs[] | select(.name|test("^(gate-selftest|lint|test|e2e)")) 
                        | select(.conclusion != "success")] | length')
          total=$(gh api "repos/${{ github.repository }}/commits/$sha/check-runs" \
                 --jq '[.check_runs[] | select(.name|test("^gate-selftest$"))] | length')
          [ "$bad" -eq 0 ] || { echo "::error::$bad gate(s) not green on $sha"; exit 1; }
          [ "$total" -ge 1 ] || { echo "::error::gate-selftest never ran on $sha; gate results are void"; exit 1; }
      - name: promote
        run: |
          gh pr edit "$PR" --add-label deploy:production
          gh pr comment "$PR" --body "Staging authorizing run passed on \`${{ github.event.pull_request.head.sha }}\`. Promoting to production."
#+end_src

Guard 2 checks =gate-selftest= ran /and/ is green before trusting the other
three — a gate suite whose self-test never ran produces no verdict, so its
green is void rather than merely unverified (§Verification contract).

** Emergency — the only bypass

=change:emergency= is a human label and the sole authorization to reach
production without =staging:passed=. It does not bypass guard 2 or guard 5.

#+begin_example
change:emergency + deploy:production
  → require: one approving review from a change authority
  → require: gates green on head SHA        (guard 2, no bypass)
  → preflight: lock only; a FREEZE event does not block an emergency
  → deploy production
  → health check                            (guard 5, no bypass)
  → PIR records: bypassed staging, why, who approved, and the merge-base
    divergence from main at deploy time
#+end_example

An emergency PR is exempt from guard 0, so it may be behind =main=. The PIR
therefore records the divergence explicitly: shipping a tree behind main is a
known, accepted regression risk, and naming it is the difference between an
emergency change and an accident.

Note the asymmetry with §Change enablement: an =EMERGENCY:= event on the change
schedule /blocks everyone else/, while the =change:emergency= label /exempts one
PR/. Same word, opposite direction; the calendar governs the estate, the label
governs a change.

** Health check and release

#+begin_src bash :tangle gates/health.sh :shebang "#!/bin/sh"
# health.sh <base-url> <expected-sha> [samples] -- guard 5. Exit 0, or 7.
#
# Asserts CONVERGENCE, not liveness. Two defects the single-sample version had:
#
#   1. It made TWO requests per route -- one for the status code, one for the
#      header -- so during a rolling deploy the first could hit an old replica
#      and the second a new one, and the pair would pass while the estate was
#      mixed. Both facts must come from ONE response.
#   2. One sample cannot distinguish "converged" from "I happened to reach a
#      new replica". A fleet that is 10% migrated passes one sample 10% of the
#      time, which is not a bug you find by re-running.
#
# So: N samples per route, every one must report the expected build. This is
# still only evidence, not proof -- see spec.org, What completes a deployment.
set -eu
base="$1"; want="$2"; samples="${3:-${HEALTH_SAMPLES:-5}}"; rc=0
MODE="${HEALTH_MODE:-header}"   # header | manifest (static targets)

for app in $(jq -r '.[].app' router/routes.json); do
  path=$(jq -r --arg a "$app" '.[] | select(.app==$a) | .health' router/routes.json)
  seen=""; bad=0
  n=1
  while [ "$n" -le "$samples" ]; do
    # Cache-bust. A CDN with max-age=600 serves the OLD build for ten
    # minutes after deploy, and a convergence check that trusts it is
    # measuring the CDN, not the estate (spec.org, Targets).
    bust="$(date +%s)-$n"
    if [ "$MODE" = "manifest" ]; then
      # Static targets (GitHub Pages) cannot set response headers, so the
      # served build is published as a generated file instead.
      body=$(curl -sS --max-time 10 -H "Cache-Control: no-cache" \
               "$base/version.json?_cb=$bust" 2>/dev/null || echo "{}")
      code=$(curl -sS -o /dev/null --max-time 10 -H "Cache-Control: no-cache" \
               -w "%{http_code}" "$base/version.json?_cb=$bust" 2>/dev/null || echo 000)
      sha=$(printf '%s' "$body" | jq -r '.sha // "-"' 2>/dev/null || echo "-")
    else
      # one request, both facts
      resp=$(curl -sS -o /dev/null --max-time 10 -H "Cache-Control: no-cache" \
               -w '%{http_code} %header{x-build-sha}' "$base$path?_cb=$bust" \
               2>/dev/null || echo "000 -")
      code=${resp%% *}; sha=${resp##* }
    fi
    case "$seen" in *" $sha "*) : ;; *) seen="$seen $sha " ;; esac
    if [ "$code" != "200" ] || [ "$sha" != "$want" ]; then bad=$((bad+1)); fi
    n=$((n+1))
  done
  distinct=$(echo "$seen" | tr ' ' '\n' | grep -c . || true)
  if [ "$bad" -gt 0 ]; then
    echo "UNHEALTHY $app: $bad/$samples samples not serving $want (saw:$seen)"
    rc=7
  elif [ "$distinct" -gt 1 ]; then
    echo "UNCONVERGED $app: still serving more than one build (saw:$seen)"
    rc=7
  else
    echo "ok $app $path ($samples/$samples on $want)"
  fi
done
exit $rc
#+end_src

The SHA assertion is the load-bearing half. A 200 only proves /something/ is
serving; =x-build-sha= proves the thing we just deployed is serving. A health
check that cannot distinguish the new deploy from the old one passes happily
through a failed deploy, which is the silent failure this gate exists to catch.

On =rc=7=: roll back to the previous production SHA from the deployment record,
post the PIR with the failure, remove =deploy:production= and =deploy:staging=,
and release the lock. The queue frees even on failure — a broken deployment
must not also wedge the pipeline.

On success: =production:healthy=, PIR comment, =deployed:production=, then

#+begin_src bash :tangle change/release.sh :shebang "#!/bin/sh"
# release.sh <pr> -- merge (if auto-merge enabled) and free the queue.
set -eu
pr="$1"; repo="${GH_REPO:-$GITHUB_REPOSITORY}"

# Guard 4b, at the MERGE. Not redundant with the activation check: with more
# than one deployment in flight, two changes can both pass guard 4b (trunk has
# not moved yet) and then merge in sequence -- the first moves trunk, the
# second lands a tree predating it. Found in sim/ at berths=2. Activation is
# not the last point of reliance; the merge is.
emergency=$(gh pr view "$pr" --repo "$repo" --json labels \
  -q '[.labels[].name] | index("change:emergency") // empty')
if [ -z "$emergency" ]; then
  state=$(gh pr view "$pr" --repo "$repo" --json mergeStateStatus -q .mergeStateStatus)
  if [ "$state" = "BEHIND" ] || [ "$state" = "DIRTY" ]; then
    base=$(gh pr view "$pr" --repo "$repo" --json baseRefOid -q .baseRefOid)
    class=$(./change/divergence.sh "$base" origin/main || true)
    case "$class" in
      artifact|hotfix)
        gh pr edit "$pr" --repo "$repo" --remove-label staging:passed \
                                        --remove-label deploy:production
        gh pr comment "$pr" --repo "$repo" --body \
          "Merge refused: \`main\` moved during your window and it was a \`$class\` change. Production is deployed but this tree predates what is now on main, so merging it would revert that. Rebase and re-run staging; the berth is held."
        exit 8 ;;
    esac
  fi
fi

if [ "${AUTO_MERGE:-1}" = "1" ]; then
  gh pr merge "$pr" --repo "$repo" --squash --delete-branch
else
  gh pr comment "$pr" --repo "$repo" --body "Production healthy. Ready to merge; the staging queue frees on merge."
fi
gh pr edit "$pr" --repo "$repo" \
  --remove-label deploy:staging --remove-label deploy:production \
  --remove-label staging:passed --remove-label production:healthy
./change/lock.sh release

# Announce ONCE, on the queue issue -- never fan out to every waiter.
#
# The previous version commented on each blocked:queue PR. At the several-
# hundred-PR scale that is one API call per waiter per release, and worse than
# the cost: the queue has no ordering, so telling everyone at once produces a
# thundering herd that all rebase and race for a berth exactly one of them can
# take. Announcing once turns the queue into something waiters read rather than
# something that pages them.
gh issue comment "${QUEUE_ISSUE:-1}" --repo "$repo" --body \
  "Staging freed by #$pr at $(date -u +%FT%TZ). Next claimant: rebase onto \`main\` first -- guard 0 will refuse a branch that is behind."
#+end_src

Repo variable =AUTO_MERGE=0= turns the last hop manual: production is deployed
and verified, and a human merges. Everything before the merge is identical, so
the variable changes who presses the button and nothing about what was checked.

* Workflows

          ./router/generate.sh
          # A fresh registry: the committed ports.tsv claims block 0 for a
          # developer's path, so alloc would hand this runner block 1 and the
          # router would not be where the next step looked.
          echo "PORTS_REGISTRY=$RUNNER_TEMP/ports.tsv" >> "$GITHUB_ENV"
          PORTS_REGISTRY=$RUNNER_TEMP/ports.tsv ./change/ports.sh alloc
          PORTS_REGISTRY=$RUNNER_TEMP/ports.tsv ./change/ports.sh run-apps
          sleep 4
      - name: journeys through the router
        run: |
          . ./.env.ports
          echo "router on $BASE_PORT"
          ROUTER_URL="http://127.0.0.1:$BASE_PORT" ./gates/e2e.sh
      - if: always()
        run: PORTS_REGISTRY=$RUNNER_TEMP/ports.tsv ./change/ports.sh stop || true
#+end_src

** deploy-production.yml skeleton

#+begin_src yaml :tangle .github/workflows/deploy-production.yml
name: deploy-production
on:
  pull_request:
    types: [labeled]
permissions: {contents: write, pull-requests: write, deployments: write}
jobs:
  deploy:
    if: github.event.label.name == 'deploy:production'
    runs-on: ubuntu-latest
    concurrency: {group: production, cancel-in-progress: false}
    environment: production          # require reviewers here for change:normal
    env: {GH_TOKEN: "${{ github.token }}", PR: "${{ github.event.pull_request.number }}"}
    steps:
      - uses: actions/checkout@v4
      # Guard 2 AGAIN, here and not only in promote.yml. promote.yml is gated on
      # the staging:passed label, so the emergency path never reaches it; without
      # this step guard 2 has exactly the bypass the spec says it does not have.
      - name: require gates green on head SHA
        run: |
          sha="${{ github.event.pull_request.head.sha }}"
          runs=$(gh api "repos/${{ github.repository }}/commits/$sha/check-runs")
          bad=$(echo "$runs" | jq '[.check_runs[]
                 | select(.name|test("^(gate-selftest|lint|test|e2e)"))
                 | select(.conclusion != "success")] | length')
          self=$(echo "$runs" | jq '[.check_runs[]
                 | select(.name|test("^gate-selftest$"))
                 | select(.conclusion == "success")] | length')
          [ "$bad" -eq 0 ] || { echo "::error::$bad gate(s) not green on $sha"; exit 1; }
          [ "$self" -ge 1 ] || { echo "::error::gate-selftest did not pass on $sha; gate results are void"; exit 1; }
      # Guard 4: no production without a staging pass on THIS SHA, unless emergency.
      - name: require staging pass or emergency
        run: |
          labels=$(gh pr view "$PR" --json labels -q '[.labels[].name]')
          echo "$labels" | jq -e 'index("staging:passed")' >/dev/null && exit 0
          echo "$labels" | jq -e 'index("change:emergency")' >/dev/null || {
            echo "::error::no staging:passed on head SHA and not change:emergency"; exit 1; }
          gh api "repos/${{ github.repository }}/pulls/$PR/reviews" \
            --jq '[.[]|select(.state=="APPROVED")]|length' | grep -qv '^0$' || {
            echo "::error::change:emergency requires an approving review"; exit 1; }
      - run: ./gates/preflight.sh production
      - run: ./change/lock.sh acquire "$PR" production
      - run: ./targets/${{ vars.DEPLOY_TARGET }}/deploy.sh production "$(./change/groups.sh "$PR")"
      - name: health check
        run: ./gates/health.sh "${{ vars.PRODUCTION_URL }}" "${{ github.event.pull_request.head.sha }}"
      - if: failure()
        run: ./targets/${{ vars.DEPLOY_TARGET }}/rollback.sh production
      - if: always()
        run: ./change/pir.sh "$PR" "${{ job.status }}"
      - if: success()
        run: |
          gh pr edit "$PR" --add-label production:healthy --add-label deployed:production
          ./change/release.sh "$PR"
      - if: always()
        run: ./change/lock.sh release
#+end_src

** Targets

=vars.DEPLOY_TARGET= selects =github= or =cloudflare=. Both expose =deploy.sh <env> <groups...>=, =rollback.sh <env>=, and write =.slot-url=.

| Target     | Staging                                    | Production                       | Router                          |
|------------+--------------------------------------------+----------------------------------+---------------------------------|
| github     | Environment =staging=; Pages branch        | Environment =production=; Pages  | =routes.json= + base-path rewrite |
| cloudflare | Worker per app named =<group>-staging=     | Worker per app, production route | Router Worker, service bindings |

Each target must expose the served build. *A response header is not always
available*: GitHub Pages serves static files through a fixed CDN header set and
*cannot set custom response headers* [E, verified 2026-09-13 against
=pages.github.com=], so =x-build-sha= is unimplementable there. Two modes:

| target                | how the served build is exposed          | guard 5 mode |
|-----------------------+------------------------------------------+--------------|
| cloudflare (Worker)   | =x-build-sha= response header            | =header=     |
| github (Pages)        | a generated =/version.json= =({"sha":…})= | =manifest=   |

Pages also sends =cache-control: max-age=600= [E, observed =age: 284= on a
live response], so *"deployed" and "served" can be ten minutes apart*. Guard 5
must bust the cache or wait out the TTL; a convergence check that trusts a CDN
is measuring the CDN. This is the clearest case of §Domain model's C2 warning
arriving in a new place: the artifact you verify must be the artifact being
served, and a cache is another way for those to differ.

* Checklists

Each checklist is a =.github/PULL_REQUEST_TEMPLATE= section and a =pir.sh= field. Unchecked required items block the corresponding label from taking effect (=gates/preflight.sh= reads the PR body).

** Standard change (before =deploy:<group>=)

- [ ] =app:*= labels match the intended groups
- [ ] Gate self-test green
- [ ] lint, test, e2e green on head SHA
- [ ] Change window length stated (default 30 minutes)

** Production (before =deploy:production=)

- [ ] =deployed:staging-<group>-<n>= present for every =app:*= group
- [ ] Staging e2e run is on the head SHA (not a prior push)
- [ ] No =blocked:*= label
- [ ] For =change:normal=: one approving review from a listed change authority
- [ ] Rollback SHA recorded in PR body (=pir.sh= fills this from the production deployment record)

** Post-implementation review (generated)

- Gate durations per app
- Staging slot and window event ids
- Production deployment record id and previous SHA
- Any stale-lock clearance or freeze wait encountered
- Journeys run against production and their results

** The tuple

Every claim in this repo lives at a coordinate:

- *platform* — the OS the gate ran on.
- *router* — how the four apps are fronted: =nginx= locally, a Worker or
  base-path rewrite in the cloud.
- *browser* — what Playwright drives.

A cell is *supported* only when a gate was /watched/ to pass on it, with
versions recorded in §Host survey of record. Anything else is [H].

- *nginx* — *resolved 2026-09-13*. The =pkg= catalogue was stale; after

- *eslint is not installed* [E]; it is a project-local dev dependency, so this

- *=make= is BSD make* [E]; GNU Make 4.4.1 is available as =gmake= [E]. The

- *wrangler is not installed* [E]; the Cloudflare target is unexercised.

* Verification contract

- *Two gates, different things.* The code gate is =gates/{lint,test,e2e}.sh=.
  The documents gate is this spec and its derived files: every =:tangle= target
  resolves, every internal reference names a section that exists, and =CLAUDE.md=
  asserts nothing absent here. Neither substitutes for the other.
- *Ordering is load-bearing.* =gate-selftest= runs /before/ the gates' own
  results count. A gate whose negative fixture it fails to reject produces no
  usable verdict that run — its PASS is void, not merely suspect.
- *Pass criterion.* A gate passes when it exits 0 with zero findings. There is
  no warning tier.
- *Promotion.* A matrix cell moves from [H] to [E] only when a human watched
  all three gates pass on it and the exact versions were pasted into §Host
  survey of record. A green run on convenient infrastructure grants a claim
  nothing that was not observed on a real target cell.
- *The second e2e run authorizes production*, not the first. The in-runner run
  proves the build; the staging-slot run proves the deployment.

* Controls audit

Every control the spec claims is auditable as JSON, without a UI visit.
=gates/audit-controls.py= is four reads: rulesets, the workflow files,
environments, and repository variables.

** Three outcomes, never two

The audit distinguishes =ok= / =FINDING= / =ABSENT= / =UNAVAILABLE=, and the
last is the one that matters. *An audit that reports "no findings" because it
could not read anything is worse than no audit* — it launders an unknown as a
pass, which is the failure mode §Verification contract exists to prevent.
Unreadable controls exit 2, distinct from findings (1) and clean (0).

** Ruleset rules to spec controls

| Ruleset rule                   | Control it enforces                              | Audit check                                      |
|--------------------------------+--------------------------------------------------+--------------------------------------------------|
| Require a pull request         | every change is a PR with =app:*=; no direct push | =rules[].type == "pull_request"=; approvals >= 1  |
| Require status checks          | the gates are the change authority                | contexts ⊇ {=gate-selftest=, =lint=, =test=, =e2e=} |
| — its =strict= flag            | guard 0, *at merge only* — see below              | =strict_required_status_checks_policy == true=    |
| Require deployments to succeed | staging before production                         | =required_deployment_environments= lists =staging= |
| Require linear history         | one logical step per commit; single-parent rollback | =required_linear_history=                       |
| Block force push / deletion    | the recorded production SHA stays reachable       | =non_fast_forward=, =deletion=                    |
| Bypass list                    | who may skip the change authority                 | empty, or only the named emergency actor          |
| Enforcement status             | rules exist but are not applied                   | =enforcement == "active"=; =evaluate= is a finding |
| Target branches                | rules cover the production branch                 | =~DEFAULT_BRANCH= or =refs/heads/main=            |

Out of scope, and ignored deliberately: code scanning, code quality, coverage
thresholds, Copilot review. A project may enable them; this model makes no
claim about them, and an audit that scored them would be scoring someone else's
spec.

** =strict= does not protect production [E]

Their natural reading is that =strict_required_status_checks_policy= covers the
"staging run is on the head SHA" checklist item. It does not, and the reason is
specific to this pipeline: *production deploys before the merge.* In
=deploy-production.yml= the health check runs at the deploy step and
=change/release.sh= merges afterwards. So =strict= gates a merge that happens
/after/ production has already taken the change.

=strict= is therefore a backstop on =main='s history, not a guard on the
estate. It is a partial, native implementation of *guard 0* — and only at merge
time. *Guard 4b remains load-bearing and is not replaceable by any ruleset
rule*, because the window it closes opens after every ruleset check has passed.

** The per-group limitation dissolved at 0.3

=required_deployments= is static per ruleset and cannot express "only the slot
for the changed group". That was a real limitation against the 0.1 model's
=staging-<group>-<n>= slots. At 0.3 staging is a *singleton* (§Labels), so
=required_deployment_environments: ["staging"]= expresses the control exactly.
The constraint that made the rule awkward was our own.

** Not expressible as ruleset rules

Three controls need their own reads, and the audit does them:

- *deployment lock* — the issue or discussion body, plus =concurrency= groups
  in the workflow files. The audit checks =cancel-in-progress: false= on
  production: a cancelled production deploy leaves an indeterminate estate,
  which is worse than a queue.
- *freeze and emergency* — the change schedule, and the =EMERGENCY_CHANGE=
  repository variable as the fallback when the calendar is unreachable.
- *environment protection* — =environments/production= must carry a required
  reviewer for =change:normal=, =wait_timer= 0, and a =deployment_branch_policy=
  restricting which branches may deploy.

** Availability on the development box [E, 2026-09-13]

Against =aygp-dr/standard-change= the audit returns *eight unreadable
controls*: both =repos/{r}/rulesets= and the classic
=branches/main/protection= answer =403 Upgrade to GitHub Pro or make this
repository public=. Verified across 50 repos on this account: 35 public → 200,
15 private → 403, no exceptions. The org route is closed too — =defrecord= and
=walsh= are free orgs whose private repos 403 identically. Environment
/protection rules/ carry the same gate, so =environment: production= is
decorative here.

*This is a property of the development box, not of the model.* The target is an
enterprise account, where every control in the table above is available. The
finding is kept because it exercised something worth keeping — the audit's
four-outcome design. An audit reporting "no findings" because it could not read
anything would have laundered an unknown as a pass. That distinction is the
point; the plan tier is incidental.

** On an enterprise account

What becomes available, and what it changes:

| Capability                        | Effect on the model                                            |
|-----------------------------------+----------------------------------------------------------------|
| repo + *org-level* rulesets       | the guard table can be enforced once, across every repo, rather than configured per repo |
| environment protection rules      | guard 4's approval becomes platform-attested instead of a =pulls/{n}/reviews= query in a job |
| required reviewers as *teams*     | "a named change authority" stops being one person; §The balance's =prevent_self_review= deadlock dissolves |
| CODEOWNERS enforcement            | =change:normal='s path-based authority becomes native rather than a labeller convention |
| *custom deployment protection rules* | see below — this is the significant one |

*Custom deployment protection rules are the native home for guard 4b.* An app
can approve or reject a pending deployment /at deployment time/, which is
precisely the "at reliance, not at request" semantics the guard requires
(§Domain model, capabilities C4 and C5). On the free tier guard 4b has to be
synthesised from a =push= trigger on trunk plus label withdrawal
(=main-moved.yml=); on enterprise it can be a gate the platform itself asks
before letting the deployment proceed — attested rather than self-reported,
and revocable by construction.

That is worth designing toward now, because it changes /where/ the guard lives
without changing /what it says/. The predicate in §Domain model is unchanged;
only the encoding moves. Which is the claim §Domain model exists to make.

* What completes a deployment

The model had no answer to this, which is worth stating plainly because three
layers each invented a different one:

| layer         | what ended a deployment                                  |
|---------------+----------------------------------------------------------|
| =sim/=        | *a timer* — =clock >= activated + hold_slots=             |
| =tla/=        | *nothing* — =CompleteMerge= is enabled whenever guards pass |
| =gates/health.sh= | *one sample*, taken in two separate requests           |

None of those is a completion condition. A timer says time passed; an enabled
transition says nothing was forbidden; one sample says one replica answered.

** Three events, routinely conflated

| event     | means                                        | attested by                  |
|-----------+----------------------------------------------+------------------------------|
| *live*    | the estate serves the new build              | guard 5 (convergence)        |
| *closed*  | the change record is complete (ITIL)         | the PIR                      |
| *merged*  | trunk contains the change                    | the forge                    |

These occur in that order and are not interchangeable. *The berth protects the
estate but is released on =merged=, a repository event* — a mismatch worth
naming even though releasing slightly late is the safe direction.

** Convergence, not liveness [E, experiments/004]

Guard 5 now asserts that N samples all report the expected build, and reports
=UNCONVERGED= when it sees more than one. Measured against a deliberately
half-migrated fleet (two =apps/core= instances on different =BUILD_SHA= behind
an nginx round-robin):

- the old single-sample check *passed 6 of 12 runs* on an estate that was half
  unmigrated;
- the new check refused it every time (=4/8 samples not serving newsha22=);
- and passed once the old replica was retired (=8/8=).

The old failure mode is the dangerous kind: it *looks like flake*, so the
reflex is to re-run until green — and re-running until green is precisely what
manufactures a false pass against a mixed population.

** What it still does not know [P]

N samples is evidence, not proof. It cannot see a replica taking no traffic
during the window, it samples through whatever the load balancer chooses, and
it says nothing about in-flight requests still being served by the old build.
*A sampling check cannot establish convergence; it can only fail to refute
it.* Proof needs the platform to enumerate its own replicas and their
versions — which is capability C6, a platform-attested deployment record, and
is exactly why an attested record outranks a self-reported one.

So the honest answer: *a deployment completes when the platform says every
serving instance runs the new build, and in the absence of such a platform we
substitute repeated sampling and record that we have done so.*

* C6, and the one platform that can meet it

=docs/release-standards.org= found capability C6 — a *platform-attested*
deployment record — unmet on GitHub and unstandardised generally. Cloudflare
Workers *versions* appear to meet it [E from docs, [H] until run]:

| requirement                              | Workers versions                                   |
|------------------------------------------+----------------------------------------------------|
| promote the artifact staging tested      | upload and deploy are decoupled; deploy a version *by ID* |
| immutable artifact identity              | each version has a unique ID with creation metadata |
| a record written by the platform         | =wrangler deployments list= — Cloudflare's own      |
| rollback to a known previous artifact    | revert to a previously deployed version             |
| the served build is identifiable         | a Worker can set =x-build-sha= directly             |

Contrast =wrangler environments=, which are the *wrong primitive for a path to
production*: =[env.staging]= and =[env.production]= create *separate Worker
scripts* named =<worker>-<env>=, each deployed from source with =--env=. There
is no promotion between them, so production would run a script staging never
tested — the precise failure §Cloud mirror forbids. Environments separate
config; versions carry artifacts.

** Why GitHub cannot meet C6 and Cloudflare can

The difference is not API quality, and stating it properly generalises:

#+begin_quote
*A platform can attest to what is running only if it runs it.*
#+end_quote

GitHub's Deployments API records a claim about *someone else's* estate —
GitHub never contacts the target, so its record is a self-report with good
provenance about who claimed it. Cloudflare runs the Workers, so its record of
which version serves is a statement about its own estate. That is what makes
one attestation and the other bookkeeping, and it is the test to apply to any
future target: *does the recorder run the code?*

** Gradual deployment makes guard 5 ambiguous [P]

A Workers deployment may reference *two versions at once*, splitting traffic.
So a mixed fleet becomes an *intended state*, and guard 5 as written
(§What completes a deployment) reports =UNCONVERGED= for it — correctly by its
own definition and uselessly in context.

Guard 5 therefore needs an expected shape rather than a single expected build:
converged on X, or split between X and Y at a declared ratio. *Sampling cannot
supply that* — it cannot distinguish an intended 10% canary from an accidental
90%-stale estate without being told which to expect. Which is the argument for
C6 again from the other side: the platform's record says what the split is
*meant* to be, and sampling can then check the estate against it rather than
guessing.

Not implemented. Recorded because it falsifies the current guard 5 for any
canary or gradual rollout, which is the normal case for services.

* Every automation has a bypass

Not a concession — a design rule. An automation without a declared escape hatch
does not get obeyed, it gets *circumvented*, and a circumvention leaves no
record. §The balance already measured one instance of this: queue friction does
not slow delivery, it routes traffic onto =change:emergency=, the one path with
fewer checks. The general form:

#+begin_quote
*Design the bypass, or one gets invented in the dark.*
#+end_quote

The catalogue, so no future exception has to be argued from first principles:

| automation                    | bypass                | what it costs                        | where it shows |
|-------------------------------+-----------------------+--------------------------------------+----------------|
| labeller owns =app:*=         | =labeler:skip=        | manifest becomes asserted, not derived | label on the PR |
| staging must pass             | =change:emergency=    | no staging evidence for this change  | label + approval + PIR |
| the berth queue               | =change:emergency=    | jumps the queue                      | label + PIR    |
| the freeze window             | =EMERGENCY_CHANGE=    | the calendar stops governing         | repo variable  |
| guard 0 up-to-date            | =change:emergency=    | may ship behind trunk                | PIR records the divergence |
| *guard 2 gates green*         | *none*                | —                                    | —              |
| *guard 5 production healthy*  | *none*                | —                                    | —              |

** The two that have none, and why

The rule is not "everything has a bypass". It is:

#+begin_quote
Everything has a bypass *except the things whose bypass would make the system
lie about itself.*
#+end_quote

Guard 2 is the gate suite's verdict on this exact tree. Bypass it and every
downstream record — the staging pass, the PIR, the deployment record — asserts
a verification that did not happen. Guard 5 is the only evidence that what was
deployed is what is serving; bypass it and "deployed" becomes a claim rather
than an observation (§What completes a deployment).

Those are not stricter rules than the others. They are the rules that keep the
*other* bypasses honest: =change:emergency= is a legible, auditable act
precisely because the records it appears in are otherwise true.

** What makes a bypass acceptable

Three properties, and all three are required:

1. *Visible on the artifact* — a label on the PR, not a flag in a job.
2. *Carried into the record* — the PIR names it and who authorized it.
3. *Narrow* — it suspends one automation, not the guards around it.
   =labeler:skip= stops the labeller and touches no gate; =change:emergency=
   skips the staging environment and still faces guards 2 and 5.

A "force" flag fails all three, which is why =docs/idp-api.org= refuses to
offer one: a flag that appears to bypass guards 2 or 5 would be a lie in the
API surface.

* The balance

*The objective is protecting production. The queue and the calendar are
instruments.* Stating the hierarchy matters because every control below has a
cost, and a control whose cost is paid in queue time buys nothing unless it
also reduces the chance of an unsafe change reaching the estate.

** What each control actually protects

| Control              | Protects                | Cost is paid in       | Removable? |
|----------------------+-------------------------+-----------------------+------------|
| gate-selftest        | *production*            | seconds               | no         |
| lint / test / e2e    | *production*            | minutes               | no         |
| guard 5 health check | *production*            | seconds               | no         |
| guard 4 staging pass | *production*            | one staging cycle     | emergency only |
| guard 4b divergence  | *production*            | a rebase, when earned | no         |
| guard 0 up-to-date   | production, indirectly  | a rebase              | emergency only |
| guard 1 singleton    | *the queue*             | berth wait            | *negotiable* |
| freeze window        | *the calendar*          | berth wait            | *negotiable* |
| change window record | nothing; it is a record | nothing               | n/a        |

The first five are load-bearing: each closes a path by which a broken or
unauthorized change reaches production. The last three are coordination
devices. They are worth having, and they are the ones to tune.

** Over-protecting the queue costs production safety

This is not the usual safety-versus-speed trade, and reading it that way gets
the sign wrong.

=change:emergency= is the *one* label that bypasses staging. So queue friction
does not convert into slower-but-equally-safe delivery — it converts into
traffic on the path with fewer checks. =gates/simulate-gates.py= models it: at
a mean berth wait of two hours roughly a sixth of changes route to emergency;
past about four hours it is the majority. Tighten the queue far enough and you
have optimised your way to *less* production safety, through the only door you
deliberately left open.

The practical consequences, which is why this section exists rather than being
a remark:

- *Guard 1's singleton is the tunable*, not the gates. If the berth is the
  bottleneck, add berths (per-team paths to production, §What this model gets
  wrong) before weakening a gate. Never trade a gate for throughput; the gates
  are the reason the berth is worth holding.
- *Freezes should be narrow and few.* A freeze protects the calendar's promise,
  not the estate. A standing freeze is indistinguishable from a slow queue, and
  produces the same emergency traffic.
- *A change window is a record and must never block.* The moment writing it can
  fail closed, a calendar outage becomes a deployment outage — see
  §Change enablement, preflight exit 4, and the =EMERGENCY_CHANGE= fallback that
  exists precisely because a /record/ was allowed to become a /control/.
- *Watch the emergency rate as the health metric.* A rising share of
  =change:emergency= is not an incident trend; it is the queue reporting that it
  has become too expensive to use honestly. The PIR already records every
  bypass, so the number is free.

** Where the balance was already wrong, and corrected

Guard 4b as first written withdrew =deploy:staging= on any movement of =main=.
That protected production and charged the queue for it indiscriminately — a
README merge cost a full rebase and re-verify, and the berth went back to the
pool. Both corrections in §Guard 4b are this section applied:

- *classify the divergence*, so only =artifact= and =hotfix= — the classes that
  can actually change what ships — withdraw the staging pass;
- *never take the berth for someone else's merge*, because losing your position
  to another team's emergency is a cost with no corresponding safety gain.

The test for any future control is the same: name what it protects, name who
pays, and if the answer is "the queue pays and production gains nothing",
it is ceremony.

* At scale

The design has a throughput ceiling and it is the berth. =gates/simulate-gates.py --soak=
computes it: 20 checks at 95% with one re-run of failed checks, 30-minute
holds.

| PRs | berths | wall-clock | mean wait | emergency share |
|-----+--------+------------+-----------+-----------------|
| 100 |      1 |     2.2 d  |    26.3 h |          100.0% |
| 100 |     16 |     0.1 d  |     1.6 h |           13.2% |
| 200 |      1 |     4.4 d  |    52.6 h |          100.0% |
| 500 |      1 |    11.0 d  |   131.4 h |          100.0% |
| 500 |     16 |     0.7 d  |     8.2 h |           98.6% |

*A few hundred changes through one berth is weeks of serialized wall-clock*,
and §The balance says what that queue wait does: the emergency share goes to
100%. So a high-volume soak run against a singleton berth *does not test the
pipeline — it tests the bypass*, because by the time the queue is that deep
every change has a rational reason to carry =change:emergency=.

Read that carefully, because it is not a defect the soak /finds/. It is the
singleton berth meeting its design limit, exactly where §What this model gets
wrong, on purpose says it would. The remedy is the one already named there —
hard contracts at the router and a path to production per team — and the scale
requirement is *evidence for that fix rather than a new problem*.

Consequences for anyone planning a soak:

- *Do not measure gate behaviour through a deep queue.* Guards 2 and 5 are
  per-change and can be soaked at any N. Guards 0, 1 and 4b are queue
  properties and are the thing under test; conflating them wastes the run.
- *Widen the berth first, or shorten the hold.* Sixteen berths brings 100 PRs
  to under a day. At 500 even sixteen is not enough, which is the honest signal
  that per-team paths to production — not more berths on one path — is the
  answer.
- *Or do not run it at all.* =gates/pbt-pipeline.py --exhaustive= already
  enumerates every ordering at a small bound, deterministically, in seconds. A
  soak buys evidence about /volume and flake/, not about /correctness of the
  guards/; the exhaustive model already settles the latter more completely than
  any number of PRs could.

* Refutation conditions

Concretely, what observation falsifies this repo's central claim — /that the
gate sequence prevents an unauthorized or unsafe production deployment/:

1. A production deployment completes while =blocked:lock= or =blocked:freeze=
   is set, or while another production run holds the lock.
2. =gates/preflight.sh= exits 0 when the change schedule is unreachable and no
   =EMERGENCY_CHANGE= variable is set (it must exit 4 and block).
3. Any gate passes on a =gates/fixtures/<gate>/fail/= input, or fails on the
   matching =pass/= input. Either direction voids the gate.
4. =deploy-production.yml= deploys a group that has no
   =deployed:staging-<group>-<n>= label on the head SHA.
5. A =change:normal= PR reaches production with no approving review.
6. The rendered nginx config and =router/routes.json= disagree while
   =gates/lint.sh= exits 0.
7. A stale lock older than 60 minutes is cleared without the clearance
   appearing in a PIR.
8. The share of changes carrying =change:emergency= rises without a matching
   rise in incidents — the queue has become too expensive to use honestly, and
   the bypass is absorbing normal traffic (§The balance).

Each is a test to be written, not merely a worry. Until they exist as
executable checks, the central claim is [H].
