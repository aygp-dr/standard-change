#+TITLE: Who owns a label, and what happens when nobody does
#+DATE: 2026-09-13

* The failure this documents

On 2026-09-13, =production:healthy= on PR #9 was added and withdrawn four times
in nine minutes:

: 15:23:21  +production:healthy   by aygp-dr            (a person typed gh pr edit)
: 15:23:31  -production:healthy   by github-actions     (8 seconds later)
: 15:32:13  +production:healthy   by aygp-dr
: 15:32:24  -production:healthy   by github-actions     (11 seconds later)

Nobody was wrong about the world. Both writers were doing exactly what they had
been told to do, and the result was a label that flickered and a change that
silently could not proceed. *Thrash is not a bug in either writer. It is the
absence of an owner.*

* Rule 1 — every label has exactly one writer, and it is the instrument

An observation label may be written *only by the thing that took the
measurement*. Not by a person who read the measurement, not by a workflow that
believes the measurement, not by an agent summarising a terminal.

| label                  | the instrument                        | may a person write it? |
|------------------------+---------------------------------------+------------------------|
| =staging:e2e=          | =gates/e2e.sh --pr=                   | no                     |
| =staging:smoke=        | =gates/smoke.sh --pr=                 | no                     |
| =production:healthy=   | =gates/health.sh --pr=                | no                     |
| =staging:uat=          | *a person* — for acceptance, the person IS the instrument | yes, via =change/observe.sh= |
| =release=              | a person — it is intent, not a measurement | yes               |
| =hold:staging=         | a person                              | yes                    |
| =deploy:<env>=         | the workflow doing the deploying      | no                     |
| =change:*=             | the pipeline, as the record advances  | =change:requested= only |

*The violation that started this.* =production:healthy= was typed by hand
because =health.sh= had no =--pr= flag, unlike =e2e.sh= and =smoke.sh=. A gate
with no way to record its own verdict forces someone else to record it, and
that someone is then asserting a measurement they did not take. *A missing
=--pr= flag is a label-ownership defect, not a convenience gap.*

* Rule 1b — derived labels are owned by the deriver, and ownership transfers by an opt-out, never by an edit

=app:*= and =change:standard= are *derived*: the labeller computes them from the
diff on every push. They are owned by the labeller, absolutely, and hand-editing
one is not a disagreement the system can see — the next push simply recomputes
it and your edit is gone. There is no argument, and no record that one was had.

So the escape hatch is not "edit the label", it is *=labeler:skip=*:

: if: "!contains(github.event.pull_request.labels.*.name, 'labeler:skip')"

=labeler:skip= hands the manifest back to a human — for forcing a build the
diff does not imply, or suppressing one it wrongly does. This is the right
shape for every derived label, and it generalises:

| | |
|--------------------------------+----------------------------------------------|
| *wrong*                        | edit the derived label; it is silently recomputed away |
| *right*                        | add the opt-out; ownership transfers, visibly and on the record |

Three properties make the opt-out better than an edit, and they are the reason
to prefer this pattern anywhere a machine derives a label:

1. *It is visible.* =labeler:skip= sits on the PR where a reviewer sees it. An
   overwritten =app:*= looks identical to a correctly derived one.
2. *It is durable.* The skip survives the next push. An edit does not.
3. *It names the disagreement.* The label says "a human has taken this over",
   which is a fact worth recording. An edit says nothing — it is indistinguishable
   from the machine's own output, which is precisely how a forged observation
   hides.

The same reasoning is why =hold:staging= is a separate label rather than
"remove =staging:e2e= so it stops promoting". Removing an annotation to change
behaviour is editing a measurement. Adding a hold states an intent.

*Corollary.* If you find yourself wanting to hand-edit a derived or observed
label, the missing thing is an opt-out label, not permission to edit. That is
the shape of the fix.

* Rule 2 — unreachable is not falsified

This is the rule the thrash actually broke.

=merge-on-healthy.yml= is right to distrust the label that triggered it — its
own comment says *"do not trust the label that triggered this"*, and
re-deriving rather than trusting is correct. It then failed, withdrew
=production:healthy=, and refused the merge.

It was not observing divergence. It was observing *nothing*: the runner is
=ubuntu-latest= and production is on hydra's =192.168.86.0/24=. No GitHub
runner can open a socket to any environment in this repository. The check could
not run, and its inability to run was recorded as a negative result.

: could not observe   ->  treated as  ->  observed to be false

Those are different states and collapsing them is what produced the thrash. The
correct behaviour when an instrument cannot reach its subject is to *abstain*:
say so, refuse to proceed, and *leave the label alone*. Withdrawing a label you
could not check is asserting a measurement you did not take — the same defect as
adding one, in the opposite direction.

*Failing closed is right. Falsifying is not.* The merge should still refuse.
What it must not do is rewrite the record of somebody else's measurement.

* Rule 3 — an agent owns no observation label

Claude, or any agent driving this pipeline, is not an instrument. It runs
instruments and reads their output.

This was violated three times on 2026-09-13, each time by an agent typing a
label a gate should have written:

1. =staging:passed= was moved from failed to passed using a measurement from a
   different estate, which authorized a production deploy through guard 4.
2. =production:healthy= was typed by hand, above.
3. =staging:smoke= was recorded against the *production* front, because the gate
   hardcoded the environment name into the label.

All three have the same shape: *a label whose name does not fully identify what
was measured can be satisfied by measuring something else.* Naming the
environment and the instrument in the label is not bookkeeping; it is what makes
the label checkable.

The agent's legitimate moves are to run the instrument, to report what it said,
and to say plainly when it could not run. It may also carry a human's intent
(=release=, =hold:staging=) when asked, because intent is the human's to give.

* Rule 4 — a label with two writers needs a tiebreak written down

Where two writers genuinely must touch one label, the precedence must be
explicit, because the alternative is last-write-wins and last is not the same
as authoritative:

- a *failure* annotation outranks its *pass*: =guard4.sh= refuses when
  =staging:e2e-failed= is present even if =staging:e2e= is too. A recorded
  failure must be withdrawn deliberately, not overwritten by whichever
  instrument ran most recently.
- an *annotation* never outranks the *record*: nothing in =staging:*= or
  =production:*= may set or clear =change:*=.
- a *human hold* outranks every automated pass. =hold:staging= is lifted only by
  a person.

* Rule 5 — a label cannot carry a build, so a guard must not authorize on one

Rules 1 to 4 settle *who* may write a label. They say nothing about *what a
label can hold*, and that is where the next failure came from.

On 2026-09-13, #11's head moved =9d85a33= → =baed821=. Twenty-five minutes
later the pull request still carried =staging:e2e staging:smoke staging:uat=,
recorded against =9d85a33=, and guard 4 read them as authorization for
=baed821=. Nobody had measured what was about to ship (issue #16).

The labels were written by their declared instruments, at a moment when each
was true. Every rule above was obeyed. The defect is one level down: *a label
names the measurement and cannot name the build*. =staging:e2e= says e2e
passed; it cannot say on what.

The pipeline covered that gap with a cleanup step — the labeller withdraws
every observation on =synchronize=. That makes the guard sound only for as long
as the cleanup keeps firing, and it fails *open* when it stops. It stopped.

The repair is not a better cleanup. It is to split observations by a property
of the measurement itself:

| kind | example | can it be re-taken? | what authorizes |
|------+---------+---------------------+-----------------|
| repeatable | =staging:e2e=, =staging:smoke=, =production:healthy= | yes, by a machine | the observation *record* — a PR comment naming environment, instrument, verdict and SHA — whose SHA must equal the head being authorized |
| not repeatable | =staging:uat= | no; a person used the site | the record *and* the label, because the label is the person's own signal and a person may withdraw it |

A record does not go stale and so does not need withdrawing. It stays true
about the build it names and simply stops matching a newer head. Nothing has to
fire for that to hold, which is the whole difference:

: durable label          "this PR has passed staging e2e"
: point-in-time record   "the run at 16:06 observed e2e green on 9d85a33"

The labels stay, and they stay useful — they are the *current-run* signal the
deployment process sets as it goes and clears as it moves on, and they are what
a person reads at a glance. What they are no longer is the thing a guard
authorizes on. Written by =change/evidence.sh record=, read by
=change/evidence.sh latest=, enforced in =change/guard4.sh= and
=gates/production-first.sh=, and tested offline by =gates/observation-test.sh=,
which is itself negative-tested against the frozen pre-#16 guard.

Two things this does *not* fix, recorded so they are not mistaken for fixed:

- nothing stops a person typing an observation marker into a comment by hand,
  exactly as nothing stops a person adding the label by hand. =evidence.sh
  latest= reports the comment author and no guard enforces it yet.
- =change/settle.sh= still requires the =staging:*= labels rather than the
  records, because it runs where the estate is visible and re-derives the part
  that matters (what production is serving) directly.

* What this costs, and why it is still right

Rule 2 means the merge on this repository cannot be automated at all: the only
thing that can check production is on hydra, and the only thing that can merge
is on GitHub. That is the reachability gap, and it is the honest consequence of
refusing to let a workflow falsify what it cannot see.

See =docs/adr/0001-automatic-promotion.org= Option 0, and
=experiments/013-freebsd-browser/notes.org= for why the label is a proxy for a
check run in the first place.
