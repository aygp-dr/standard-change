#+TITLE: The IDP service, and a divergence from the prior art
#+DATE: 2026-09-13

* What it is

=.idp/server.mjs=, SQLite-backed, gitignored. Started with =node .idp/server.mjs=,
listens on =:9300=.

| route                      | |
|----------------------------+------------------------------------------|
| =/healthz=, =/health=      | both, same body                          |
| =/changes=                 | every change and its state               |
| =/transitions=             | the state machine, and where it came from |
| =/change?pr=N=             | one change: state, cleared checks, history, *what is allowed next* |
| =/advance?pr=N&to=STATE=   | a transition, refused if illegal          |
| =/clear?pr=N&check=NAME=   | clear a named check                      |

Both health spellings are served because =guile-changeflow= serves =/health= and
everything k8s-shaped expects =/healthz=. Nobody should have to guess which one
this service chose.

* The health check asks the database

=/healthz= runs =SELECT count(*) FROM change= and reports what came back.

It would be cheaper to return =200 {"status":"ok"}= from a handler that does
nothing, and that is the defect this project spent the day finding: *guard 5
passed on a SHA that did not exist* because it read back a manifest its own
deployer had written. A health check that reports the server's *intent* to be
working is the same shape. Degraded returns *503*, not 200-with-a-sad-field,
because a caller that only reads status codes must not see a lie.

* The divergence, recorded rather than resolved

The transitions are lifted verbatim from
=dsp-dr/guile-changeflow src/models/state-machine.scm=, the prior art this
project has cited since =spec.org=. *Two of them differ from the Python copy in
=.claude/skills/_shared/idp.py=*, which claims to be that state machine:

| from           | guile-changeflow                    | our =idp.py=                  |
|----------------+-------------------------------------+-------------------------------|
| =implementing= | completed failed *cancelled*        | completed failed              |
| =failed=       | *implementing* cancelled            | assessing cancelled           |

The first is minor — guile lets you cancel mid-implementation.

*The second is a policy disagreement and it matters.* guile lets a failed
change be retried *directly*: =failed → implementing=. The Python copy sends it
back to =assessing=, requiring re-approval before another attempt.

Those encode different answers to: *does a failed deployment need
re-authorisation before you try again?*

- guile says no — the change was approved, the deployment failed, try again
- =idp.py= says yes — a failure is new information, reassess

Neither is wrong. *What is wrong is that nobody chose.* The Python file says it
implements guile's machine and does not, and the difference only appears when a
deployment fails — the moment you least want to discover that two components
disagree about what happens next.

The service follows *guile*, because it is the cited source and a copy that
silently edits its source is worse than either policy.

* Which is right for this pipeline

Unresolved, and it interacts with something already decided. =guard 4b= and
=change/settle.sh= re-check at the moment of reliance, and
=docs/changing-the-pipeline.org= argues a pipeline change is proven by *use*.
Under those, a failed deployment has already invalidated its staging pass —
=main= may have moved, the estate may be mid-cutover — so *=assessing= is
arguably the honest destination even though guile permits =implementing=*.

Trigger to decide: the first deployment that actually fails after approval.
Until then both are written down and the disagreement is visible, which is
better than the file quietly having an opinion.

* Why gitignored

Per-host state: which slots *this* machine granted, which checks *it* saw
clear. Fifth instance of the rule today, after =ports.tsv=, =front.pid=,
=targets/node/live= and =ports.tsv= again — each stale the moment it was
committed, and between them they blocked three rebases and caused a production
503 when a git operation deleted the file the front reads per request.

The durable, shared record stays where it was: =change/schedule.sh=, a
compare-and-swap git ref.
