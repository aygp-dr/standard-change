#+TITLE: What actually forces these apps to deploy together
#+SUBTITLE: A concern, recorded — not scheduled for a fix
#+DATE: 2026-09-13
#+OPTIONS: toc:2 num:t

* The question

Is there something here like a vendored library or a shared gem — cross-cutting,
and forcing a *shared* deployment?

Yes. Two of them, and *one was introduced during this session while fixing
something else*.

* 1. router/routes.json — a live shared artifact

All five apps read =router/routes.json= at startup to build their nav:

: ALL_ROUTES = JSON.parse(readFileSync(join(here,'..','..','..','router','routes.json')))

=router/routes.json= is *generated from every app's own =routes.json=*. So:

#+begin_src mermaid :eval never-export
flowchart LR
    A1["apps/plp/routes.json"] --> G["router/routes.json<br/>generated union"]
    A2["apps/pdp/routes.json"] --> G
    A3["apps/core/routes.json"] --> G
    G --> R["the router"]
    G --> C1["core reads it"]
    G --> C2["plp reads it"]
    G --> C3["pdp reads it"]
    G --> C4["checkout reads it"]
    G --> C5["mock reads it"]
    style G fill:#fecaca,stroke:#b91c1c,color:#000
#+end_src

*A route added to plp changes what core renders.* Core has not changed, its
tests still pass, and it must still be redeployed — or it serves a nav that
describes an estate that no longer exists.

That is precisely a vendored shared library: a artifact every consumer links
against, where a change at the source obliges every consumer to ship.

*It was introduced by a fix.* The nav was originally generated at authoring
time and went stale the moment core gained =/about=; making it read the live
file removed the staleness and created the coupling. *The two are the same
property seen from different sides* — a nav that cannot go stale is a nav that
forces coordinated deployment.

* 2. The app source is vendored by copy

| app      | lines differing from =core= |
|----------+-----------------------------|
| plp      | 4 of 68                     |
| pdp      | 4 of 68                     |
| mock     | 4 of 68                     |
| checkout | 12 of 66                    |

*Roughly 94% identical.* The HTML view, the nav, the header handling and the
=isMain= guard are copied five times. Changing the nav meant editing five files
— twice, in one afternoon.

This is the =vendor/= directory pattern without the directory: no shared
package, so no version, so no way for one app to lag. Every app is pinned to
=HEAD= of a library that does not exist.

* Why this matters to the ADR

=docs/adr/0001-automatic-promotion.org= measures 10–20 validation runs per
shipped change and attributes it to *a shared trunk*. That is the symptom. This
is the *mechanism*:

#+begin_quote
=apps/**= is one deployable not because of the directory layout, but because
the apps share artifacts. Splitting the repository without splitting the shared
artifact would move the files and keep the coupling.
#+end_quote

So Option A2 — /split the deployable surface out of the monorepo/ — is
*necessary but not sufficient*. Five repos each reading a generated
=routes.json= from a sixth would deploy together exactly as they do now. The
real work is turning the shared thing into a *versioned artifact with a
contract*, which is what makes independent adoption possible: a consumer pins
a version and upgrades when it chooses.

That is also the shape =wal.sh/research/2026-shipping-the-model= describes — a
model *exported as an artifact* so independent implementations agree against a
shared oracle without being ported. The coupling it removes is the one here:
adapters agree by consuming a published artifact, not by reading the producer's
live file.

* Blast radius is not the same as path, and only path is gating

A shared UI package is *effectively a breaking change*: one edit can break five
consumers at once. ITIL defines a standard change as low-risk, pre-approved,
repeatable, with a known outcome — and a change that can break five consumers
simultaneously fails every clause.

*Two of this repo's own mechanisms disagree about exactly that change:*

| mechanism                        | verdict on a shared-surface change | does it gate? |
|----------------------------------+------------------------------------+---------------|
| =idp.py change risk=             | =risk=55=, *type=normal*           | *no* — not wired into the pipeline |
| the labeller (=.github/labeler.yml=) | *=change:standard=*            | *yes* — this is what gates |

The risk scorer already counts blast radius (=multi_app= +15, =per_app= ×n).
The labeller matches *paths* — =router/=, =gates/=, =change/=, =targets/= — and
a package at =apps/shared/= or =packages/oneui/= matches none of them.

#+begin_quote
The mechanism that sees blast radius does not decide, and the mechanism that
decides is blind to it.
#+end_quote

** There is already a live instance

PR #5 carries *five* =app:*= labels and is labelled *=change:standard=*:
pre-authorized, gates as the change authority, no human approval. Its manifest
covers the entire estate. That is not a hypothetical about OneUI; it is the
rule mis-classifying a real change today.

** The rule that follows

*Blast radius, not path, should determine the change type.* Concretely, and
using data the labeller already computes:

: count(app:*) > 1  ->  change:normal

The labeller derives =app:*= from the diff, so the manifest size is already in
hand at the moment of classification. A change touching one app stays standard;
a change whose manifest covers several is a coordinated change and should meet
a change authority.

Note this would also catch =labeler:skip= manifests — deliberately, since a
hand-built manifest spanning five apps is the clearest case of a change whose
blast radius a person should have to acknowledge.

* Status — a concern, deliberately not fixed

Not scheduled. Recorded because:

1. It names the mechanism behind a number the ADR already measures, and
2. it is the thing that would make a repository split *disappointing* — the
   most likely way to do the expensive work and not get the benefit.

*Trigger to revisit:* the first serious move toward A2. At that point the
question to ask is not "which repo does this file go in" but *"what is the
versioned contract between them, and can a consumer lag a version?"* If the
answer is no, the split will not buy what it appears to.
