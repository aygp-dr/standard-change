#+TITLE: Interfaces — what the pipeline needs from an IDP, a calendar, and a forge
#+PROPERTY: header-args :mkdirp t

* Why this file

Everything here runs on shell scripts, a git ref and GitHub labels. That is
deliberate for a simulation, and it hides which parts are *essential* and which
are *this implementation*. If any of it were replaced by a real IDP (Backstage,
Cortex, an internal portal) or a real change calendar (ServiceNow, Jira Service
Management, a Google Calendar), what would it actually have to provide?

This file states the contracts. Each one names the *questions* a component must
answer, the operations it must support, and — most importantly — the properties
the answers must have, because those are what the guards depend on and they are
not obvious from the operation names.

*Nothing here is built beyond the shell implementations named at the end of each
section.* This is an interface specification, not a plan.

* The properties every interface must have

These are cross-cutting and each one was a defect here first. An implementation
that satisfies the operations and violates these is worse than no
implementation, because the guards will trust it.

** UNREACHABLE IS NOT FALSIFIED

Every read must distinguish three answers, not two:

| answer | meaning | what the caller does |
|--------+----------------------------------+----------------------|
| yes    | the fact holds                   | proceed              |
| no     | the fact does not hold           | refuse               |
| *unknown* | I could not determine it      | *refuse*, differently |

An API that returns =404= for "no window" and =404= for "the calendar is down"
cannot be used here. A timeout must not deserialise to =false=. This has fired
six times in this repo — in check-run reads, in a scheduler path error, in a
health probe, and once inside a guard.

** A FACT NAMES THE BUILD IT IS ABOUT

Every observation, approval and deployment record carries the commit SHA it was
measured against. "Staging passed" is not a fact; "staging passed at =a013270="
is. An interface that records verdicts without a build identifier cannot
support guard 4b, and the pipeline will authorise a change on evidence about a
different artifact.

** THE ORACLE IS INDEPENDENT OF THE CALLER

A read must report what the system observed, not what the caller asserted.
=marker.sh= took =--observed-by= and =--samples= from its caller and rendered
them as an observation; a health check that accepts "I saw 5/5 healthy" as
input is a logging API, not an oracle. Where an interface takes a verdict as
*input*, the record must say who supplied it.

** READS ARE RE-READABLE AT THE MOMENT OF RELIANCE

Anything checked at booking is stale when the window opens. The interface must
support asking again cheaply — which means no "consume the answer" semantics,
no one-shot tokens, and idempotent reads.

** CLEARING IS NOT ASSERTING

Adding a claim and withdrawing one are different acts with different
authorities. A person asks for a change; automation may *answer* the ask but
may not *invent* one. Any permission model needs both verbs, separately.

* 1. The change calendar

** The questions

1. Is there an open window for change =X= on environment =E= covering *now*?
2. What is booked on =E=, and when?
3. Is a freeze in force over an interval?
4. What happened to window =W=?

** Operations

#+begin_src text :eval no
  block   <change> <groups> <minutes> [--at <instant>]  -> window-id | CLASH | PAST
  current <change> <env>                                -> window-id | NONE
  check   <window-id>                                   -> OK | FREEZE <reason>
  close   <window-id> <code>                            -> ()
  list    [--open]                                      -> [window]
  freeze  <start> <end> <reason>                        -> ()
#+end_src

** Properties beyond the operations

- *Booking is compare-and-swap.* Two agents booking the same slot must not both
  succeed. A calendar is last-write-wins by default, and the thing being
  double-booked is the path to production. This is the single strongest reason
  the calendar here is a git ref rather than a real calendar: CAS first,
  human-readable second.
- *=current= must compare the END to now.* Returning a window whose time has
  passed is the defect that authorised a change nine minutes after its window
  shut.
- *A designated slot does not win a clash.* Naming an hour is not an argument
  about who holds the berth.
- *Closure codes are a closed set and mean different things:*
  =passed=, =failed= (attempted, did not complete), =cancelled= (decided
  against), =expired= (lapsed unattempted), =held=. Collapsing =expired= into
  =failed= loses the only signal that says the slots are too short.
- *Windows must be reapable.* Something has to close a window nobody drove, or
  a stale reservation keeps answering "yes, you have a window" and the queue
  stacks behind a booking nobody is using.

/Here: =change/schedule.sh= (CAS on =refs/idp/schedule=), =change/reap.sh=./

* 2. The change record (the "RFC")

** The questions

1. What is this change's classification, and who set it?
2. Where is it in its lifecycle?
3. What evidence authorises it, and at which build?
4. What happened, in a form that survives the labels being cleared?

** Operations

#+begin_src text :eval no
  classify <change> <standard|normal|emergency> <actor>   -> ()
  state    <change>                                       -> requested|scheduled|complete|failed|backed-out
  evidence <change> <instrument> <verdict> <sha> <actor>  -> record-id
  latest   <change> <instrument>                          -> record | NONE
  close    <change> <code> <narrative>                    -> ()
#+end_src

** Properties beyond the operations

- *Classification and lifecycle are different namespaces.* "What kind of change
  is this" and "how far has it got" answer different questions and must not
  share a field. Exactly one classification; at most one active lifecycle state.
- *Evidence is append-only and names its instrument.* "Someone said it was
  fine" is not evidence; "=gates/smoke.sh= observed =pass= on =a013270=" is.
  The instrument matters because UAT's instrument is a person and everything
  else's is a script, and a reader must be able to tell.
- *The record outlives the working state.* Labels are cleared at settlement;
  the narrative must not be. Write the record *before* clearing anything.
- *Ownership is declared and enforced.* Every field has exactly one writer.
  Two writers is how the same value flipped five times in twenty minutes.

/Here: GitHub labels + =change/label-owners.tsv= + =change/evidence.sh=,
audited by =gates/label-audit.py=./

* 3. The environment registry

** The questions

1. What environments exist, and what is each one *for*?
2. What is each one running *right now*?
3. Which addresses are reserved even though nothing answers there?
4. Can this environment promote?

** Operations

#+begin_src text :eval no
  declare  <name> <tier> <address> <activated> <promotes>  -> ()
  list                                                     -> [declaration]
  observe  <name>                                          -> {up, build, unreachable}
  claim    <name> <holder>                                 -> OK | HELD-BY <other>
  release  <name> <holder>                                 -> ()
#+end_src

** Properties beyond the operations

- *Declared and running are separate registries.* What is NAMED is a decision;
  what is RUNNING is an observation. One is reviewed, the other is measured.
  Merging them means a typo can look like an outage and an outage can look like
  a config change.
- *=observe= must probe, not read a manifest.* The deployer writes the manifest,
  so a guard reading it is asking the change whether the change worked. Guard 5
  passed on a SHA that did not exist for exactly this reason.
- *=observe= distinguishes refused from timed out.* Nothing listening and
  accepted-but-never-answered are different incidents; the second is the
  dangerous one, and it is the one that reads as "down" if you collapse them.
- *The berth is a lock on the PATH, not on a host.* =claim= is a mutex over
  "may promote", which is why replicating staging would not change the
  invariant.

/Here: =environments.tsv= (declared) + =ports.tsv= (running) +
=targets/node/= + the =deploy:staging= label as the berth./

* 4. The gate runner

** The questions

1. Did the gates pass *on this exact build*?
2. Did they *run*?
3. Can this suite be shown to fail?

** Operations

#+begin_src text :eval no
  run    <suite> <sha>          -> {verdict, ran, detail}
  report <suite> <sha> <result> -> ()
  status <sha>                  -> [{suite, verdict, ran, measured-by}]
#+end_src

** Properties beyond the operations

- *=ran= is a separate field from =verdict=.* A job that never started and a
  job that failed are not the same fact, and a forge that reports both as
  =failure= is unusable without a second call. Cost here: half an hour chasing
  a divergence that did not exist.
- *The self-test gates the suite.* A suite that cannot be shown to reject its
  own negative fixture produces *no verdict* that run — not a pass. This is the
  repo's central rule and it must be part of the interface, not a convention:
  =run= returns =unknown= when the self-test did not pass.
- *A result names where it was measured.* A host run and a CI run are both
  admissible and a reader must always be able to tell them apart. Prefixing is
  enough; hiding it is not.

/Here: =gmake gate=, =gates/report.sh= (posts =local/= commit statuses),
=gates/observation-test.sh --selftest=./

* 5. What a CLI needs regardless of backend

The shell scripts here are the CLI. If they were rewritten against real
services, these are the utilities that would have to exist first — every one of
them is currently duplicated inline in several scripts, and every duplication
has diverged at least once.

| utility | why it is not optional |
|---------+------------------------|
| =tri(cmd)= — run, return yes/no/*unknown* | The single most repeated bug here. Without it, every call site re-invents the collapse of "could not check" into "no". |
| =at(sha)= — bind a verdict to a build | Guard 4b is unimplementable without it, and every call site that forgets it authorises stale evidence. |
| =indent(cmd)= — format output, *return the command's code* | =cmd \vert{} sed= makes =$?= sed's. This shipped an UNHEALTHY estate as =passed=. |
| =cas(ref, expected, new)= | Any shared state two agents can write. |
| =owner(label, verb)= — may this actor add/remove? | Needs both verbs. Clearing is not asserting. |
| =probe(url)= — {up, build, refused, timeout} | Four outcomes, not two. |
| =when(instant)= — render relative to now | A window's *remaining* time only means something once it has started. |

* 6. What a real IDP would have to give up

Worth stating because the pull is always the other way:

- *No auto-reslotting.* A named hour is usually a person saying they will be
  present. Moving the change moves it away from them.
- *No priority queue.* Nothing here is urgent except an emergency, and an
  emergency is exempt from the freeze and the queue rules — not from having a
  window, because the window is what tells everyone else the path is occupied.
- *No "deploy anyway" button.* Every bypass in this repo was removed rather than
  gated, because a gated bypass is used.
- *No verdict without an instrument.* A portal that lets a person tick "staging
  looks fine" is recording an intention. UAT is the one place a human IS the
  instrument, and even there the record says so.

* 7. The data model, speculatively

Written as entities and keys rather than tables, because the storage engine is
the least interesting decision here. What matters is which facts are *separate
rows* — nearly every defect in this repo was two facts sharing one field, or one
fact living in two places.

** CHANGE — the record

: change_id, forge_ref, classification, classified_by, lifecycle, opened_at, closed_at, closure_code, narrative

- =classification= and =lifecycle= are *separate columns*. "What kind of change"
  and "how far has it got" answer different questions. Exactly one
  classification, at most one active lifecycle state.
- =classified_by= exists because the labeller derives a class from the diff and
  a person declares an emergency, and nothing reconciles them. A change carrying
  both is a change whose class is undefined while every rule branches on it.
- =closure_code= is a closed enum, and =expired= is NOT =failed=. Collapsing
  them loses the only signal that says the slots are too short.
- =narrative= is written *before* any working state is cleared.

** WINDOW — the reservation

: window_id, change_id, environment, start, end, groups, sha, booked_at, result, result_at

- =(environment, [start,end))= must be non-overlapping among rows where
  =result IS NULL=. This is the only true uniqueness constraint in the model
  and it is the one the whole thing rests on. *Enforce it in the store*, not in
  the caller — the caller is two agents racing.
- =result IS NULL= means *unresolved*, not *in force*. A window whose end has
  passed and whose result is null is a lapsed reservation and still occupies
  the environment until something reaps it.
- =sha= is on the window, so a booking names the build it was made for. A head
  that moves after booking invalidates the reservation, and you can only see
  that if the reservation recorded what it was for.
- A change may hold *at most one* unresolved window. Not enforced by the
  non-overlap rule — two non-overlapping windows for one change is a different
  mistake, and it happened twice today before anything could ask the question.

** OBSERVATION — the evidence

: observation_id, change_id, instrument, verdict, sha, observed_at, observed_by, environment, target

- Append-only. A withdrawal is a *new row*, never an update, because an audit
  needs to see that a verdict was taken and then retracted.
- =(change_id, instrument, sha)= is what a guard queries. Not
  =(change_id, instrument)= — that is the stale-evidence bug.
- =instrument= matters because UAT's instrument is a person and everything
  else's is a script. =observed_by= is the actor; both are needed, and a portal
  that records only the second cannot tell a measurement from an assertion.

** ENVIRONMENT — declared, and RUN — observed

: environment: name, tier, address, activated, promotes
: run:         environment, sha, started_at, observed_at, state

Two entities on purpose. The first is a *decision* and is reviewed; the second
is a *measurement* and is probed. Merging them lets a typo look like an outage.
=run= is a cache with a timestamp, never an authority — the authority is the
probe, and a =run= row older than a few seconds answers "what did we last see",
not "what is serving".

** ESTATE — the world

: estate_flag: flag, declared_by, declared_at, cleared_by, cleared_at, reason

Not attached to a change, which is the entire point. A flag on a change is a
flag whose carrier is exempt from it. =cleared_by= is a separate column from
=declared_by= because asserting and withdrawing are different acts with
different authorities.

** What the model deliberately does NOT have

- *No priority column.* Adding one creates the question "who gets production
  first", which nothing here needs and every scheduler answers badly.
- *No =deployed_by= on CHANGE.* A change is not deployed; a *build* is deployed
  to an *environment*. Putting it on the change makes a redeploy indistinguishable
  from the first deploy.
- *No boolean =healthy=.* Three-valued or nothing: healthy, unhealthy, could not
  reach. A boolean forces the collapse this repo keeps finding.
- *No cascade delete.* An observation outlives the change it is about; the
  record is the point.

** Who owns scheduling

A person, explicitly. There is no auto-scheduler and the model has no field to
support one. Booking, rescheduling and cancelling are acts by a named actor;
=reap.sh= is the one automation that touches a window, it produces exactly one
outcome (=expired=), and it does not rebook.

* 8. Responsibilities, with no eventing system

There is no event bus. Nothing is published, nothing subscribes, and there are
no retries or dead letters. Every reaction in this pipeline is one of three
things, and *which one it is* is the contract:

| kind | what it means | what happens if it does not run |
|------+---------------+---------------------------------|
| =forge-triggered= | GitHub fires a workflow | the reaction silently does not happen |
| =polled= | somebody runs a command | it does not happen until they do |
| =unowned= | nothing watches for it | it never happens |

*=unowned= is a legitimate entry.* Writing "nobody does this" is the point of
the table — an unowned transition that everyone assumes is handled is how a
guard ends up trusting state nothing maintains.

** The contract for each event

Each row names the OBSERVER (what notices), the ACTOR (what changes state), and
— the column that matters — WHAT IS TRUE IF NOBODY ACTS.

*** A head moves (author pushes)

- Observer: =.github/workflows/labeller.yml= on =synchronize=. *forge-triggered*
- Actor: same; withdraws =staging:*= observations.
- If it does not run: *the change keeps observations measured on a different
  build.* Guard 4 is the backstop and holds, because it re-derives from the
  evidence record's SHA rather than from label presence — the withdrawal is
  hygiene, not the guard. This is why issue #16 moved authorization off labels.

*** A window's end passes

- Observer: nothing. *unowned until somebody runs =change/reap.sh=* — polled.
- Actor: =reap.sh=; closes =expired=, clears =change:scheduled=, releases the
  berth if the lapsed window still held it.
- If nobody runs it: the window stays unresolved, =schedule.sh current= keeps
  answering "yes you have a window" past the end, =block= queues everything
  behind a reservation nobody is using, and the PR claims =change:scheduled=
  against a slot that is gone. *Four separate wrong answers from one missing
  poll.* Observed today, repeatedly.

*** =main= moves under an in-flight change

- Observer: =.github/workflows/main-moved.yml=. *forge-triggered*
- Actor: guard 0 refuses at the next claim; =change/divergence.sh= classifies
  whether it matters (=inert= / =pipeline= / =artifact= / =hotfix=).
- If it does not run: guard 0 still refuses at claim time, because it compares
  merge-base at the moment of reliance rather than trusting a label. Correct by
  construction, not by notification.

*** A freeze is declared while a change is mid-flight

- Observer: *nobody.* =unowned.=
- Actor: none. =gates/preflight.sh= checks the estate at *entry*, and
  =change/uat.sh= re-checks the *window* before and after the walk — but
  nothing re-reads the freeze between the staging deploy and the cutover.
- If nobody acts: *a change that entered a legally open estate keeps going into
  a closed one.* This is R4 in =docs/grind-plan.org= and it is honestly
  unfixed. The guard exists and is checked once; the law says a guard whose
  subject can change must be re-checked at reliance, and here it is not.

*** Production converges on a new build

- Observer: =gates/health.sh= when somebody runs it. *polled*
- Actor: =change/settle.sh= — writes the PIR, sets =change:complete=, merges,
  redlines the window, clears the validation labels.
- If nobody runs it: *production serves a change that =main= does not contain
  and no window covers.* The state with no name; see =grind-plan.org=. The next
  change branches from a =main= without it and silently reverts it on promotion.

*** A change fails, or is abandoned

- Observer: a person. *polled*
- Actor: =change/abort.sh= — closure code, record, berth released, annotations
  cleared.
- If nobody runs it: the berth stays claimed by a change nobody is driving, and
  guard 1 blocks everyone with no declared cause. =reap.sh= releases the berth
  as a side effect only when a *window* lapsed; a change that failed inside its
  window and was walked away from holds it indefinitely.

**** What abort.sh knows about the estate, and how

It *asks*. Issue #37's shape-of-the-fix listed five things an abort must do and
the fifth was "state what the estate is now serving"; the first cut of
=abort.sh= did the other four and ended with the line /"It is not merged and not
deployed"/ printed unconditionally, having measured neither.

That is the D13 sentence from the other side. There, =settle.sh= reported a
merge that had not happened while production served the build; an abort that
asserts *not deployed* over a replica currently serving this SHA is the same
claim, on the failure path, and it then clears the labels that were the only
remaining evidence of what is out there.

=change/serving.sh= is the instrument, and it has the three answers this file
requires of every read — the build, *not answering*, and *answered and named no
build*. It exists as a file because the =curl -sI | tr | awk= idiom it replaces
appears eight times in this repository and in all eight the exit status belongs
to =awk=: curl failing yields an empty string and a zero status, so the front
being down and the front naming no build are one value.

What abort does with the answer:

| observed | closure |
|----------+---------|
| serving some other build | proceeds; the record names what is out there |
| *serving THIS change* | *refuses.* Neither =failed= nor =backed-out= is true while a replica serves it — the estate must move first |
| could not be observed | proceeds, and the record says =NOT OBSERVED= with the command to check |

The asymmetry in the last two rows is the rule: it refuses only on a *positive
contrary observation*. "I could not look" is not evidence, and no runner can
reach this estate at all — a change that could not be closed out because the
front was down would hold the berth for nothing, which is the deadlock this
verb exists to end.

**** Still =unowned=, and named rather than fixed

- *A berth held by a change nobody aborts.* Unchanged by the above: =abort.sh=
  is polled, and a change abandoned inside its window still holds
  =deploy:staging= indefinitely. =reap.sh= sweeps the *schedule*, so it cannot
  see a berth whose window is already closed or was never booked.
- *The idle colour.* Nothing clears it, ever. After a failed cutover the idle
  colour holds whatever was there last, which is only "the previous change"
  while every deploy came from a change — see issue #26.
- *Guard 5 failing after a successful cutover.* =switch.sh= refuses a colour
  that is not answering, so the cutover itself fails closed; a cutover that
  succeeds onto a build that then fails to converge is not rolled back by
  anything.
- *=failed → implementing= versus =failed → assessing=.* =docs/idp-service.org=
  and the guile machine disagree, and the disagreement is reachable only on the
  failure path.

*** An observation instrument fails to record

- Observer: guard 4, at the moment of reliance. *polled, and this is correct*
- Actor: guard 4 refuses.
- If nobody acts: nothing ships. *This is the one event whose failure mode is
  safe*, and it is safe because the reader re-derives rather than waiting to be
  told.

** The rule that makes the absence of eventing survivable

Every guard above that is *correct by construction* is correct for the same
reason: **it re-derives its answer at the moment it is relied on, from the
system, rather than caching what it was told.** Guard 0 compares merge-base at
claim. Guard 4 reads the evidence record's SHA. Guard 5 asks the front what it
is serving.

Every guard that is *wrong or unowned* is wrong for the mirror reason: it was
checked once and the subject moved. The freeze case is exactly this.

So the contract for adding any new reaction is not "publish an event". It is:

1. Can the reader *re-derive* the fact at the moment it matters? Then no event
   is needed and none should be added.
2. If not — if the fact is only observable at the instant it happens — then it
   must be *recorded*, with the build it is about, and the reader re-derives
   from the record.
3. If neither, it is =unowned=, and that belongs in this table rather than in
   somebody's head.

** What an event system would have to add to earn its place

Not delivery. *Accountability*: a subscriber that did not run must be
distinguishable from one that ran and decided nothing was needed. An at-least-
once bus with no such distinction turns every one of the =unowned= rows above
into an =unknown= row, which is strictly worse — the pipeline would stop being
able to tell "nobody watches this" from "something watched it and said no".
