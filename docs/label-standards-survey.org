*Research notes.* =spec.org= governs; nothing here amends it. Epistemic markers
are =spec.org='s: [E] observed or read directly, [H] inferred or not checked,
[E, secondary] read only in a restatement because the primary is paywalled.

This file deliberately does not repeat =docs/release-standards.org=, which
already established the six-tier taxonomy used throughout, and already read
CDEvents, OpenTelemetry semconv, SLSA, in-toto, ITIL 4, ISO/IEC 20000-1 and the
GitHub Deployments API for a *different* question — /what is a deployment
record/. This file asks the question that one did not:

#+begin_quote
*Is there a standard, or even a convention, for the LABELS?* Not for the
deployment record — for the vocabulary a change carries while it moves between a
staging environment and a production one. And in particular: does anyone else
separate "please deploy this" from "this is deployed", and does anyone else have
a third value for "I could not tell"?
#+end_quote

** The answers, stated first

#+begin_quote
*1. There is no standard for deployment labels, at any tier, and there is no
plausible candidate.* Labels are a GitHub-specific UI affordance with no schema,
no registry and no conformance notion; nothing at tier 1 or tier 2 mentions
them. Every label vocabulary found in the wild — including this repo's — is
*tier 6, folklore*.

*2. The intent/state split this repo cares most about is independently attested,
under the same two prefixes, and by an unrelated party.* =nyrkio/nyrkio= ships
=deploy:staging= described as "Initiates deployment on staging" and
=deployed:staging= described as "State of successful staging deployment" [E].
That is =deploy:*= for intent and =deployed:*= for state, arrived at
independently. It is convergent design, not a standard, and it is the single
strongest external corroboration in this survey.

*3. The two label vocabularies that are actually widespread are both
environment-blind.* =released= (semantic-release, 2,740,897 issues/PRs) and the
=autorelease: {pending, tagged, published, snapshot, snoozed, triggered}= family
(release-please, 738,000+ combined) are by far the largest machine-owned label
state machines on GitHub — and neither names an environment at all. They model
/the package registry/, where there is only one destination. *The moment there
are two environments, the convention stops.*

*4. Three-valuedness is the sharpest discriminator, it splits the field cleanly,
and one tier-2 specification draws exactly this repo's line.* OpenTelemetry's
=cicd.pipeline.result= defines =failure= as "usually detected by non-zero exit
codes of the tools executed in the pipeline run" and =error= as "an error in the
CI/CD system, eg. due to the worker being killed" [E, verbatim]. *That is
=docs/exit-codes.org='s 1-versus-4, with the same criterion, written by a
standards body* — plus =timeout=, =cancellation= and =skip=, and the repo has no
code for =skip=, which is the 19-skipped-check-runs incident exactly. The
orchestrators agree: Kubernetes =ConditionUnknown=, Argo CD =HealthStatusUnknown=
and =SyncStatusCodeUnknown=, and above all Argo Rollouts
=AnalysisPhaseInconclusive=, a terminal phase beside =Failed= and =Error= [E].
The forge-side vocabularies do not: GitHub's REST deployment states have no
indeterminate value (only the read-only, GraphQL-only =ABANDONED=), CDEvents'
deployment events have no outcome field at all, and *no label vocabulary found
anywhere has a third value.*

*5. The observation labels that name a build are NOT unusual — the prediction is
refuted.* =openstax/rex-web= carries =in-staging=, =in-production= and 34
=in-release-<N>= labels naming specific builds [E]. That is the same shape as
=deployed:staging-<group>-<n>=, in a real repo, at scale.

*6. The estate-global =freeze= IS unusual — the prediction is confirmed, and
more sharply than expected.* No label meaning "the estate is stopped for
everyone" was found in any repository surveyed. The bare =freeze= label
(1,376 issues) is overwhelmingly *UI-freeze bug reports* [E, sampled]. The only
=code-freeze= labels found carry the *opposite* semantics to this repo's:
=camunda/camunda-platform-helm= defines =code-freeze= as "Issue eligible for
work during the code freeze" [E] — a per-change *exemption*, which is exactly
the collapse =spec.org= §Nomenclature warns against ("freeze /is/ a property of
the WORLD… /is NOT/ a property of a change").
#+end_quote

** Method, and what the numbers do and do not mean

All counts were taken on 2026-09-14 against =GET /search/issues= with
=q=label:"<exact string>"=, authenticated as =aygp-dr=, read-only. No write of
any kind was made to any repository.

*Three caveats, and the third is fatal to half the table.*

1. *The unit is an issue or pull request, not a repository.* A single active
   repo produces thousands. Where it mattered, the top repositories per label
   were pulled separately and are reported beside the count.
2. *Label search is exact on the name, case-insensitively.* =deploy:staging= and
   =deploy-staging= are counted separately, correctly.
3. *Bare English words are uninterpretable and must not be read as evidence.*
   =production= (42,062), =staging= (15,450), =live= (6,645), =blocked=
   (99,870), =release= (274,336), =scheduled= (6,661) and =freeze= (1,376) are
   dominated by labels meaning something else entirely — a component area, a
   triage state, or a bug about the UI locking up. Sampling =freeze= returned
   twenty issues of which none concerned a change freeze [E]. *Only prefixed or
   compound strings carry a readable signal*, and the analysis below uses only
   those.

Primary sources were read from the projects' own source trees via the GitHub
contents API wherever an enum was at stake, rather than from documentation —
=argoproj/argo-rollouts=, =kubernetes/api=, =argoproj/gitops-engine=,
=argoproj/argo-cd=, =fluxcd/pkg=, =spinnaker/orca=, =cdevents/spec=,
=googleapis/release-please=. Those are marked [E] and the file path is named.
GitHub's own API semantics were read from =docs.github.com= and from the
published GraphQL schema at =docs.github.com/public/fpt/schema.docs.graphql=.

* Part 1 — GitHub's own primitives, and the state machine it actually has

=docs/release-standards.org= §GitHub in particular already established the
*epistemic* point — a Deployment is self-reported, "GitHub is never actually
accessing your servers", and the =state= mirrors the deploy script's exit code
rather than the target's condition. Not repeated. What follows is the *shape of
the state machine*, which that note did not enumerate.

** The REST enum is seven values and the GraphQL enum is eleven

The writable REST =state= on a deployment status, verbatim from
=docs.github.com/en/rest/deployments/statuses= [E]:

#+begin_quote
"The state of the status. When you set a transient deployment to =inactive=, the
deployment will be shown as destroyed in GitHub. Can be one of: =error=,
=failure=, =inactive=, =in_progress=, =queued=, =pending=, =success="
#+end_quote

GraphQL exposes *two* enums where REST has one, and the difference is the whole
finding [E, read from the published schema]:

| enum | values | writable? |
|------+--------+-----------|
| =DeploymentStatusState= | =ERROR=, =FAILURE=, =INACTIVE=, =IN_PROGRESS=, =PENDING=, =QUEUED=, =SUCCESS=, =WAITING= | yes, except =WAITING= |
| =DeploymentState= | the above *plus* =ACTIVE=, =ABANDONED=, =DESTROYED= | *no* — derived |

The three GraphQL-only values are the interesting ones, with the schema's own
descriptions:

- =ACTIVE= — "The deployment is currently active."
- =DESTROYED= — "An inactive transient deployment."
- =ABANDONED= — *"The pending deployment was not updated after 30 minutes."*

*=ABANDONED= is the only indeterminate value in GitHub's entire deployment
model, it is read-only, and REST cannot see it.* [E] It is not a failure and not
a success; it is a timeout. Nothing else in the model distinguishes "we do not
know" from "it did not work".

** =inactive= is supersession, not failure — and it is silent

The docs never describe =inactive= as a failure. Three doc statements settle it
[E]:

- "A deployment can accumulate multiple statuses over time as it progresses, for
  example from =pending= to =in_progress= to =success=. *GitHub tracks the most
  recent status for each deployment and uses it to display the deployment's
  current state.*"
- On deleting a deployment: "Mark the active deployment as inactive by adding
  *any non-successful deployment status*" — so =inactive= is one of several ways
  to stop being active, alongside =failure= and =error=.
- "This ensures that repositories with multiple deployments will always have an
  active deployment."

So =inactive= and =failure= differ in *cause*, not in effect: both end
activeness. =inactive= says "superseded"; =failure= says "it broke". A consumer
reading only the current state cannot tell a retired-but-good build from a
broken one without walking the status chain.

Two operational traps worth recording, both [E] from the doc text:

1. *Supersession emits no webhook.* "A webhook event is not fired for deployment
   statuses with an =inactive= state." A listener cannot observe a build ceasing
   to be current; it must poll.
2. *=auto_inactive= excludes production.* Verbatim: "Adds a new inactive status
   to all prior *non-transient, non-production* environment deployments with the
   same repository and environment name as the created status's deployment. An
   inactive status is only added to deployments that had a =success= state."
   And =production_environment= "Default: true when environment is =production=".
   =docs/release-standards.org= flagged this as [H] on a literal reading; the
   doc text is confirmed [E], the *implementation* remains [H]. For a blue/green
   production pair, *nothing retires the old slot for you.*

Also: "GitHub retains records of previous deployment statuses for *90 days*" [E].
Any settlement evidence older than that is gone from both APIs.

** How GitHub says "environment X is serving build Y": it does not, quite

There is no field for it. The Environment object — REST =({id, node_id, name,
url, html_url, created_at, updated_at, protection_rules[],
deployment_branch_policy})= and GraphQL =({databaseId, id, isPinned,
latestCompletedDeployment, name, pinnedPosition, protectionRules})= — has no
current-deployment pointer [E].

The nearest two things, and neither is what it looks like:

| candidate | what it actually means |
|-----------+------------------------|
| =Deployment.state = ACTIVE= (GraphQL) | nobody has posted a superseding or failing status. A claim about GitHub's records, not about the estate |
| =Environment.latestCompletedDeployment= | "The latest completed deployment with status *success, failure, or error*" — the most recent attempt that *finished*, which may well be a failure |

*The reduction "current build = the most recent deployment for that environment
whose latest status is =success= and which has not since been marked
=inactive=" is an inference* [H] assembled from those three doc sentences. No
single doc sentence states it.

** Protection rules gate entry, not outcome

Verbatim [E]: "Deployment protection rules require specific conditions to pass
before a job referencing the environment can proceed." The rule types, exactly:
=wait_timer= (1–43,200 minutes per the Actions docs; "0 and 43,200" per the REST
docs — *the two pages disagree on the lower bound* [E]), =required_reviewers=
(≤6 users or teams, "Only one of the required reviewers needs to approve",
optional =prevent_self_review=), =branch_policy= (=branch= | =tag= name
patterns, "Wildcard characters will not match =/="), and GitHub-App *custom
deployment protection rules* (public preview; max 6 enabled per environment).

While waiting, the *job* status is =Waiting=, the GraphQL deployment state is
=WAITING=, and there is *no REST deployment-status value for it* [E]. "If a job
is not approved within 30 days, it will automatically fail."

The approval verdict is two-valued: =DeploymentReviewState= is exactly
={APPROVED, REJECTED}=, and the =pending_deployments= review API takes =state=
of =approved= or =rejected= [E]. There is no "cannot determine".

*The one place GitHub allows a verdict-free report*, and it is buried in the
custom-protection-rule docs [E]: "to add a status report without taking any
other action to GitHub, send a POST … In the request body, *omit the =state=*…
You can post a status report on the same deployment up to 10 times." That is the
only slot in the whole platform for "I have looked and I am not answering yet" —
and it exists only for GitHub Apps on custom protection rules, which are in
public preview and unavailable to this repo (=spec.org= §Open items: rulesets
already 403 on this plan).

** Freeze: GitHub has no such primitive at any scope

Repository, organisation, enterprise — none [H, an argued absence: no
documentation page names such a feature, which proves no doc names it, not that
none exists]. GitHub's own docs point outward for exactly this use case, naming
"Datadog, Honeycomb, and ServiceNow" for "automated approvals" and an ITSM case
of "service readiness by validating quality, security, and compliance
processes".

The compositional substitutes are all per-environment, and each has a defect
against =spec.org='s definition of a freeze as a property of the world:

| substitute | why it is not a freeze |
|------------+------------------------|
| custom protection rule app that rejects everything | per-environment, ≤6 rules, public preview, and unavailable below Enterprise on private repos |
| required reviewers who decline | per-environment; indistinguishable from a review that has not happened |
| deployment branch policy narrowed to nothing | per-environment; also blocks the emergency that should pass |
| disabling Actions org-wide | stops CI too, so the gates cannot run either — it freezes the instruments, not the estate |

*None of them is a single writable fact that every guard reads.* That is exactly
what =freeze= is here, and the platform has no place to put it.

** Webhook surface, for completeness

Four events, with their action types [E]: =deployment= (=created=),
=deployment_status= (=created=), =deployment_review= (=approved=, =rejected=,
=requested= — GitHub Apps only), =deployment_protection_rule= (=requested= —
GitHub Apps only). The last carries =deployment_callback_url= and a =sha= that
is "Always populated from the check suite, regardless of whether a deployment is
created".

** Verdict on GitHub

*Tier 3, vendor contract*, per =docs/release-standards.org='s taxonomy: no
conformance test, the platform is the test, and it can change without notice.
Its deployment state machine is real, enumerable, and *two-valued at every
decision point that matters* — approve/reject, success/failure, active/inactive
— with a single read-only timeout value (=ABANDONED=) as the sole gesture at
indeterminacy. It has no freeze, no intent/state distinction beyond =task= and
=payload= as free-form strings, and no per-SHA "this is what staging is serving".

release-please's README states the model outright [E]:

#+begin_quote
"You can tell where the Release PR is in its lifecycle by the status label on
the [pull request]…

- =autorelease: pending= is the initial state of the Release PR before it is
  merged
- =autorelease: tagged= means that the Release PR has been merged and the
  release has been tagged in GitHub
- =autorelease: snapshot= is a special state for snapshot version bumps
- =autorelease: published= means that a GitHub release has been published based
  on the Release PR (/release-please does not automatically add this tag, but we
  recommend it as a convention for publication tooling/)."
#+end_quote

Three things to take from that, and the third is the one this repo will care
about.

1. *It is a lifecycle state machine expressed as labels, machine-owned, with a
   single writer per state.* It is the same construction as =change:*=.
2. *It names no environment.* There is one destination — the registry — so the
   environment axis never arises. This is why the convention scales: it is
   solving a one-environment problem.
3. *It hits the ownership question this repo's =change/label-owners.tsv= exists
   for, and answers it explicitly.* =autorelease: published= is deliberately
   *not written by release-please*; the README hands the writer to "publication
   tooling" as "a convention". 32,785 issues carry it, so the convention is
   actually adopted. That is an independent arrival at rule 1 of
   =docs/label-ownership.org= — the instrument writes its own verdict, and a
   tool that did not take the measurement declines to record it.

=release-please:force-run= is the matching *intent* label: a person adds it, the
bot consumes it. Same shape as this repo's =release=.

** The three repositories worth reading in full

*** =nyrkio/nyrkio= — the intent/state split, independently invented [E]

Three labels, with the maintainer's own descriptions read from the repository's
label API:

| label | description, verbatim |
|-------+-----------------------|
| =deploy:staging= | "Initiates deployment on staging" |
| =deployed:staging= | "State of successful staging deployment" |
| =deploy-failed:staging= | "State of failed staging deployment." |

This is the closest external match to this repo's central distinction, and it
arrived at *the same two prefixes*: the imperative =deploy:= for the trigger and
the past participle =deployed:= for the observation. It also has the
verdict-pair shape — =deployed:staging= against =deploy-failed:staging= is
=staging:e2e= against =staging:e2e-failed=.

*What it does not have*: a production tier (staging only), a third value, a
declared writer, an exclusion rule, or a build identity. It is the right
distinction with none of the machinery.

*** =openstax/rex-web= — observation labels naming a build [E]

76 labels, of which 34 are =in-release-<N>=, plus =in-staging=, =in-production=,
=dev-approved= (259 issues), =scan-passed= (31), =HOLD= and =ICE=.

This *refutes the survey's own prediction*. The task predicted that "observation
labels that name a build" would be unusual. They are not: =in-release-1712= is a
label whose entire content is *which build this change is in*, and openstax has
34 of them live and many more retired. The two-tier =in-staging= / =in-production=
pair is the environment-state distinction, and =dev-approved= / =scan-passed=
are gate observations recorded as labels.

The differences from this repo are real but narrower than predicted: openstax
names a *release number*, not a head SHA; the labels are not declared to have a
single writer; and there is no failure counterpart to =scan-passed=, so a change
with no =scan-passed= is indistinguishable from one the scan could not run on.
*Which is the three-valued defect, in the wild.*

*** =mysociety/alaveteli= — the two-environment pair, at its simplest [E]

=awaiting-deploy=, =on-staging=, =next-release=, =has-blockers=. Four labels
covering intent, staging state, release targeting, and blockage. No production
label; production is implied by the absence of the others. Fourteen years of a
real civic-tech deployment, and this is the whole vocabulary.

*** Honourable mentions

- =climatepolicyradar/navigator-backend= [E]: =deploy:dev= — "Create an
  ephemeral environment for the PR"; =deploy:staging= — "Deploy the latest
  commit automatically if it has this label". *Pure intent, and the description
  says so.* Note "if it has this label" — a trigger that stays on re-fires,
  which is the defect =change/label-owners.tsv= records against =release=.
- =fedora-infra/anitya= [E]: =deployed:staging=, =deployed:prod=. Pure state,
  two tiers, no intent labels at all.
- =app-vitals/shipwright= [E]: =status:pending=, =status:ready=,
  =status:blocked=, =status:deploying=, =status:deployed=, plus =hold:manual=
  ("Reserved — do not auto-pick; worked manually in a specific session"). A
  single =status:*= namespace carrying lifecycle *and* action *and* blockage —
  the overloading =spec.org= §Nomenclature says to avoid.
- =elastic/kibana= [E]: twelve =ci:*deploy*= labels
  (=ci:cloud-deploy=, =ci:project-deploy-security=, =ci:cloud-redeploy=,
  =ci:cloud-persist-deployment=…). *All intent, none state.* Plus
  =Environment:ECH= / =Environment:MKI= as loci.
- =grafana/grafana= [E]: =deploy-frontend-preview=, =deploy-storybook=. Intent.
- =mozilla/addons-server= [E]: =env:dev=, =env:stage=, =env:prod=,
  =type:prod_bug=, =priority:blocks_release=. These are *loci* — where the bug
  was seen — not deployment states. Easy to mistake for the latter.

Scanning the full label sets of nineteen prominent repositories for any
deployment vocabulary [E]:

|------+-------------------------+---------------------|
| kubernetes/kubernetes | *none* | =release-blocker=, =sig/release=, =do-not-merge/*= |
| rust-lang/rust | *none* | =T-release=, =I-release-nominated=, =S-waiting-on-t-release= |
| cockroachdb/cockroach | *none* | ~90 =branch-release-<version>= labels |
| spinnaker/spinnaker | *none* | =target-release/<version>=, =release/blocker= |
| fluxcd/flux2 | *none* | =backport:release/v2.9.x= |
| microsoft/vscode | *none* | =insiders-released=, =unreleased=, =release-cherry-pick= |
| backstage/backstage | *none* | =workflow:before-release=, =workflow:after-release= |
| hashicorp/terraform | *none* | — |

| argoproj/argo-cd | *none* | =production-binary=, =production-image= (artifact kinds) |
| cdevents/spec | *none* | — |

*Every one of these ships software, and none of them labels where a change is
deployed.* The pattern is consistent: large projects label *which release a
change is targeted at or landed in* — a version axis — and let the deployment
axis live entirely outside the issue tracker. The one partial exception is
elastic/kibana, whose =ci:*-deploy-*= labels are deployment *triggers* and carry
no state.

*The inference* [H]: deployment-state labels appear where the repository and the
estate are the same team's concern and the estate is small enough to have one
staging and one production. A project with thousands of downstream operators has
no single "production" to label, so the axis is meaningless and nobody invents
a vocabulary for it. *This repo is in the first category, which is why it needed
one.*

** Intent versus state, counted

Of the 34 environment-bearing strings measured, classified by whether the
label's job is to *cause* a deployment or to *record* one:

| kind | strings | combined issues | note |
|------+---------+-----------------+------|
| intent — "please deploy" | 13 | 9,106 | =deploy:*=, =deploy-*=, =auto-deploy=, =needs-deploy=, =staging-ready=, =do-not-deploy=, =awaiting-deploy= |
| state — "is deployed" | 15 | 8,096 | =deployed:*=, =in-staging=, =in-production=, =on-staging=, =status:deployed=, =state:deployed=, =deploying=, =*-failed=, =deploy-blocked=, =pending-deployment= |
| ambiguous — both or neither | 6 | 2,423 | =env:*=, =environment:staging=, =production-ready=, =code-freeze=, =deploy-freeze= |

(=awaiting-deploy= is counted as intent; it is arguably a queue state. It is
one repository's label and moving it changes the totals by 2,137 without
changing the conclusion.)

*The distinction is real and people do make it* — the grammar carries it,
imperative for intent and past participle for state, in exactly the way
=deploy:staging= versus =deployed:staging= does. *What nobody does is declare
it.* Not one of the surveyed repositories has a file stating which labels are
intent and which are state, or who may write each. =nyrkio/nyrkio= comes closest
by putting "Initiates" and "State of" in the label descriptions, which is a
declaration of a kind, and it covers three labels.

*Three repositories mix the two in one namespace* — =app-vitals/shipwright='s
=status:*= holds =ready= (intent-ish), =deploying= (action) and =deployed=
(state); =mozilla/addons-server='s =env:*= holds a locus that reads as a state.
That is the failure mode =change/label-owners.tsv='s exclusion-group split was
written to fix, occurring naturally.

** Freeze, verified rather than assumed

The prediction was that the estate-global =freeze= would have no external
equivalent. *Confirmed, and the reason is more interesting than the absence.*

- Bare =freeze= (1,376): sampled twenty issues; all were application-freeze bug
  reports ("tab hidden", "auto crash: ResizeObserver loop", "Freeze idle mods")
  [E]. Zero change freezes.
- =deploy-freeze= (4): four issues, GitHub-wide.
- =code-freeze= (53): the largest user, =camunda/camunda-platform-helm=, defines
  it as *"Issue eligible for work during the code freeze"*, with a companion
  =code-freeze-candidate= = "Issue found during a code freeze that we aren't
  sure yet are eligible to work on during the code fz" [E].

That last one is the finding. Camunda's =code-freeze= is an *exemption carried
by a change*, not a property of the estate — the freeze itself lives somewhere
else (a calendar, a Slack message, a release manager's head) and the label marks
which changes may cross it. *That is precisely the collapse this repo rejected
when it split =emergency= (estate) from =itil:emergency= (exemption)*, and it is
the default thing people do.

Where estate-global freezes *do* exist as a first-class object, they are not
labels and not in the forge. =docs/reference-survey.org= already records the
three: AWS Systems Manager Change Calendar (iCalendar/RFC 5545 documents that
are "Open by default" or "Closed by default"), AWS CodePipeline's
=DeploymentWindow= rule provider, and Google Cloud Deploy's deploy policies with
=rolloutRestriction= =timeWindows=. All tier 3. All external to the change.

Tiers are =docs/release-standards.org= §A taxonomy: 1 formal standard, 2 open

- *OpenTelemetry semconv* has the six-valued result with =error= defined against
  =failure=, and a =deploy= task type to hang it on, and no notion of a
  deployment *state* that persists after the run ends.

Joined, they would be the standard this repo needs. Nobody has joined them, and
=docs/release-standards.org= already recorded the adjacent version of the same
gap: signed provenance stops at the registry, deployment events start at the
environment, and nothing crosses.

** CDEvents — names environments perfectly, and cannot say a deployment failed

Read from =cdevents/spec= at =main= (=version.txt= = =0.6.0-draft=; the released
line is v0.5.1 per =docs/release-standards.org=) [E]. The subjects, verbatim
from =continuous-deployment.md=:

| subject | fields |
|---------+--------|
| =environment= | =id=, =source=, =name= ("Name of the environment"; examples =dev=, =staging=, =production=, =ci-123=), =url= |
| =service= | =id=, =source=, =environment= (a reference to the above, *required*), =artifactId= (a *Purl*, *required*) |

The eight conformance events under continuous deployment, which is the complete
list [E, enumerated from =conformance/=]:

: environment_created  environment_modified  environment_deleted
: service_deployed  service_upgraded  service_rolledback  service_removed  service_published

*There is no failure event and no outcome field on any of them.* =service
deployed= carries ={id, source, environment, artifactId}= and nothing else; a
deployment that did not work simply produces no event. CDEvents' deployment
vocabulary is a *success-only log*, and the question "is this environment
currently serving X" is answered by replaying it, not by reading a state.

*And yet CDEvents is four-valued where it does record outcomes* [E]. From
=core.md= and =testing-events.md=, the =outcome= enum on =pipelineRun finished=,
=taskRun finished=, =testCaseRun finished= and =testSuiteRun finished= is
exactly:

: success | failure | cancel | error

with a companion free-text =reason= ("Canceled by user", "Failed assertion",
"Timed out") and =errors= ("In case of error, canceled, or failed pipeline,
provides details about the failure").

*That enum is the closest thing in any open specification to this repo's exit
code contract.* =docs/exit-codes.org= distinguishes 1 "refused — the check
failed" from 4 "I could not check"; CDEvents distinguishes =failure= from
=error=, and adds =cancel=, which =docs/exit-codes.org= has no code for and
=spec.org= §Nomenclature names as a closure code. *The vocabulary this repo needs
exists, one document away from the deployment events, and is not applied to
them.*

CDEvents also has =continuous-operations.md= with =incident detected=, =incident
reported=, =incident resolved= [E] — adjacent to =emergency=, but about
incidents, not about stopping the estate.

*Tier 2, CDF incubating, pre-1.0.* Free.

** OpenTelemetry semantic conventions — the one specification that draws this repo's own line

=docs/release-standards.org= §OpenTelemetry already took the /resource/
attributes (=service.name=, =service.version=, =service.instance.id=,
=deployment.environment.name= — all Stable, with =staging= and =production=
among the well-known values). Not repeated. The addition here is the =cicd.*=
family, which that note did not cover, and *it is the most important single
finding in Part 3.*

Read from =open-telemetry/semantic-conventions=, =model/cicd/registry.yaml= [E].
Two separate enums, on two separate axes:

| attribute | members | stability |
|-----------+---------+-----------|
| =cicd.pipeline.run.state= | =pending=, =executing=, =finalizing= | release_candidate |
| =cicd.pipeline.result= and =cicd.pipeline.task.run.result= | =success=, =failure=, =error=, =timeout=, =cancellation=, =skip= | release_candidate |

*Six values, and the two that matter are defined against each other, verbatim:*

#+begin_quote
=failure= — "The pipeline run did not finish successfully, eg. due to a compile
error or a failing test. *Such failures are usually detected by non-zero exit
codes of the tools executed in the pipeline run.*"

=error= — "The pipeline run failed due to *an error in the CI/CD system*, eg. due
to the worker being killed."

=timeout= — "A timeout caused the pipeline run to be interrupted."

=cancellation= — "The pipeline run was cancelled, eg. by a user manually
cancelling the pipeline run."

=skip= — "The pipeline run was skipped, eg. due to a precondition not being met."

— =model/cicd/registry.yaml=, all six members at =stability: release_candidate=
#+end_quote

*That is =docs/exit-codes.org=, written by a standards body.* This repo spends a
section defending why exit 4 ("I could not check") must not collapse into exit 1
("the check failed"); OpenTelemetry defines exactly that boundary and puts the
distinguishing criterion in the same place this repo does — *the failure is the
tool's non-zero exit; the error is the apparatus breaking underneath it.* It
further supplies =timeout=, =cancellation= and =skip=, of which the repo has
=cancel= and =expired= as closure codes (§Nomenclature) and *no code at all* for
=skip= — which is precisely the 19-skipped-check-runs incident
(=docs/exit-codes.org=, issue #34), where skipped was read as not-green.

Also relevant: =cicd.pipeline.task.type= has members =build=, =test=, =deploy=,
so a deploy is a task type whose run carries the six-valued result. *This is the
only place in any specification surveyed where a deployment gets a verdict with
an indeterminate value.*

The stability caveat is real and cuts both ways: =release_candidate= is one step
below Stable and above Experimental — the names are close to frozen but not
frozen, so =docs/ci-portability.org='s rule still applies. The *resource*
attributes this repo would use for guard 5 (=service.version=,
=deployment.environment.name=) are Stable [E via =docs/release-standards.org=].

*Tier 2.* Free. *The best adoption candidate in this survey.*

** SLSA and in-toto — build-side, and they say so

=docs/release-standards.org= §Provenance already established that SLSA
"explicitly does not cover deployment" and that in-toto's Statement binds a
predicate to an artifact digest. Nothing here changes that. Two notes:

- SLSA has *levels*, not states. There is no state machine to align to.
- in-toto's Verification Summary Attestation is the nearest thing to a recorded
  verdict about an artifact, and its result field is *two-valued* — an artifact
  either passed the verification or did not. There is no "the verifier could not
  reach the evidence". *The same defect as everywhere else.*

*Tier 2.* Free. Out of scope for the label question.

** SPIFFE, OSCAL

- *SPIFFE/SPIRE*: workload identity. No deployment-state vocabulary. Tier 2,
  free, *irrelevant to this survey* — listed only so the absence is recorded.
- *OSCAL*: models assessment results and control satisfaction, not deployment.
  Its findings vocabulary does admit an indeterminate outcome, which is
  structurally the right shape, but the subject is a control objective and not a
  build in an environment. Adopting it would mean re-describing a gate verdict
  as a control assessment, which is a much larger move than a vocabulary
  borrowing. Tier 1/2 depending on which artifact; free.

** ISO/IEC 20000-1:2018 — tier 1, paywalled, and it names no states

*Paywalled; not read.* Claims below are [E, secondary] from independent
restatements and are consistent across them.

Two corrections to the task's framing, both worth recording:

1. *Change control is clause 8.5.1 in the 2018 edition*, not 8.5.3.
   =docs/reference-survey.org= already cites it correctly as 8.5.1. The 2018
   edition's 8.5 covers service design/build/transition, with 8.5.1 change
   management/control and the release-and-deployment requirements adjacent
   within 8.5 [E, secondary].
2. *It requires records and authority; it does not enumerate states.* The
   requirement shape is "define change types, record changes, determine who
   authorises" — a conformance target for *having* a process, not a vocabulary
   for the process's states. There is nothing here to map a label onto.

*Tier 1. Paywalled. Defines no state machine.* It is the only genuine formal
standard in this survey and it has the least to say about the question.

** ITIL 4 change enablement — tier 4, paywalled, and the only source of three of this repo's labels

*Paywalled (AXELOS/PeopleCert); the practice guides were not read.* Claims are
[E, secondary], consistent with =docs/reference-survey.org='s verbatim quotations
of the 9 January 2020 Change Enablement practice guide, which this file takes as
its secondary source of record.

What ITIL supplies that nothing else does:

| this repo | ITIL 4 |
|-----------+--------|
| =itil:standard= | "A low-risk, pre-authorized change that is well understood and fully documented, and which can be implemented without needing additional authorization" |
| =itil:normal= | a change following "a process that includes collective expert assessment, authorization, and control" |
| =itil:emergency= | the practice "should ensure that changes are implemented effectively, safely, and promptly in emergency situations" |
| the change schedule | the change schedule, a named artifact of the practice |
| the approver | "change authority — A person or group responsible for authorizing a change" |
| =change:failed= / =change:backed-out= | closure codes |

*The classification axis is ITIL's, and the =itil:= prefix is honest about it.*
That is the one place where this repo's vocabulary has a real external parent,
and the parent is tier 4 — a commercially licensed body of practice whose
conformance notion certifies *people*, not systems.

Two things ITIL does *not* supply, which this repo has anyway:

- *A lifecycle state machine with stable names.* Secondary restatements list
  change-record states, but they vary between restatements and between tools
  (ServiceNow's model is not ITIL's). =change:requested= / =scheduled= /
  =complete= is *this repo's*, not ITIL's.
- *A post-implementation review as a named ITIL 4 artifact.* PIR is ITIL v3
  vocabulary; ITIL 4 folds the review into the practice's continual-improvement
  loop and the term is not prominent [H — this rests on secondary sources that
  disagree, and the primary is paywalled]. The repo's use of "PIR" is
  defensible and should be read as v3-inherited rather than as ITIL 4
  conformance.

** Kubernetes, Argo, Flux — the three-valued family

These are the rows that answer the three-valuedness question, and every enum
below was read from the project's own source tree [E].

*** Kubernetes conditions — =Unknown= is normative, with a normative reason

From =kubernetes/api=, =core/v1/types.go= (verbatim comment):

#+begin_quote
"These are valid condition statuses. =ConditionTrue= means a resource is in the
condition. =ConditionFalse= means a resource is not in the condition.
*=ConditionUnknown= means kubernetes can't decide if a resource is in the
condition or not.* In the future, we could add other intermediate conditions,
e.g. ConditionDegraded."
#+end_quote

: ConditionTrue = "True"   ConditionFalse = "False"   ConditionUnknown = "Unknown"

And from =apps/v1/types.go=, the Deployment condition types:
=Available=, =Progressing=, =ReplicaFailure=.

*"Kubernetes can't decide" is =docs/exit-codes.org='s code 4, in a type system,
in the most widely deployed control plane in existence.* It is not an edge case
there; it is the default value of a condition nobody has reported on.

*** Argo Rollouts — =Inconclusive= is a terminal phase

From =argoproj/argo-rollouts=,
=pkg/apis/rollouts/v1alpha1/analysis_types.go= [E]:

: AnalysisPhasePending      = "Pending"
: AnalysisPhaseRunning      = "Running"
: AnalysisPhaseSuccessful   = "Successful"
: AnalysisPhaseFailed       = "Failed"
: AnalysisPhaseError        = "Error"
: AnalysisPhaseInconclusive = "Inconclusive"

and =Completed()= returns true for =Successful=, =Failed=, =Error= *and*
=Inconclusive= — so =Inconclusive= is a *finished* analysis, not a pending one.
There is also a per-metric =InconclusiveLimit= ("the maximum number of times the
measurement is allowed to measure =Inconclusive=, before the entire metric is
considered =Inconclusive="), and the =MetricResult= struct counts
=Successful=, =Failed= and =Inconclusive= separately.

*This is the single best external precedent for the repo's position on exit code
4.* Argo Rollouts is a deployment controller whose verdict vocabulary is
four-valued at the terminal — pass, fail, broke, could-not-tell — with a
configurable tolerance for the fourth. It is exactly the shape
=docs/interfaces.org= §=tri(cmd)= argues for, built and shipped.

*** Argo CD — three independent =Unknown=-bearing axes

From =argoproj/gitops-engine= =pkg/health/health.go= and =argo-cd=
=pkg/apis/application/v1alpha1/types.go= [E]:

| axis | values |
|------+--------|
| health | =Unknown=, =Progressing=, =Healthy=, =Suspended=, =Degraded=, =Missing= |
| sync | =Unknown=, =Synced=, =OutOfSync= |
| hydrate operation | =Unknown=, =Hydrating=, =Failed=, =Hydrated= |

Note =Unknown= is the *first* constant in each enum — the zero value. The system
is built so that the default answer is "I do not know", and a definite answer
requires a successful observation. That is the inverse of every label scheme in
Part 2, where the absence of a label is read as "no" rather than "unobserved".

*** Flux CD — Kubernetes conditions, with a reason vocabulary

From =fluxcd/pkg= =apis/meta/conditions.go= [E]: condition types =Ready=,
=Stalled=, =Reconciling=, =Healthy=; reasons =Succeeded=, =Failed=,
=Progressing=, =Suspended=, =ProgressingWithRetry=, =DependencyNotReady=,
=HealthCheckFailed=, =ReconciliationSucceeded=, =ReconciliationFailed=,
=HealthCheckCanceled=, =PruneFailed=, =ArtifactFailed=, =BuildFailed=, and more.
Status values are inherited from =metav1.Condition= and are therefore the

=DependencyNotReady= is worth noting: it is a *blocked* reason distinct from a
*failed* reason — the same fact this repo carries as =blocked:queue= versus
=staging:e2e-failed=.

** Spinnaker — the only vocabulary with a second dimension

From =spinnaker/orca=,
=orca-api/src/main/java/com/netflix/spinnaker/orca/api/pipeline/models/ExecutionStatus.java=
[E]. Twelve values, and *each carries two booleans*, =complete= and =halt=:

| value | complete | halt | the source's own comment |
|-------+----------+------+--------------------------|
| =NOT_STARTED= | false | false | "The task has yet to start." |
| =RUNNING= | false | false | "still running and the Task may be re-executed in order to continue" |
| =PAUSED= | false | false | "still running and the Task may be resumed" |
| =SUSPENDED= | false | false | "complete but the pipeline should now be stopped pending a trigger of some kind" |

(=depends-on=, =allowed-times=, =manual-judgement=) — already recorded in

** What has no external equivalent at all

Five labels, and they are five different kinds of unusual.

1. *=control-plane=.* "Says WHY the change is handled differently: it alters how
   every future change is verified, so it cannot be verified by the pipeline."
   Nothing in any surveyed vocabulary distinguishes a change to the *judging
   apparatus* from a change to the thing judged. Argo, Flux and Spinnaker all
   deploy their own config through the same machinery that deploys workloads.
   *This is a genuine invention and it is the one most worth writing up
   elsewhere.*
2. *=change:backfill-owed=.* A persistent marker that a change reached main
   without its record and still owes one, which blocks nothing and which
   automation may not clear. ITIL requires retrospective documentation of an
   emergency change [E, secondary]; nothing gives that debt a *name a machine can
   read*.
3. *=freeze= as an estate property.* The concept exists at tier 3 in three
   clouds. As a *label in the forge that every guard reads*, nothing. The one
   thing people do label — =code-freeze= — means the opposite.
4. *=blocked:freeze=.* Follows from 3.
5. *The =production:*= observation stack.* Everyone verifies staging; nobody
   found records an authorising e2e verdict *against production* as a labelled
   observation. Production is verified by telemetry, by Argo CD health, by
   alerting — continuously and outside the change record. Recording it *on the
   change* is unusual, and it is what makes guard 5 possible.

** The two predictions, judged

| prediction | verdict |
|------------+---------|
| Observation labels that name a build are likely unusual | *REFUTED.* =openstax/rex-web= has 34 =in-release-<N>= labels plus =in-staging= and =in-production= [E]. The shape is attested. What is unusual is not the build-naming but the *declared single writer* and the *failure counterpart* |
| The estate-global =freeze= is likely unusual | *CONFIRMED*, and sharpened: the only real =code-freeze= labels found carry the inverted, per-change-exemption semantics that =spec.org= §Nomenclature names as the defect |

A third result nobody predicted: *the intent/state split is attested, string for
string.* =nyrkio/nyrkio='s =deploy:staging= / =deployed:staging= pair, with its
descriptions, is the discovery of this survey.

* Part 5 — is there a standard to adopt, and what would it cost

** The direct answer

*No. There is no standard for deployment labels, and the label layer is
genuinely tier 6 folklore — this repo's included.* But that verdict is too
convenient, because it is true of everyone's labels and therefore says nothing.
The useful version is narrower:

#+begin_quote
*The labels are folklore, and they should stay folklore — but three of the
vocabularies they encode are standardised elsewhere, and this repo is currently
poorer than the standard in exactly one respect: three-valuedness.*
#+end_quote

** What to adopt, and the price

*** 1. Adopt OpenTelemetry's result enum as the names for gate verdicts. Tier 2. Cheap.

=cicd.pipeline.result= is =success | failure | error | timeout | cancellation |
skip=, and OTel defines =failure= as the tool's non-zero exit and =error= as the
CI/CD system breaking underneath it [E, verbatim in §OTel]. *That is
=docs/exit-codes.org='s 1-versus-4, with the same distinguishing criterion, in a
tier-2 specification.* CDEvents' =success | failure | cancel | error= is the
same idea with two fewer values and should be treated as the fallback.

- *Cost*: a naming column in =docs/exit-codes.org= mapping each exit code to its
  semconv member, and the same strings in gate output. *No behavioural change*;
  0, 1 and 4 keep their numbers and their meanings.
- *Gain, immediately*: two values the repo does not currently have a code for.
  =skip= is the 19-skipped-check-runs incident (issue #34) — "skipped" is *not*
  "not green", and there is now a published name for it. =timeout= is what
  =change/reap.sh= produces and what =spec.org= calls the =expired= closure code.
- *Gain, later*: when a deployment record needs a schema —
  =docs/release-standards.org= recommends CDEvents' shape for that — the gate
  verdicts translate without loss, because CDEvents' four values are a subset.
- *Risk*: =release_candidate= stability, so the strings may still move. Record
  the version read (=model/cicd/registry.yaml= at =main=, 2026-09-14) and re-check
  before any claim of conformance. =docs/ci-portability.org='s rule applies.

*** 2. Adopt Argo Rollouts' =Inconclusive= as the name for exit 4. Tier 3. Free.

This costs nothing and buys the argument. =docs/exit-codes.org= spends a section
defending why 4 is not 1; Argo Rollouts *ships* that distinction as
=AnalysisPhaseInconclusive=, as a terminal phase with a configurable tolerance,
in a deployment controller with wide adoption [E]. The next time the rule has to
be defended, it is not a local eccentricity — it is what the most-used
progressive-delivery controller does.

- *Cost*: nothing. A citation.
- *The stronger version, which is not free*: give the =staging:*= and
  =production:*= verdict stacks a *third* label —
  =staging:e2e-inconclusive= beside =staging:e2e= and =staging:e2e-failed= —
  so that "the instrument could not run" is recorded rather than represented by
  absence. Today an absent =staging:e2e= means "not yet run" *or* "ran and could
  not tell", and guard 4 cannot distinguish them. *That is the same defect this
  repo has already found three times* (§Disagreements, =merge-on-healthy.yml=,
  =preflight= and the 19 skipped check runs). Cost: three new labels, three new
  exclusion-group rows, and a change to =gates/e2e.sh --pr=. *This is the one
  recommendation in this file that is a real proposal and not a citation.*

*** 3. Keep the =itil:= prefix, and keep it honest. Tier 4, paywalled.

The classification axis genuinely descends from ITIL 4, and the prefix says so.
Nothing to adopt; something to *not* over-claim. Two corrections for the record:
"post-implementation review" is ITIL v3 vocabulary and its status in ITIL 4 is
[H] from disagreeing secondary sources; and ITIL 4 supplies no stable
change-record state strings, so =change:requested/scheduled/complete= is this
repo's own and should not be described as ITIL conformance.

*** 4. Do not adopt ISO/IEC 20000-1. Tier 1, paywalled.

It is the only formal standard in the survey. It requires that change types,
records and authorities be *defined*; it does not define them. There is nothing
to align a label to, and the conformance test is an audit of an organisation,
not of a repository. *Cost of adoption: a paid copy, an auditor, and no change
to any label.*

*** 5. Do not adopt GitHub's deployment state machine as the source of truth.

Already argued in =docs/release-standards.org= (self-reported, not attested) and
in =docs/github-environments.org= (nothing that deploys this estate runs in
Actions). Three additions from this survey that strengthen the case [E]:
supersession fires no webhook, =auto_inactive= excludes production so a
blue/green pair retires nothing by itself, and status history is deleted at 90
days. *Use the Deployments API as a place to write records, as
=docs/github-environments.org= concludes. Do not read the estate out of it.*

*** 6. Adopt nothing from SLSA, in-toto, SPIFFE, OSCAL or Backstage for this question.

Recorded so the absence is on the record rather than an omission.

** The cost of the status quo, stated plainly

Keeping the labels as folklore costs three things, and only the third is serious:

1. *No interoperability.* Nothing else can read =staging:e2e=. This is priced at
   zero: nothing else is trying to.
2. *No conformance test.* =gates/label-audit.py= and =tla/Labels.tla= are the
   conformance test, and they are better than anything a standard would give,
   because they check *this* machine (=docs/label-state-machine.org=: 2,336,400
   states, twelve rules, 13/13 cross-checked). *A repo that model-checks its own
   label machine does not need a standard to tell it the machine is consistent.*
3. *The two-valued verdict stacks.* This is the real cost, it is the thing
   Kubernetes, Argo CD, Argo Rollouts and Flux all get right, and it is fixable
   for the price of three labels. Everything else in this file is a citation;
   this is a defect.

nothing crosses.* That is the same boundary =docs/release-standards.org= drew
between signed provenance and deployment events, one layer up.

* Refutation conditions for this file

1. A tier-1 or tier-2 specification is found that defines a deployment state
   machine with named environments *and* a third value distinct from failure.
   (§Part 3's summary table asserts none exists.)
2. A label string with environment semantics is found on more than 100 *distinct
   repositories*. (§Part 2 asserts every one is a single-repo habit; the counts
   are per issue, not per repo, and only the top-6 repositories per label were
   checked — *this is the weakest measurement in the file* [H].)
3. Any repository is found whose =freeze=-family label means "the estate is
   stopped for everyone" rather than "this change may cross the freeze".
4. GitHub ships a repository- or organisation-scoped deployment freeze.
5. CDEvents adds a failure predicate or an =outcome= field to
   =dev.cdevents.service.deployed=.
6. =gates/label-audit.py= is shown to accept a write by a non-declared owner,
   which would make the conformance claim in §The cost of the status quo false.
