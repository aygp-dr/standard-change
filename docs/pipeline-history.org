#+TITLE: A timeline of the deployment pipeline, and where the options for the next ADR come from
#+SUBTITLE: Research notes — which historical changes altered what a pipeline *means*, and which of our five options each one belongs to
#+AUTHOR: aygp-dr
#+DATE: 2026-09-14
#+OPTIONS: toc:2 num:nil

* Status

*Research notes. Not spec, not an ADR, not a proposal.* =spec.org= governs;
nothing here amends it. Epistemic labels are =spec.org='s: [E] established,
[P] provisional, [H] hypothesis, [I] inferred.

This file sits beside =docs/release-strategies.org= (which priced release
trains against mainline-only on the simulator) and =docs/release-standards.org=
(which asked what is actually standardised) and does not repeat either. It
answers a question neither asked: *where did each of the options in front of
the next ADR come from, and what did the industry learn when it tried them?*

The next ADR follows ADR 0001 (automatic promotion, gated by evidence) and ADR
0003 (the schedule is a separate, deliberately dumb component). Its question is
how a change gets from /scheduled/ to /implementing/ — who or what starts the
deployment, and on whose evidence. Five options are on the table:

| # | Option                                                                | Ancestor in the timeline                   |
|---+-----------------------------------------------------------------------+--------------------------------------------|
| 1 | *Manual schedule, automated deployment.* A person books the window; a set of validation tasks in the environment must pass; then the deployment runs unattended, started through the API, a skill, or the CLI | Humble & Farley 2010: the pipeline with a manual gate at the end; ADR 0001 Option 0 |
| 2 | *Integrated scheduler.* The scheduler activates on its own when the window comes due, re-evaluating every guard | Kargo / CodePipeline stage conditions 2023–24; ADR 0001 Option B as built |
| 3 | *Application isolation.* Give each app its own path to production; no shared surface, no berth, no queue | Microservices / "you build it, you run it" (Amazon 2006); ADR 0001 Option A |
| 4 | *Migrate to a release train.* Fixed cadence, variable scope; a change that misses the cut rides the next one | Chrome 2010, Firefox 2011; ADR 0001 Option A3 |
| 5 | *Mainline deployment.* Deploy =main= at a SHA and nothing else; branching strategy changes to trunk-based | Trunk-based development; GitHub flow 2011; ADR 0001 Option A4 |

Every row's ancestor was tried at scale by someone, and the table at the end
records what each of them found. The timeline is the argument that the options
are not five equally-weighted alternatives: three of them are answers to a
problem the other two do not have.

* Timeline — changes that altered pipeline semantics
:PROPERTIES:
:CUSTOM_ID: timeline
:END:

The criterion for inclusion is narrow. A row belongs here only if, after it,
one of the following words meant something different: /build/, /release/,
/deploy/, /promote/, /version/. A great many important tools are omitted
because they made an existing meaning cheaper without changing it.

** 1972 — SCCS
:PROPERTIES:
:CUSTOM_ID: t-1972-sccs
:END:

Rochkind, Bell Labs. A version is a delta on *one file*. There is no notion of
a tree state; "which build" is not a question the tool can answer. [H]

** 1982 — RCS
:PROPERTIES:
:CUSTOM_ID: t-1982-rcs
:END:

Tichy, Purdue. Branches and symbolic names, still per file. A "release" is a
tag applied file by file, which can name a tree that never existed together. [H]

** 1986–1990 — CVS
:PROPERTIES:
:CUSTOM_ID: t-1986-cvs
:END:

Grune's shell scripts (1986) then Berliner's C rewrite (1989–90). Module-level
checkout over per-file revisions. A tag can still name an inconsistent tree;
the pipeline's identity problem is inherited whole. [H]

** 1995–2000 — atomic commits: Perforce, then Subversion
:PROPERTIES:
:CUSTOM_ID: t-1997-atomic
:END:

Perforce changelists (mid-1990s) and Subversion (2000, first release 2004).
A revision names a *whole tree*. "Which build" becomes answerable for the first
time. This is the first of the three inflection points. [H]

** 1999–2000 — integrate on every commit
:PROPERTIES:
:CUSTOM_ID: t-1999-ci
:END:

Beck, /Extreme Programming Explained/ (1999); Fowler, "Continuous Integration"
(2000, revised 2006). The build is the oracle for =main=. What the CI server
says about a commit *is* the verdict on that commit — the ancestor of every
gate in =gates/=. [H]

** 2001–2005 — the build server as a component
:PROPERTIES:
:CUSTOM_ID: t-2001-cruisecontrol
:END:

CruiseControl (ThoughtWorks, 2001); Hudson (Kawaguchi, 2005; forked to Jenkins
2011). The build acquires an identity and a log; it is a thing one can point
at. Guard 4b's "evidence on the head SHA" presupposes this. [H]

** 2005–2008 — Git, then GitHub
:PROPERTIES:
:CUSTOM_ID: t-2005-git
:END:

Git (Torvalds, 2005); GitHub (2008). Content-addressed tree: the SHA *is* the
build identifier, and it is the same identifier in every environment. Branching
becomes free, which is what creates the branching-policy problem — every
policy in §Branching policies is a response to Git making branches cheap. [H]

** 2006–2009 — deploy frequency as a design goal
:PROPERTIES:
:CUSTOM_ID: t-2009-flickr
:END:

Vogels on Amazon, "you build it, you run it" (ACM Queue interview, 2006);
Allspaw & Hammond, "10+ Deploys Per Day: Dev and Ops Cooperation at Flickr"
(Velocity, 2009). Deploy is decoupled from release and made routine. This is
the ancestor of *Option 3* — small teams, own path to production. [H]

** 2010 — the deployment pipeline is named
:PROPERTIES:
:CUSTOM_ID: t-2010-cd
:END:

Humble & Farley, /Continuous Delivery/. Stages, gates, *one* build promoted
through environments. The manual approval step at the end of the pipeline is
in the book; it is the ancestor of *Option 1*. [H]

** 2010 — git-flow
:PROPERTIES:
:CUSTOM_ID: t-2010-gitflow
:END:

Driessen, "A successful Git branching model". Long-lived =develop=,
=release/*=, =hotfix/*=, =master=. A release is a merge and a tag. Driessen's
own 2020 note of reflection says the model was written for versioned software
shipped to customers and is not the right fit for continuously delivered web
apps. [H]

** 2011 — GitHub flow; feature flags at scale
:PROPERTIES:
:CUSTOM_ID: t-2011-github-flow
:END:

Scott Chacon, "GitHub Flow" (2011): one =main=, short branches, *deploy the
branch before merging*, merge if healthy. This is the ancestor of our
production-first rule and of *Option 5*. Feature flags at scale (Facebook
Gatekeeper, Etsy) in the same years; Hodgson formalised the vocabulary on
martinfowler.com in 2017. Release is decoupled from deploy: code on production
is not code in use. [H]

** 2013 — Docker
:PROPERTIES:
:CUSTOM_ID: t-2013-docker
:END:

The artifact is an immutable image. "Rebuild per environment" becomes an
anti-pattern; the *digest* replaces the source SHA as the deployed identifier.
Second inflection point. Guard 5 (the estate serves the promoted build) is
only stateable once the deployed thing has an identity independent of the
source tree. [H]

** 2013–2023 — merge queues
:PROPERTIES:
:CUSTOM_ID: t-2013-bors
:END:

Bors (Hoare, Rust, 2013) implementing the "not rocket science" rule (Hoare,
2014 post); Zuul (OpenStack); Mergify; GitHub merge queue (GA 2023). =main=
only advances to a state CI has tested with the *exact merged tree*. This is
guard 0 and guard 4b implemented in the forge. [H]

** 2014 — Kubernetes; trunk-based development named
:PROPERTIES:
:CUSTOM_ID: t-2014-k8s-tbd
:END:

Kubernetes (Google, 2014): declarative desired state; reconciliation replaces
scripted deploy. Hammant, trunkbaseddevelopment.com (2017, drawing on practice
from the 2000s): the counter-model to git-flow. [H]

** 2016 — SRE book; academic framing
:PROPERTIES:
:CUSTOM_ID: t-2016-sre
:END:

Beyer et al., /Site Reliability Engineering/, ch. 8 "Release Engineering"
(Rapid): hermetic builds, cherry-pick release branches, canary. Adams &
McIntosh, "Modern Release Engineering in a Nutshell" (SANER 2016); Savor et
al., "Continuous Deployment at Facebook and OANDA" (ICSE-SEIP 2016). The
pipeline becomes a research object. [H]

** 2017–2018 — GitOps
:PROPERTIES:
:CUSTOM_ID: t-2017-gitops
:END:

Richardson, "GitOps — Operations by Pull Request" (Weaveworks, 2017); Flux
(2016–17); Argo CD (2018). Git is the desired state; deploy is a *sync*, not a
push. Third inflection point, and the one that matters most for the ADR:
reconciliation has no verb for /promote/, so promotion has to be modelled
separately. Our berth, calendar and activation sit in the gap GitOps opened. [H]

** 2018 — Accelerate
:PROPERTIES:
:CUSTOM_ID: t-2018-accelerate
:END:

Forsgren, Humble, Kim. The four DORA metrics as the measure of pipeline
quality. =docs/release-standards.org= already records that this frame is
structurally blind to forfeited windows and revalidation runs. [H]

** 2019–2021 — provenance
:PROPERTIES:
:CUSTOM_ID: t-2019-provenance
:END:

in-toto 1.0 (2019); SLSA (2021); Sigstore (2021). Verdicts and provenance are
bound to artifacts and signed by the party that produced them. This is the
only genuinely standardised layer in the space, and it is about builds, not
deployments. [H]

** 2020 — ITIL 4 Change Enablement
:PROPERTIES:
:CUSTOM_ID: t-2020-itil4
:END:

Standard / normal / emergency change, change authority, change schedule — in
the vocabulary most enterprises use. This repo's name and its =itil:*= labels
are from here. [H]

** 2020–2021 — the forge carries environment state
:PROPERTIES:
:CUSTOM_ID: t-2020-gh-environments
:END:

GitHub Environments (GA 2020–21): required reviewers, wait timers, deployment
branches. Cloudflare Workers versions and gradual deployments (2024): the
version is a first-class immutable object with a percentage. [H]

** 2023–2024 — promotion as a modelled object
:PROPERTIES:
:CUSTOM_ID: t-2023-kargo
:END:

Kargo (Akuity, 2023): =Freight= and =Stage= as first-class objects, with
per-stage verification. Argo Rollouts analysis; AWS CodePipeline stage
conditions (2024) with deployment-window rules. The thing GitOps left out is
being put back as a model. This is the closest ancestor of *Option 2*. [H]

** 2025–2026 — agentic CI
:PROPERTIES:
:CUSTOM_ID: t-2025-agentic
:END:

Claude Code, Copilot coding agent. The author of a change may be a machine.
Who may add =release= becomes a policy question rather than a social one —
which is what =docs/label-ownership.org= and =change/label-owners.tsv= are
for. [E: this repo]

** The three inflection points

Everything above collapses to three changes of meaning, and the ADR's options
sort by which one they respond to:

1. *Atomic commits* — a build is a tree. Without this, "the tested thing is
   the deployed thing" is not a statement anyone can make.
2. *Docker* — the artifact is immutable and its identifier is a digest.
   Without this, guard 5 has nothing to read.
3. *GitOps* — deploy is reconciliation, so /promote/ needs a separate model.
   This is the gap the berth and the calendar fill, and the gap Options 1 and
   2 are both proposals for filling.

Options 3, 4 and 5 are not about the gap. They are about whether the shared
surface that makes the gap expensive should exist at all.

* Branching policies
:PROPERTIES:
:CUSTOM_ID: branching-policies
:END:

Each policy is a response to Git making branches free. Listed with the option
it feeds.

- *Git-flow* (Driessen 2010). =develop=, =release/*=, =hotfix/*=, =master=;
  release is a merge and a tag. Long-lived branches, merge-heavy; matches
  versioned products shipped to customers. Feeds no option here — it is the
  thing Option 5 replaces.
- *GitHub flow* (Chacon 2011). One =main=, short feature branches, deploy from
  the branch before merge. GitHub's own practice was deploy-the-branch, then
  merge if healthy. Direct ancestor of the production-first rule and of
  *Option 5*'s "deploy =main@sha=" discipline.
- *GitLab flow* (2014). =main= plus environment branches (=pre-production=,
  =production=) or release branches; promotion is a merge into the environment
  branch. A branch-bound authorization — exactly the silent failure
  =scenarios.org= C2 names. Named here so nobody proposes it.
- *Trunk-based development* (Hammant). Commit to =main= or branches shorter
  than a day; release branches cut from trunk with fixes cherry-picked forward;
  feature flags carry incomplete work. Google, Facebook, and most DORA-elite
  organisations. The branching side of *Option 5*.
- *Release branches with cherry-picks* (Google Rapid, Chromium). =main= moves;
  a release branch is cut and only accepts cherry-picks. Stabilisation happens
  on the branch, not on =main=. The mechanism inside *Option 4*.
- *Stacked diffs* (Phabricator, Graphite, Sapling). A series of dependent small
  changes reviewed and landed in order; =main= is always deployable, and a
  change is one diff, not one branch. Orthogonal to all five options; noted
  because it changes what a *unit* is.
- *Merge queues* (Bors 2013, Zuul, Mergify, GitHub merge queue 2023). =main=
  only advances to a state CI has tested with the exact merged tree. This is
  guard 0 and guard 4b implemented in the forge, and it is a prerequisite for
  *Option 5* to be honest rather than nominal.

* Release trains
:PROPERTIES:
:CUSTOM_ID: release-trains
:END:

- *Origin.* Chrome (2010) and Firefox (2011) rapid release. A train leaves on a
  fixed cadence (six weeks, later four); a change catches the next train or
  waits. Cadence is fixed, scope is variable.
- *Eclipse simultaneous release* (2006, "Callisto"). Many independent projects
  aligned to one annual date; the train is a coordination point across teams,
  not a deployment mechanism.
- *SAFe Agile Release Train.* The organisational form, ten to twelve weeks,
  mostly a planning construct.
- *Mobile app stores.* The train is forced by review latency; hotfixes are
  expensive, so the release branch is cut early and soaked.
- *Relation to our model.* A train is a designated window that repeats. The
  queue is FIFO into the train; a change that misses the cut is =expired= for
  that train and eligible for the next. ADR 0003's "no automatic reslotting"
  is the trunk-based position; a train is the *opposite* choice, where
  reslotting to the next cadence is the norm and the calendar is the product.
  =docs/release-strategies.org= measured this: 23× less revalidation work per
  shipped change at a one-hour cadence, and no help at all for
  =change:emergency=.

* What each option's ancestor found
:PROPERTIES:
:CUSTOM_ID: what-each-found
:END:

| Option | Tried by | What they found | Bearing on the ADR |
|--------+----------+-----------------+--------------------|
| 1 manual schedule, automated deploy | Humble & Farley's pipeline with a manual production gate; most enterprises under ITIL | The gate becomes a rubber stamp when it cannot fail on evidence; it becomes a bottleneck when it can. | Only honest if the validation tasks are real gates (ADR 0001 §Option 0's test: a guard that cannot be made to fail is not a guard). The interface — API, skill, CLI — carries no semantics (=README.org= §Interfaces). |
| 2 integrated scheduler | Kargo, CodePipeline stage conditions, GitHub Environments wait timers | Promotion needs its own model once deploy is a sync; deployment windows are a first-class rule in every one of these. | This is what =change/activate.sh= already is. The ADR's question is whether the scheduler /re-evaluates/ or merely /fires/ — ADR 0003 says re-evaluates. |
| 3 application isolation | Amazon 2006; every microservices migration since | Contention disappears; coordination reappears at the interface. | Dissolves the problem rather than repricing it (ADR 0001 §Option A). The cost is contracts at the router, which is real engineering. |
| 4 release train | Chrome, Firefox, Facebook web 2008–2016 | Facebook abandoned the branch-and-cherry-pick train when the *coordination* cost stopped scaling, not the batching arithmetic (=release-strategies.org= §History). Firefox's rapid release did not measurably worsen quality (Khomh et al. 2012) but did shorten the fix window. | Fixes the 1/20 contention; does nothing for emergencies; rollback granularity becomes the train. |
| 5 mainline deployment | GitHub 2011, trunk-based shops, DORA-elite cohort | "Deploy main" without a verdict on the SHA is branch-bound authorization; with a verdict it costs one run per merge. | Relocates guard 4b, does not remove it (=release-strategies.org= §Mainline-only does not touch guard 4b). Requires a merge queue to be more than nominal. |

The table says what the timeline says. Options 1 and 2 are two ways of filling
the promotion gap and differ only in who presses the button. Options 3, 4 and 5
change what is being promoted. The next ADR should decide the first pair
knowing that the second triple is available and that only Option 3 removes
the problem rather than repricing it.
