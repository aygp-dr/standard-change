#+TITLE: Emulating the jail estate on macOS, and the primitives a cloud deploy needs
#+SUBTITLE: Speculation — what a lightweight-container stand-in for the bastille target must provide, and what CodeDeploy and its peers expose that ours does not
#+AUTHOR: aygp-dr
#+DATE: 2026-09-14
#+OPTIONS: toc:2 num:nil

* Status

*Speculation. Not spec, not an ADR, nothing here has been run.* Every claim
below is [H] unless marked otherwise; the [E] rows are the repo's own recorded
observations of the bastille target on hydra. =spec.org= governs.

The question is in two halves. First: hydra runs the protected environments
as FreeBSD jails, and the owner's laptop is a Mac. What would a lightweight
container estate on macOS have to provide for the same gates to produce the
same verdicts? Second: if the estate were AWS CodeDeploy, or Google Cloud
Deploy, or Kubernetes, which primitives would the pipeline have to read and
write — and which of those does the local stand-in need to fake so that the
model stays honest about what it has and has not exercised?

* What the jail estate actually is, reduced to primitives
:PROPERTIES:
:CUSTOM_ID: jail-primitives
:END:

Read off =targets/bastille/README.org=, =SETUP.org= and =deploy.sh=:

| primitive | how the jail provides it | status |
|-----------+--------------------------+--------|
| *one network namespace per environment* | each jail has its own =10.0.0.x=; nginx on =:80=, apps on =127.0.0.1:8001–8005=; identical layout in every environment, so promotion cannot introduce a config difference | [E], with a defect: non-VNET jails remap loopback to the jail IP, so =curl 10.0.0.60:8002= answers. Route ownership is a convention here, not a network fact |
| *host-side attestation of what is running* | =jls= and =bastille list= are the host's statement, not the deployer's | [E] |
| *a build identity written by the environment, not the deployer* | =/var/run/version.json= written at deploy, served at =/version.json=; =x-build-sha= header from the apps | [E], but =deploy.sh= writes it from the SHA it was handed. ADR 0001 §Option 0 found guard 5 tautological in manifest mode for exactly this reason |
| *replicas with real identities* | =sc-prod-1=, =sc-prod-2=, each its own IP, so guard 5's convergence is over a fleet | [E] |
| *a traffic switch distinct from install* | =front= reads the live colour per request; blue/green at 9210/9220 | [E] |
| *a rollback target that survives* | the previous jail can be kept stopped rather than destroyed | [P] — proposed, not exercised |
| *promotion by identity* | absent. =deploy.sh= installs a commit and each environment builds it; staging and production are separate builds of the same source | [E] defect, recorded in =SETUP.org= |

The last two rows are the interesting ones, because a container substrate
gives the missing one for free and jails cannot. That reverses the usual
framing: the Mac is not a degraded copy of hydra. It is a different substrate
that is *stronger* on identity and *weaker* on FreeBSD fidelity, and the
emulation question is which of those the gates actually care about.

* Four ways to run it on macOS
:PROPERTIES:
:CUSTOM_ID: macos-options
:END:

Every container on macOS is inside a Linux VM; there is no native jail or
container primitive in Darwin. The choices differ in how many VMs, whether
each environment gets its own address, and what the host can attest.

** A. A FreeBSD VM, bastille inside it
:PROPERTIES:
:CUSTOM_ID: option-freebsd-vm
:END:

One FreeBSD guest under Virtualization.framework (Lima carries a FreeBSD
template; =vfkit= or =qemu= work too), bastille installed in it, the three
jails on a bridge inside the guest. This is the *only* option that runs the
same =jexec=/=jls= path as hydra, so =targets/bastille/deploy.sh= runs
unmodified and its attestation claim is the same claim.

- What the Mac sees: the guest's bridge is not routable from the host by
  default. Either add a route to the guest's =10.0.0.0/24= via the VM's
  address, or port-forward =:80= of each jail to a distinct host port — which
  reintroduces the port-block scheme the jail target exists to kill, on the
  host side only.
- Cost: one VM image to build and keep; FreeBSD guests under
  Virtualization.framework are workable but less trodden than Linux. The
  non-VNET loopback defect is reproduced exactly, which is a feature for an
  emulation and a bug for a product.
- Verdict: the highest-fidelity stand-in and the only one where "the same
  gate produced the same verdict" is literally true rather than analogous.

** B. Apple =container= (Containerization framework, macOS 26)
:PROPERTIES:
:CUSTOM_ID: option-apple-container
:END:

Each container is its own lightweight Linux VM with its own IP on a host
bridge, reachable from the Mac by address. That is the closest structural
match to "one jail, one IP": four containers (=front=, =staging=,
=prod-blue=, =prod-green=), each running nginx =:80= and the apps on
loopback, identical config, addressed directly.

- Attestation: =container ls= and =container inspect= are the daemon's
  statement, which is the same *kind* of evidence as =jls= — the party that
  runs the workload says what it is running. The build identity is the image
  digest, which is stronger than =version.json=: the environment cannot
  misreport what it is running because the digest *is* what it is running.
- Loopback is real: a container's =127.0.0.1= is its own, so the non-VNET
  defect does *not* reproduce. The e2e assertion "only the router is
  routable" becomes true here and false on hydra, which is a cell the matrix
  must record as a difference, not a pass.
- Cost: Linux, not FreeBSD; =app.py= and nginx are portable, so the fixture
  apps do not care, but nothing about FreeBSD packaging is exercised. macOS 26
  only. [H — the per-container-IP claim is from Apple's announcement, not
  observed here.]

** C. Docker Desktop, Podman machine, or colima
:PROPERTIES:
:CUSTOM_ID: option-docker
:END:

One Linux VM, containers on a user-defined bridge inside it. Containers have
their own IPs *inside the VM* and their own loopback, but the Mac cannot reach
container IPs directly; only published ports are visible. So:

- Either publish =front= alone on one host port and let it proxy to the
  others by container name — which mirrors the estate exactly, since
  =front= is the only thing that should be routable anyway. The gates then
  run *inside* the VM network (a fifth container running =gates/=), or
  against =front= only.
- Or publish each environment on a distinct host port, which is the
  port-block scheme again.
- Attestation is =docker inspect=; identity is the image digest. Same
  strengths as B.
- Cost: lowest. Works on any macOS today. The compose file is about forty
  lines. The gates must learn to run from inside the network or accept that
  staging and production are only reachable through =front= on the host —
  the latter is arguably *more* faithful to a real estate than hydra is.

** D. Nested: jails inside a Linux container
:PROPERTIES:
:CUSTOM_ID: option-nested
:END:

Not possible. Jails are a FreeBSD kernel facility; a Linux container cannot
host one. Listed only because "jails under lightweight containers" reads that
way, and the answer is that the nesting runs the other direction: a FreeBSD
*VM* is the lightweight thing and the jails are inside it (option A). If the
phrase meant "the jail's *role* played by a lightweight container", that is
options B and C.

** What the gates care about, and which option provides it
:PROPERTIES:
:CUSTOM_ID: gates-by-option
:END:

| gate needs | A FreeBSD VM | B Apple container | C Docker |
|------------+--------------+-------------------+----------|
| =front= reachable from the host | yes, via route or forward | yes, by address | yes, published port |
| staging and production addressable individually | via route or forward | yes | only from inside the VM, or forwarded |
| =x-build-sha= from every replica | yes (apps unchanged) | yes | yes |
| =/version.json= written by the environment | same defect as hydra | entrypoint writes it from the image label — the environment *does* know its own digest | same as B |
| independent "what is running" read for guard 5 | =jls= over ssh | =container inspect= | =docker inspect= |
| promotion by identity (spec §Cloud mirror) | no | yes — retag/redeploy the digest staging ran | yes |
| rollback target survives | previous jail stopped | previous image, previous container stopped | same |
| non-VNET loopback defect reproduced | yes | no | no |
| FreeBSD packaging exercised | yes | no | no |

The table says B or C is the better estate and A is the better *emulation*.
Which one is wanted depends on what the matrix cell is for. A cell that says
"the gates pass on macOS" should use C, because it is cheapest and it
exercises the property hydra cannot. A cell that says "hydra's own target
runs on a laptop" needs A. They are different claims and =spec.org= §Host
survey should not let one stand in for the other.

* The primitives a cloud deploy exposes, and what ours lacks
:PROPERTIES:
:CUSTOM_ID: cloud-primitives
:END:

Whatever the local estate is, the model claims platform neutrality, so the
stand-in should expose the primitives a real deploy service would, or record
that it does not. Read off the vendors' own models:

** AWS CodeDeploy
:PROPERTIES:
:CUSTOM_ID: codedeploy
:END:

- *Application → deployment group → deployment.* A deployment group is a set
  of targets (instances by tag, an ASG, an ECS service, a Lambda alias) plus
  a deployment configuration and rollback settings. A deployment has an ID
  and a status from a closed set (=Created=, =Queued=, =InProgress=,
  =Succeeded=, =Failed=, =Stopped=, =Ready=).
- *Revision.* The thing deployed is a bundle in S3 identified by bucket, key,
  and ETag or version, or a GitHub commit. The revision is immutable and the
  deployment names it.
- *Deployment configuration.* =AllAtOnce=, =HalfAtATime=, =OneAtATime=, or a
  custom minimum-healthy-hosts count; for ECS and Lambda, canary and linear
  traffic-shifting configurations with percentages and intervals.
- *Lifecycle hooks.* =ApplicationStop=, =BeforeInstall=, =Install=,
  =AfterInstall=, =ApplicationStart=, =ValidateService=; blue/green adds
  =BeforeAllowTraffic= and =AfterAllowTraffic=. Each hook runs a script on
  each target and the *agent* reports the outcome per target per hook.
- *Rollback.* Automatic on deployment failure or on a CloudWatch alarm; a
  rollback is itself a new deployment of the previous revision.
- *What CodeDeploy does not have.* A calendar, a berth, or a change class.
  Those live in Systems Manager Change Manager and Change Calendar, and in
  CodePipeline's =DeploymentWindow= stage condition — *outside* the deploy
  service. That is ADR 0003's position, implemented by a vendor: scheduling
  is a separate component and the deployer reads one bit from it.

Mapped to this repo:

| CodeDeploy | here | gap |
|------------+------+-----|
| deployment ID + status enum | the activation lease and =change/state.sh= | our status is labels on a PR; not a closed enum written by the platform |
| revision (immutable, named by the deployment) | head SHA, =version.json= | jails rebuild per environment — no immutable revision |
| minimum healthy hosts | guard 5 convergence across =sc-prod-1/2= | we have two replicas and no notion of "healthy count during the roll" |
| =ValidateService= hook | =gates/health.sh=, =gates/e2e.sh= | ours runs from outside; CodeDeploy's runs *on the target* and the agent reports it |
| =BeforeAllowTraffic= / =AfterAllowTraffic= | =front= switch | we switch, but no hook runs between install and switch |
| alarm-driven rollback | rollback + PIR, on a failed health check | no alarm input; a metric that degrades after the health check passes does nothing |
| per-target lifecycle event stream | none | =deploy-run/= emits no per-replica, per-hook events |

** The others, briefly
:PROPERTIES:
:CUSTOM_ID: other-providers
:END:

| provider | unit of promotion | build identity | health oracle | traffic shift | window / calendar | attestation of what is running |
|----------+-------------------+----------------+---------------+---------------+-------------------+--------------------------------|
| Google Cloud Deploy | release → rollout, through ordered targets; phases | release names container images by digest | =verify= job (Skaffold) per rollout | canary via service mesh or Cloud Run traffic | deploy policies with =timeWindows=; timed promotion | rollout state from the service |
| Kubernetes Deployment | a new ReplicaSet | image digest in the pod spec | readiness and liveness probes; =rollout status= | rolling update with =maxSurge= / =maxUnavailable= | none native | =kubectl get pods= — the API server's statement |
| Argo Rollouts | a Rollout step sequence | image digest | =AnalysisRun= against metrics | canary weights, blue/green preview and active services | none native | rollout status |
| Cloudflare Workers | a version | version ID | none native; external checks | gradual deployment percentages between two versions | none | =wrangler deployments list= — the platform's statement [E: =spec.org= §C6] |
| Spinnaker Managed Delivery | an artifact into an environment | artifact version | canary constraint (Kayenta) | via the cloud provider | =allowed-times= constraint | environment state |
| Kargo | Freight into a Stage | Freight ID over image digests and git commits | Stage verification (AnalysisTemplate) | via Argo Rollouts | none native; promotion policies | Stage health from Argo CD |

Two things every column agrees on, and which the local stand-in must
therefore provide:

1. *The platform, not the deployer, records what is running.* =jls=,
   =container inspect=, =kubectl get pods=, =deployments list=. The stand-in
   on macOS has this for free from the container runtime. The bastille target
   has it from =jls=. What neither has yet is a gate that *reads* it — guard
   5 reads =/version.json= and the header, both written by the thing under
   test. Whichever substrate is chosen, the next gate to write is the one
   that compares the environment's self-report against the runtime's record.
2. *Windows live outside the deployer.* CodeDeploy, Kubernetes, Argo,
   Cloudflare and Kargo have no calendar; CodePipeline, Cloud Deploy and
   Spinnaker bolt one on as a stage condition or a constraint; AWS puts the
   calendar in a different service entirely. Nobody integrates the scheduler
   into the deploy primitive. ADR 0003 is the industry's position, not a
   local preference.

And three primitives ours lacks that the stand-in should fake explicitly
rather than omit silently, so that a matrix cell can say "exercised" or
"not exercised" per primitive:

- *a per-replica, per-hook event stream* — =deploy-run/= should emit one
  record per replica per lifecycle step, because that is what every vendor's
  agent does and what a PIR reads;
- *a metric or alarm input to rollback* — a health check is a point read;
  CodeDeploy, Argo and Cloud Deploy all roll back on a *trend* after the
  point read passed;
- *a closed status enum for a deployment written by the platform* — ours is
  labels, which are a person's or a workflow's assertion, and =spec.org=
  §Domain model already says a self-report is not a record.

* Proposed experiment [H — not filed]
:PROPERTIES:
:CUSTOM_ID: proposed-experiment
:END:

=experiments/020-macos-estate/=, option C (Docker or Podman), because it is
the cheapest and it exercises promotion by identity, which hydra cannot.

- *Hypothesis.* Every scenario in =scenarios.org= that is run against the
  bastille target produces the same verdict against a four-container estate
  on macOS, with =front= the only published port and the gates run from a
  fifth container on the same bridge.
- *Success criterion.* Verdict-for-verdict agreement on the scenario table,
  *plus* two expected disagreements recorded as differences: the non-VNET
  loopback defect does not reproduce, and =deploy.sh= promotes a digest
  rather than rebuilding.
- *Run.* =docker compose -f experiments/020-macos-estate/compose.yml up=;
  then =docker compose exec gates sh -c 'gmake gate app=plp'=.
- *What would refute it.* Any scenario whose verdict differs for a reason
  other than the two named. In particular, if guard 5 passes on macOS only
  because the entrypoint writes =version.json= from the image label, that is
  the same tautology ADR 0001 found, wearing a digest — and the experiment
  should say so rather than count it.

Option A is a second experiment, not this one, and only if a matrix cell
"hydra's target on a laptop" is actually wanted.

* Refutation conditions

1. A macOS container runtime whose per-environment IPs are reachable from the
   host without a route or forward, *and* which is available below macOS 26.
   Would collapse B and C into one option.
2. A vendor deploy service with a native change calendar inside the deploy
   primitive. Would refute "windows live outside the deployer".
3. A bastille configuration under which promotion is by identity. Would
   remove the strongest reason to prefer B or C over A.
