* Status

*Research notes. Not spec, not an ADR, not a proposal.* =spec.org= governs;
nothing here amends it. Epistemic labels are =spec.org='s: [E] established on a
named cell, [P] provisional, [H] hypothesis, [I] inferred.

This file sits beside two others and deliberately does not repeat them.
=docs/release-strategies.org= priced release trains against mainline-only and
found DORA never studied release trains; =docs/ci-portability.org= asked which
platforms provide the capabilities the guards need. This file asks the two
questions neither of those asked:

1. Of the things we argue about — release records, deployment records,
   provenance, cadence — *which are actually standardised*, and which are
   folklore wearing a standard's clothes?
2. Our guards assume one production surface serving one build. *What happens to
   them when the artifact is a library, or a fleet mid-rollout, or GitHub
   Pages?*

The answers, stated first.

#+begin_quote
*On standards.* Almost nothing here is standardised. DORA is an empirical
research programme, not a standard, and its measurement frame is *structurally
blind* to this repo's dominant cost: all five of its metrics take a deployment
that reached production as the unit of observation, so a forfeited window is
not an event and a revalidation run is not an event. Ten years of State of
DevOps reports contain *zero* occurrences of "release train", "release branch",
"cherry-pick", "deployment window", "change window" or "forfeit" [E]. The only
genuinely standardised thing in the whole space is *provenance* — and provenance
standards are about builds, not deployments. ITIL 4, the framework everyone
treats as the bureaucratic one, is the *only* body of practice that can even
record a forfeited window.

*On artifact types.* The claim is *confirmed with one correction*. Guard 5 is
the first to break, everywhere and for three unrelated reasons — and it is
*unimplementable as written on this repo's own default target*, because GitHub
Pages cannot set custom response headers [E]. But guard 4b is *not* the second
to break: it survives libraries literally, with only its subject restated. The
second to go vacuous is *guard 1*, the berth — because the berth is a property
of a shared surface, and three of the four artifact shapes do not have one. And
the axiom that fails most expensively is the one nobody listed: *the model
assumes deployment is undoable*, and for libraries and for stateful services it
is not.
#+end_quote

* Scope, method, and what was deliberately not researched

** Deliberately excluded

The internal release harnesses of Anthropic, OpenAI, IBM and Oracle were *not*
researched, on instruction: we are not following them, and the standing mandate

there and nothing below depends on it.

Everything marked [E] below was read. Where a document is paywalled, that is
said, and the claim is labelled accordingly rather than quietly upgraded.

- *DORA*: all nine State of DevOps report PDFs (2016–2019, 2021–2025; there is
  no 2020 report [E]) were fetched and searched in full text, along with
  =dora.dev='s guide, capability and survey-instrument pages. The 2014 and 2015
  reports were *not* fetched, so term counts start at 2016 [H for those years].
- *Google SRE*: =sre.google= chapters read directly.
- *ITIL 4 and ISO/IEC 20000-1:2018*: both paywalled. The purpose statements
  below are quoted from *secondary* sources and are labelled [E, secondary] —

  corroboration and not verification.
- *Vendor documentation is not an observation.* =ci-portability.org='s rule
  applies: that GitHub documents a behaviour makes it [H] until we run it. The
  one exception below is the GitHub Pages header finding, which is a documented
  *absence* confirmed by a named GitHub staff member — an absence is the one
  thing a vendor doc is authoritative about.

* Part 1 — what is actually standardised

** A taxonomy, because "standard" is doing too much work

Half the confusion in this area comes from one word covering six different kinds
of object. They differ in exactly one respect that matters: *is there a
conformance test, and who can change the rules?*

| Tier | Kind | Conformance test? | Who can change it | Examples in scope |
|------+------+-------------------+-------------------+-------------------|
| 1 | *Formal standard* — published by a recognised SDO | yes, and certifiable | a committee, slowly | ISO/IEC 20000-1:2018 §8.5.3; ECMA-424; ISO/IEC 5962:2021 |
| 2 | *Open specification* — versioned, with normative language, no SDO | yes, self-asserted | a working group | SLSA, in-toto, OSV, SemVer, CDEvents, OpenTelemetry semconv, PEP 440/592 |
| 3 | *Vendor contract* — documented platform behaviour | no; the platform /is/ the test | the vendor, unilaterally, without notice | GitHub Releases / Deployments / Pages; Cloudflare Workers versions; Netlify deploys |
| 4 | *Framework* — a prescriptive body of practice | certification of people, not systems | a licensor, commercially | ITIL 4 |
| 5 | *Research programme* — descriptive and correlational | none; it measures, it does not prescribe | the researchers, annually | DORA / Accelerate |
| 6 | *Folklore* — widely practised, never written down normatively | none | nobody and everybody | "deploy main"; "one live version"; "rollback = redeploy previous"; release trains; push-on-green; canary at 1% |

*Almost every argument a team actually has at this layer is an argument between
tier 5 and tier 6.* The things that are genuinely tier 1 or tier 2 — provenance,
SBOM formats, version identity — are the things nobody argues about, because
they are settled.

Two consequences worth stating before the detail:

- *Tier 3 is binding on us even though it is not a standard.* GitHub's semantics
  for a Release and a Deployment are not a standard by any definition, and they
  are nonetheless the contract this repo runs on. Treating a vendor contract as
  a standard is how a model ends up unportable; treating it as optional is how a
  model ends up unimplementable. =ci-portability.org= exists because of the
  first failure. §GitHub Pages below is an instance of the second.
- *Tier 5 is not a standard and should stop being quoted as one.* DORA measures
  outcomes. It has no normative content, no conformance notion, and — as below —
  no place to put the number this repo cares about.

** DORA — an instrument for outcomes, with no cost axis

*** It is five metrics now, not four, and the grouping is odd

=dora.dev= no longer presents "four keys". [E]

#+begin_quote
"DORA has identified five software delivery performance metrics that provide an
effective way of measuring the outcomes of the software delivery process."

— =dora.dev/guides/dora-metrics-four-keys/=, last updated 2026-01-05
#+end_quote

| Metric | Definition, verbatim | Factor |
|--------+----------------------+--------|
| Change lead time | "The amount of time it takes for a change to go from committed to version control to deployed in production." | throughput |
| Deployment frequency | "The number of deployments over a given period or the time between deployments." | throughput |
| Failed deployment recovery time | "The time it takes to recover from a deployment that fails and requires immediate intervention." | *throughput* |
| Change fail rate | "The ratio of deployments that require immediate intervention following a deployment." | instability |
| Deployment rework rate | "The ratio of deployments that are unplanned but happen as a result of an incident in production." | instability |

Three corrections to the received version of this, all [E]:

1. *MTTR was renamed and redefined in 2023*, not merely relabelled. DORA's
   stated reason: "The previous way of asking about recovery times did not allow
   for a distinction between a failure initiated by a software change and a
   failure initiated by something like an earthquake interrupting service at a
   data center." (2023 report, appendix, v. 2023-12.)
2. *Rework rate was added in 2024*, not 2023, and the 2024 report split the five
   into throughput and instability. Verbatim: "Change failure rate and rework
   rate are used when we describe software delivery stability… Change lead time,
   deployment frequency, and failed deployment recovery time are used when we
   describe software delivery throughput."
3. *The "fifth metric" of 2021 was reliability, and DORA has since disowned that
   framing*: "The 2021 report inaccurately called the 'reliability' metric the
   'fifth metric' when, in reality, 'reliability' is more a measure of
   operational performance than a measure of software delivery performance."
   (=dora.dev/insights/dora-metrics-history/=, 2026-01-02.)

Note the grouping in the table: *failed deployment recovery time sits under
throughput*, not under instability. That is DORA's own placement and it is worth
noticing, because it means four of the five metrics are about how fast and how
often — and exactly one, plus its rework proxy, is about whether it worked.

*** The direct answer: is a forfeited window or a revalidation recordable?

*No. Neither, anywhere, by construction.* [E]

Every one of the five metrics takes *a deployment that reached production* as
its unit of observation. This repo's dominant cost — 10–20 validation runs per
shipped change (ADR-0001), or 13.63 per ship at eight berths
(=docs/release-strategies.org=) — consists entirely of events that are not
deployments.

| What we spend money on | Where DORA would record it | Verdict |
|------------------------+----------------------------+---------|
| A window reserved and then *forfeited* at activation (guard 4b) | nowhere | *invisible* |
| A staging pass *withdrawn* because =main= moved | nowhere | *invisible* |
| The 12th revalidation run of the same change | nowhere; absorbed into change lead time as elapsed seconds | *invisible, aggregated* |
| A berth held and released without deploying | nowhere | *invisible* |
| A change that deployed and broke production | change fail rate | recorded |
| An unplanned redeploy after a production incident | deployment rework rate | recorded |

The evidence is a term search over all nine reports, full text, de-hyphenated
and whitespace-flattened, with control terms confirming extraction integrity
("deployment frequency" 3–12 hits/yr, "change fail" 5–17 hits/yr): [E]

| Term | Hits, 2016–2025, all reports |
|------+------------------------------|
| =forfeit= | *0* |
| =cancel= | *0* |
| =aborted= | *0* |
| =deployment attempt= | *0* |
| =slot= | *0* |
| =wasted= | *0* |
| =re-run= / =rerun= | *0 / 0* |
| =retest= / =re-test= | *0 / 0* |
| =flaky= | *0* |
| =pipeline efficiency= | *0* |
| =CI cost= / =compute cost= | *0 / 0* |
| =release train= | *0* |
| =release branch= | *0* |
| =cherry= (any) | *0* |
| =deployment window= / =change window= / =maintenance window= / =release window= | *0* |

The six =revalidat*= hits in the 2018 and 2019 reports are false positives:
they are DORA revalidating its own structural equation model across survey
years, not anyone re-running a test suite. [E]

*** Does "rework" cover it? No, and the definition says why

Three exclusions, each independently fatal:

1. *The numerator is a deployment that happened.* A forfeited slot produced no
   deployment.
2. *The denominator is deployments.* A revalidation run is not a deployment.
3. *The trigger is a production incident.* The survey instrument: "Approximately
   what percentage of deployments in the last 6 months were not planned but were
   performed to address a user-facing bug in the application?" Revalidation
   forced by a peer's merge is neither unplanned-in-that-sense nor user-facing.

The 2024 report states the causal direction explicitly: the stability factor
"measures the likelihood deployments unintentionally lead to immediate,
additional work." The arrow runs *forward from* a deployment. Our cost runs
*backward into* a deployment that may never occur.

A separate 2016 "rework" concept exists and must not be conflated with it: it is
a *percentage of technical staff time* in an ROI chapter ("Cost of excess rework
= Technical staff size × Average salary × Benefits multiplier × Percentage of
technical staff time spent on excess rework"), and it was dropped after 2017.
[E] That older metric is, ironically, the closest DORA ever came to measuring
what this repo measures — and it was a cost model, not a delivery metric.

*** The sharp version: DORA's frame mildly rewards forfeiting

This is the finding worth carrying out of the section.

A change that is *forfeited at activation* never enters change fail rate's
denominator. Had that same change deployed and broken production, it would have.
So a pipeline that forfeits aggressively scores *better* on the instability
factor than one that ships the same changes — and identically on deployment
frequency per shipped change, since neither counts attempts.

The only metric that moves is change lead time, and it moves for a reason the
metric cannot separate from six others. The instrument's response bands are
"More than six months / Between one month and six months / Between one week and
one month / Between one day and one week / Less than one day / Less than one
hour" [E]. *Fifteen revalidation cycles inside a two-day window do not
necessarily move the reported band at all.*

Stated as one sentence, because it is the thing to remember:

#+begin_quote
=release-strategies.org= priced the release train at *0.58 validations per ship
versus 13.63*, costing *2.6 h mean latency versus 12.5 h*. In DORA's frame the
*cost* is legible (change lead time) and the *benefit* is not. The instrument
can see the price and not the goods.
#+end_quote

*** The change-fail-rate denominator is genuinely inconsistent

Worth recording because anyone citing DORA at us will cite one side of it. [E]

| Says "deployments" | Says "changes" |
|--------------------+----------------|
| =dora.dev= guide, 2026-01-05: "The ratio of *deployments* that require immediate intervention following a deployment." | Quick Check instrument: "Approximately what percentage of *changes to production or releases to users* result in degraded service…" |
| 2024 report, p. 9: "the percentage of *deployments* that cause failures in production, requiring hotfixes or rollbacks." | 2021/2024/2025 survey questions: "what percentage of *changes to production or released to users*…" |

Both readings are restricted to things that reached production, so neither
creates room for a forfeit. But the prose and the instrument disagree, and DORA
notes it changed the question wording in 2024 to improve the factor loading
("A change to the way respondents answered the change failure rate question
improved the connection"). A metric whose definition and whose instrument
disagree is not a standard.

*** What DORA does say that bears on us

Three things, all [E], and the third is the surprise.

1. *Code freezes are penalised, twice, and only in 2016–2017.* 2016: "Teams that
   don't have code freeze periods (when people can't merge code or pull
   requests) also achieve higher performance." 2017: "We also found that teams
   without code lock periods had higher software delivery performance." These
   are the *only* two hits for any freeze/lock phrasing in nine reports.

2. *The trunk-based-development capability page acknowledges release branches
   and prescribes cherry-picking* — confirming the prior note's quote verbatim:
   "there are cases where bug fixes must be cherry picked and merged into
   releases… In cases where releases happen multiple times a day, release
   branches are not required at all". Its evidence base is stated on the page as
   "DORA data from 2016 (PDF) and 2017 (PDF)". *DORA has not re-validated
   trunk-based development since 2017*, and the words =trunk= and =branch=
   appear *zero times* in the 2024 and 2025 reports. [E]

3. *DORA does have an opinion on release trains — it just never uses the term.*
   The small-batches capability page lists as a pitfall:

   #+begin_quote
   "Working in small batches but then regrouping the batches before sending them
   downstream for testing or release. Regrouping work in this way delays the
   feedback on whether the changes have defects, and whether your users and your
   organization agree the changes were the right thing to build in the first
   place."
   #+end_quote

   That is a release train, described mechanically and called a pitfall, without
   the name. It *refines* =release-strategies.org='s "DORA never studied release
   trains": DORA never *studied* them — the term is absent from every report —
   but its prescriptive pages name the mechanism and are against it. The mapping
   from "regrouping batches before sending downstream" to "a release train" is
   *this note's inference* [I], not DORA's statement. It points the same way as
   that note's own conclusion: *run it short, or not at all.*

   The same page also supplies a batch-size ceiling: "Any batch of code that
   takes longer than a week to complete and check is too big."

*** DORA's own statement of its ceiling

It is fair to DORA to note that it does not claim what people claim on its
behalf. [E]

#+begin_quote
"While these five metrics provide a vital snapshot of performance, they are
ultimately outcomes. They tell you what is happening, but they don't explain
why."

— 2025 report, v. 2025.2
#+end_quote

And the one place DORA points at the measurement that *would* see our cost — in
the 2025 report's value-stream-management chapter, explicitly outside the five
metrics:

#+begin_quote
"Track key metrics like lead time, process time, and the ratio of *value-add to
wait time*."
#+end_quote

*Ratio of value-add to wait time* is the shape of validations-per-ship. DORA
knows the instrument exists, recommends it as someone else's practice, and keeps
it out of its own five. The nearest thing in the reports themselves is a single
aside in the 2022 security chapter — "avoiding long CI wait times, sometimes
measured in hours" — attached to no metric at all. [E]

*** Verdict

*Tier 5.* DORA is a well-run research programme and is not a standard. Adopt
nothing on its authority. Keep measuring =validations/ship=; it has no standard
name, no published benchmark, and it is the number that moves when the
architecture changes.

** Google SRE — lore, and a better instrument than ours for the same job

*Tier 6 with excellent provenance.* The SRE book is a book: no version, no
conformance test, no normative language. =release-strategies.org= already
handled chapter 8's branch-and-cherry-pick passage and Google's stated reason
for it ("we know the exact contents of each release"); that is not repeated
here. Three things it did not cover:

*** SRE lore prescribes no cadence — it describes a range, in one paragraph

#+begin_quote
"Some teams perform hourly builds and then select the version to actually deploy
to production from the resulting pool of builds. Other teams have adopted a
'Push on Green' release model and deploy every build that passes all tests."

— /Release Engineering/, §High Velocity
#+end_quote

Those are the two ends of the argument =release-strategies.org= spent a whole
file on, offered side by side as equally normal. *Anyone citing "Google SRE
says" for a cadence position is citing half a sentence.* [E]

*** Error budgets are the instrument our §The balance is groping toward

=spec.org= §The balance ends with: "Watch the emergency rate as the health
metric. A rising share of =itil:emergency= is not an incident trend; it is the
queue reporting that it has become too expensive to use honestly."

That is an error budget, invented locally. The SRE version, [E]:

- the budget is "the 'budget' of how much 'unreliability' is remaining for the
  quarter" (ch. 3, §Forming Your Error Budget);
- when it is spent, "releases are temporarily halted while additional resources
  are invested in system testing" (§Release Control);
- and its purpose is that "it provides a common incentive that allows both
  product development and SRE to focus on finding the right balance between
  innovation and reliability".

The difference between the two instruments is the interesting part. *An error
budget gates release velocity on a production outcome. Our berth and our
calendar gate it on a resource.* A resource-gated pipeline has no feedback from
production at all: forfeit twenty windows and the budget is untouched, because
nothing reached production to consume it. So the two instruments are not
alternatives — an error budget cannot price contention, and a berth cannot price
risk. [I] The emergency rate is the only thing in =spec.org= that couples them,
which is why §The balance is right to call it the health metric.

*** Canarying is a formal statement that two versions serve at once

From the SRE Workbook, ch. 16: [E]

#+begin_quote
"We define canarying as a partial and time-limited deployment of a change in a
service and its evaluation."

"The part of the service that receives the change is 'the canary,' and the
remainder of the service is 'the control.'"
#+end_quote

This matters for Part 2 and it is worth flagging here: the most widely
recommended production-safety practice in the SRE canon is *definitionally
incompatible with guard 5 as written*. Guard 5 asserts
=served_build(production) = H(c)=; a canary asserts that the fleet is split, on
purpose, for a defined period. You cannot canary under guard 5. That is not a
criticism of the guard — this repo's artifact is a static site with an atomic
swap — but it is a boundary on the model that should be stated rather than
discovered.

** ITIL 4 — the only vocabulary that separates release from deployment

*Tier 4, paywalled, and more useful to us than its reputation suggests.*

*** The two practices

ITIL 4 split what was, from 1989 to ITIL v3, a single "Release and Deployment
Management" process. The purpose statements, as consistently restated by several
independent secondary sources [E, secondary — the primary practice guides are
paywalled and were not read]:

| Practice | Purpose, as restated | Type |
|----------+----------------------+------|
| Release management | "to make new and changed services and features available for use" | service management practice |
| Deployment management | "to move new or changed hardware, software, documentation, processes, or any other component to live environments. It may also be involved in deploying components to other environments for testing or staging." | technical management practice |

The mechanism that makes the two genuinely come apart is not an ITIL invention
and is better cited from engineering literature. Pete Hodgson, 2017-10-09 [E]:

#+begin_quote
"Release Toggles allow incomplete and un-tested codepaths to be shipped to
production as latent code which may never be turned on."
#+end_quote

*** The finding: we have no release-management guard

Map the six guards onto the two practices and the result is lopsided.

| Guard | Asks | ITIL practice |
|-------+------+---------------|
| 0 =B(c) = T= | is this tree current? | deployment management |
| 1 berth singleton | is the path free? | deployment management |
| 2 gates green on =H(c)= | is this content verified? | deployment management (service validation and testing) |
| 4 =staged(H(c))= | did it survive a lower environment? | deployment management |
| 4b divergence class | is what I verified still what I ship? | deployment management |
| 5 =served_build = H(c)= | is it running? | deployment management |

*All six are deployment-management guards. There is no release-management guard
in the model at all.* Nothing in the six asks whether a feature is *meant to be
available to users*, and the spec has no vocabulary for a toggle. That is a
defensible scope choice — ADR-0001 makes the same one explicitly ("It is
deliberately not about the activated deployment itself") — but it should be
stated, because the model's own ITIL 4 vocabulary table
(=spec.org= §Vocabulary) defines "Release" as "A production deployment whose PIR
comment is posted", which is *deployment management wearing release
management's name*.

*** Where ITIL and DORA talk past each other

| | ITIL 4 | DORA |
|--+--------+------|
| Unit of interest | the *change record* — a unit of intent, with an outcome | the *deployment* — an event that reached production |
| Release vs deployment | constitutive; two practices | collapsed; "deployed in production" terminates every metric |
| A change schedule | a control, and a deliverable of the practice | never named; a code freeze is the one adjacent thing measured, negatively, in 2016–2017 only |
| A forfeited window | *recordable* — a change record has an outcome and a schedule has a booking | *invisible* — not a deployment, not an event |
| Success | authorized, controlled, recorded, reviewed | frequent, fast, low-failure, fast-recovering |

The surprise is the fourth row. *The paperwork framework is better instrumented
for this repo's dominant cost than the measurement framework is.* ITIL's change
record is a first-class object with an outcome field; a forfeit is a legitimate
outcome of a change record. DORA has no object that a forfeit could be an
instance of.

That is not an argument for ITIL. ITIL gives us a *place to write the number
down* and no way to compute it, and none of its practices would tell you that
the number is 13.63. It is an argument for noticing that neither framework is
the one we need, and that =validations/ship= is ours.

*** ISO/IEC 20000-1:2018

ISO/IEC 20000-1:2018 is the tier-1 standard in this space and its clause 8.5.3
is titled "Release and deployment management". [E, secondary — the standard is
paywalled; ISO's own online browsing platform returned 403 and no clause text
was read.] Its content is process requirements — define release types, plan,
verify, record — at a level of abstraction that says nothing about any question
in this file. *It is a real standard that does not cover our case*, which is
worth recording precisely because it is the one thing here that is certifiable.
[H] on any claim about what the clause actually requires.

** Provenance — the strongest real standard here, and it stops at the registry

This is the part of the space that *is* genuinely standardised, and it is the
part that maps onto =spec.org='s sharpest sentence:

#+begin_quote
"deployment record is attested, not self-reported. The difference is who says it
happened: the platform, or the job that wanted it to."
#+end_quote

The question this section answers: *does SLSA give a standard vocabulary for
that?* The answer is *no, and it says so*, in a way that is more useful than a
yes would have been.

*** SLSA, corrected: v1.2, two tracks, three build levels, no deployment

Several things commonly repeated about SLSA are out of date. [E]

| Common belief | Actual |
|---------------+--------|
| SLSA is at v1.0 (2023) | *v1.2*, approved 2025-11-24 |
| Levels are L1–L4 | *Build L0–L3.* L4 exists only on the =future-directions= page: "A build L4 *could* include further hardening…" |
| There is one ladder | *Tracks.* v1.2 has Build and Source; the working draft adds Build Environment and Dependency |
| SLSA covers the supply chain end to end | It covers *build* and, since v1.2, *source* |

The build levels, verbatim from =slsa.dev/spec/v1.2/build-track-basics=:

| Level | Summary, verbatim |
|-------+-------------------|
| Build L0 | "No requirements—L0 represents the lack of SLSA." |
| Build L1 | "Package has provenance showing how it was built. Can be used to prevent mistakes but is trivial to bypass or forge." |
| Build L2 | "Forging the provenance or evading verification requires an explicit 'attack'… In practice, this means that builds run on a hosted platform that generates and signs the provenance." |
| Build L3 | "Forging the provenance or evading verification requires exploiting a vulnerability that is beyond the capabilities of most adversaries." |

*** SLSA explicitly does not cover deployment, and once voted on the word

Three pieces of evidence, in increasing order of how decisive they are. [E]

1. *No track.* =slsa.dev/spec/v1.2/tracks= lists exactly two, Build and Source.
   The working draft adds Build Environment ("the compute environment executing
   builds") and Dependency. =future-directions= names Build L4 and a "Platform
   Operations track" — the latter about hardening the *build and source
   platforms*, not about deploying. No issue proposing a deployment track exists
   in =slsa-framework/slsa=.

2. *The threat model terminates before deployment.* The chain runs
   A (producer) → … → G (distribution channel) → H (package selection) →
   *I (usage)*, and row (I) reads, in full:

   #+begin_quote
   "I — Usage — /Default credentials: Attacker could leverage default
   credentials to access sensitive data./ — *SLSA does not address this
   threat.*"
   #+end_quote

3. *The project removed the word on purpose.* Issue =slsa-framework/slsa#38=,
   "Proposal: Switch Wording from 'Deployment' to 'Publish'", opened 2021-05-28,
   closed 2021-06-01. Body, complete:

   #+begin_quote
   "Given this is centered on artifacts, I think the term 'publish' is more
   commonly used. In my mental model:
   Deployment == fetching an artifact and running it.
   Publish == building an artifact and making it available."
   #+end_quote

   The proposal carried. SLSA's terminology page has *Package*, *Package
   registry*, *Publish*, *Distribution platform* — and no term at all for an
   environment in the deployment sense.

*This is the cleanest answer in the whole file.* SLSA is the strongest standard
in the space and it ends exactly one step before where guard 4 and guard 5 live.

*** What SLSA does give us

Two things, both useful and neither a deployment record.

*C2, made rigorous.* The in-toto Statement's =subject= is the formal version of
"a verdict bound to a content hash":

#+begin_quote
"Set of software artifacts that the attestation applies to… Each element MUST
have =digest= set. Subjects are assumed to be *immutable*… IMPORTANT: Subject
artifacts are matched purely by digest, regardless of content type."

— =in-toto/attestation/spec/v1/statement.md=
#+end_quote

*The attested/self-reported distinction, under a different name.* SLSA's
provenance splits the build's inputs into two classes on exactly our axis:

#+begin_quote
"*externalParameters*: the external interface to the build. In SLSA, these
values are *untrusted*; they MUST be included in the provenance and MUST be
verified downstream.
*internalParameters*: set internally by the platform. In SLSA, these values are
*trusted because the platform is trusted*."
#+end_quote

That is our distinction — who says it, the platform or the party that wanted it
— applied to *build inputs* rather than to deployment outcomes. It is a
vocabulary we can borrow even though the object it describes is not ours. [I]

And =builder.id=: "URI indicating the transitive closure of the trusted build
platform. This is intended to be the sole determiner of the SLSA Build level" —
with "Consumers MUST accept only specific signer-builder pairs." That is
=ci-portability.org='s C9 (gate-authority separation) stated as a normative
requirement by a standards body. Worth knowing, since C9 is one of the two
capabilities that note found absent on both platforms we use.

*** in-toto: the registry pattern is ours, the object is not

in-toto is CNCF *Graduated* (2025-02-10) [E], and its own scope statement is the
only one in this space that says the word:

#+begin_quote
"in-toto attests to the integrity and verifiability of all the actions performed
while writing code, compiling, testing, and *deploying* software."

— /in-toto Specification/ v1.0.0, §1.1 Scope
#+end_quote

But the mechanism does not deliver it. Every in-toto assertion binds
*artifact → artifact* (=expected_materials= → =expected_products=), verified at
install time against a final product bundle. *There is no environment field
anywhere in the model*, and the vetted predicate registry —
=cyclonedx, link, provenance, reference, release, runtime-trace, scai, spdx2,
spdx3, svr, test-result, vsa, vulns= — contains *no deployment predicate*. [E]
=runtime-trace= is about build processes: "The primary use case driving the
development of this predicate is its applicability to runtime traces of build
processes."

The =release= predicate is the near miss, and it is instructive because *the
pattern is exactly ours and the object is publication*:

#+begin_quote
"*Purpose* — To authoritatively link from a specific release name and version
string in a package registry, to the artifact names and hashes that make up that
release."

"Note that while npm calls this a publish attestation, calling it a release
attestation better reflects that *it's coming from the package registry*.
Publishing often refers to an author sending content to the registry…"
#+end_quote

That parenthesis is =spec.org='s sentence in someone else's words: the registry
attesting beats the publisher asserting. The standards community solved our
problem, for packages, and did not solve it for environments.

*** SBOM formats: real standards, and the one that names an operations phase

| Format | Institutional status | Covers a deployment? |
|--------+----------------------+----------------------|
| SPDX | *ISO/IEC 5962:2021*, first edition 2021-08 — but that standard covers *SPDX 2.2.1 only*. The current spec is 3.0.1 (2024-12-17), with 3.1-RC1; *not* ISO-ratified [E] | No. =LifecycleScopeType= has =runtime=, qualifying a /relationship/, and the only deployment-adjacent relationship is =hasHost= — about the *build* host |
| CycloneDX | *ECMA-424*, 2nd edition December 2025 = CycloneDX v1.7 (1st edition June 2024 = v1.6), TC54 [E] | *Closest of any standard.* See below |

CycloneDX's =metadata.lifecycles.phase= enumerates
=design, pre-build, build, post-build, operations, discovery, decommission=, and
=operations= reads: [E]

#+begin_quote
"BOM produced that represents inventory that is running and operational. *This
may include staging or production environments* and will generally encompass
multiple SBOMs describing the applications and operating system…"
#+end_quote

And =formulation=:

#+begin_quote
"Describes the formulation of any referencable object within the BOM… This may
encompass how the object was created, assembled, *deployed*, tested, certified…
Common examples include software build pipelines, *deployment processes*… 
Processes are modeled using *declared and observed formulas*."
#+end_quote

*"Declared and observed formulas" is the closest thing in any ratified standard
to our intent-versus-evidence distinction*, and CycloneDX explicitly names
deployment processes as in scope for it. [E] That is a genuinely useful find and
it is the one place a tier-1 standard touches our argument.

It is still not a deployment record: =operations= annotates *the document* ("this
BOM was captured from a running system"), not an event, and it names no
environment and no time.

*** CDEvents — the only standard vocabulary for "X is deployed to Y", and it is unsigned

CDEvents is a Continuous Delivery Foundation *incubating* project at v0.5.1
(2026-04-15) — pre-1.0, and not a formal standard [E]. Its opening sentence is
nevertheless the thing this whole section was looking for:

#+begin_quote
"Continuous Deployment (CD) events are related to continuous deployment
pipelines and their target environments. *These events can be emitted by
environments to report where software artifacts such as services, binaries,
daemons, jobs or embedded software are running.*"

— =cdevents/spec= v0.5.1, =continuous-deployment.md=
#+end_quote

*The environment is the reporter.* That is C6 stated by a spec. The taxonomy:

| Subject | Predicates |
|---------+------------|
| =environment= | =created=, =modified=, =deleted= |
| =service= | =deployed=, =upgraded=, =rolledback=, =removed=, =published= |

=dev.cdevents.service.deployed.0.3.0= requires =id=, =environment=, and
=artifactId= — the last a *purl*, e.g.
=pkg:oci/myapp@sha256%3A0b31…=. So the tuple (artifact digest, environment,
event) is fully specified, and =service.rolledback= and =service.upgraded= exist
as first-class events. [E]

*And it has no authenticity model at all.* A full-text search of the v0.5.1
spec for =sign|attest|authentic|trust|non-repud|integrity= returns nothing
relevant; =source= is a self-declared URI-reference whose stated purpose is
"to provide global uniqueness", not authentication. [E]

*Signed attestations stop at the registry; deployment events reach the
environment but carry no signature. Nobody has bridged them* — there is no

So the answer to "does SLSA's provenance model give a standard vocabulary for
what our deployment record is?" is: *it gives a vocabulary for everything up to
the moment our model starts, and names the boundary explicitly.* Our C6 is, as
of today, unstandardised — which is worth knowing, because it means the
attested/self-reported argument in =spec.org= is not borrowed from anywhere and
must stand on its own.

** Two specs nobody reaches for, that fit our gaps better than the ones we do

*** OpenTelemetry semantic conventions — the standard nouns for "which build is serving"

Guard 5 compares *one* sampled =x-build-sha= against *one* expected value.
=release-strategies.org= §Guard 5 is false by construction during a roll already
established that this is the wrong shape for a fleet. What it did not have is
that *the right shape is standardised and stable*. [E]

| Attribute | Requirement level | Stability | Definition, verbatim |
|-----------+-------------------+-----------+----------------------|
| =service.name= | Required | Stable | "Logical name of the service." |
| =service.version= | Recommended | Stable | "The version string of the service component. The format is not defined by these conventions." Examples: =2.0.0=; =a01dbef8a= |
| =service.instance.id= | Required | Stable | "The string ID of the service instance." + "The ID helps to distinguish instances of the same service that exist at the same time (e.g. instances of a horizontally scaled service)." |
| =deployment.environment.name= | — | Stable | "Name of the deployment environment (aka deployment tier)." Well-known values: =development=, =production=, =staging=, =test= |

Note =service.version='s examples: a semver *and a git sha*. The convention
anticipates exactly our identifier.

The restatement guard 5 needs under a rolling deploy, in standardised nouns
rather than invented ones: [I]

: during the roll:  { service.version : instances of service.name in deployment.environment.name="production" } ⊆ {prev, H(c)}
: after deadline D: that set = { H(c) }

*The set-valued form is what the standard is built for and what guard 5 cannot
express.* =service.instance.id= exists precisely because several versions of one
service run at once.

One honest caveat, and it matters: *OTel is telemetry.* The process reports its
own =service.version=. That is C1/C8-grade evidence — a self-report by the thing
under test — not C6-grade attestation. Adopting the vocabulary does not upgrade
the evidence. [I]

*** OSV — revoking a verdict on an artifact you cannot recall

The OSV Schema is at v1.9.0 (2026-08-06), adopted by OSS-Fuzz, the GitHub
Advisory Database, the PyPI advisory database, RustSec and the Go vulnerability
database. Its stated purpose: "define a standard interchange format for
describing vulnerabilities in open source packages." An entry's =affected= names
=versions= and =ranges= (=SEMVER=, =ECOSYSTEM=, =GIT=); "A version is considered
affected if it lies within any one of the ranges or is listed in the versions
list." There is a =withdrawn= timestamp for retracting the entry itself. [E]

Read structurally rather than as a security tool, *OSV is C5 — "verdicts that
are revocable after issue" — standardised, for a world where rollback does not
exist.* =spec.org= says "if it gives you two, take C2 and C5. A verdict you
cannot revoke is a verdict that outlives its own truth." The package ecosystems
took exactly that advice, because it is the only advice available to them: you
cannot un-publish (§Part 2), so the only remediation is a signed, machine-
readable statement that a version range is bad. [I]

** GitHub in particular

=ci-portability.org= covered whether GitHub *provides* the capabilities. This
section asks the narrower question the prompt poses: *what do a GitHub Release
and a GitHub Deployment actually attest?*

*** A Release is a record of intent, with one 2025 exception

By default a Release is *mutable and late-bound*: [E]

- "Releases are based on Git tags, which mark a specific point in your
  repository's history. A tag date may be different than a release date since
  they can be created at different times."
- The stored fields are =tag_name= (a string) and =target_commitish= — *not a
  pinned commit sha*. =target_commitish= is "Unused if the Git tag already
  exists." So =tag_name= → commit is a lookup performed later, and the tag can
  move.
- "Repository collaborators and people with write access to a repository can
  create, edit, and delete a release." =PATCH= and =DELETE= exist for the
  release and for every asset.
- The release response schema contains *no* deployment, environment or "live"
  field. A release says these bytes exist under this name. It says nothing about
  anything running.
- =generate_release_notes= draws on "a list of merged pull requests, a list of
  contributors to the release", filtered by PR labels via =.github/release.yml=.
  *It is a record of what was merged, not of what was built or tested*, and
  "The generated release notes are not saved anywhere" — they are a snapshot
  pasted into a mutable =body=.

So: *a default GitHub Release is intent.* It is the same object class as "on
main" in =release-strategies.org= §Intent is not evidence — a statement by the
party that wanted it to be true, which can be edited afterwards.

*The exception, and it is a real one.* Immutable releases went to public preview
2025-08-26 and *GA 2025-10-28*: [E]

#+begin_quote
"Immutable releases are releases where the assets and associated Git tag cannot
be changed after publication."

"*Git tags cannot be moved*: Once an immutable release is published, its
associated Git tag is locked to a specific commit, cannot be changed, and cannot
be deleted while the release exists."

"Additionally, creating an immutable release automatically generates a *release
attestation*, which is a cryptographically verifiable record of a release
containing the release tag, commit SHA, and release assets."
#+end_quote

*That is evidence, not intent* — platform-generated, Sigstore-signed, and it
binds tag ↔ sha ↔ assets. It is the only platform-attested sha binding GitHub
offers. Three limits worth recording: only assets and the tag are locked (title,
notes and the prerelease flag stay editable); existing releases stay mutable
until republished; and the auto-generated source tarball is *not* a stored
immutable asset — "these assets are only created when a download is requested",
so =gh release verify-asset= cannot verify it.

*** A Deployment is self-reported, and GitHub says so outright

This is the crisp one, and it retroactively justifies =spec.org='s insistence on
the word "attested". [E]

#+begin_quote
"Deployments are requests to deploy a specific ref (branch, SHA, tag)."

"Deployment statuses allow *external services* to mark deployments with an
=error=, =failure=, =pending=, =in_progress=, =queued=, or =success= state…"

"*Keep in mind that GitHub is never actually accessing your servers.* It's up to
your third-party integration to interact with deployment events."

"*Users with =push= access can create deployment statuses* for a given
deployment."

— =docs.github.com/en/rest/deployments/{deployments,statuses}=
#+end_quote

And when a workflow uses =environment:=, GitHub creates the objects but the
*claim* is still the job's:

#+begin_quote
"When a workflow job that references an environment runs, it creates a
deployment object… As the workflow progresses, it also creates deployment status
objects… and *the =state= property set to the status of the job*."
#+end_quote

=state= mirrors *the deploy script's exit code*, not the target's condition.
Note also =deployment: false= in workflow syntax, which uses an environment's
secrets "without creating a deployment object" at all.

*What /is/ platform-enforced is permission to attempt, not the result:*

#+begin_quote
"All deployment protection rules must pass before a job referencing the
environment is sent to a runner."
#+end_quote

Required reviewers (up to six, with an optional no-self-review setting), wait
timer (1–43,200 minutes), deployment branch/tag policies matched against
=GITHUB_REF=, and GitHub-App-based *custom deployment protection rules* (public
preview; max six enabled per environment) — these are real. =spec.org= §On an
enterprise account is right that custom deployment protection rules are "the
native home for guard 4b": they are the one hook where an external system can
refuse the runner.

*One trap worth recording*, because it is load-bearing for "which one is live":
=auto_inactive= is documented as applying to "all prior non-transient,
*non-production* environment deployments", and =production_environment= defaults
to =true= when =environment= is =production=. On a literal reading, *the
auto-inactive bookkeeping does not apply to production*. [H] — the docs say it;
whether the implementation matches was not tested, and it should be before any
audit relies on "the active production deployment".

*Summarised against our own vocabulary:*

| Object | Who asserts | Our classification |
|--------+-------------+--------------------|
| Release (default) | anyone with write access, editable forever | *intent*, C1-grade |
| Release (immutable, GA 2025-10-28) | GitHub, Sigstore-signed | *evidence* about the package |
| Artifact attestation | Sigstore, via workflow OIDC | *evidence* about the build. "Artifact attestations by itself provides SLSA v1.0 Build Level 2"; L3 via reusable workflows |
| Deployment + status | the job, or any token holder | *intent wearing evidence's name* |
| Deployment protection rule | GitHub | *evidence* that permission was granted — not that anything shipped |
| =Environment.latestCompletedDeployment= (GraphQL) | derived from the above | "The latest completed deployment with status success, failure, or error" — most recent *attempt that finished*, not what is serving |

GitHub's own warning on attestations deserves quoting because it is the same
epistemics as this repo's: "It is important to remember that artifact
attestations are *not a guarantee that an artifact is secure*. Instead, artifact
attestations link you to the source code and the build instructions that
produced them."

*The conclusion for guard 4.* =spec.org= lists the deployment record as
"platform-attested statement that artifact X reached environment Y | the
Deployments API". *That mapping is wrong as stated* [E]: the Deployments API is
a place where a job writes down its own opinion, gated by protection rules that
GitHub does enforce. Guard 4 leans on C6 and GitHub does not supply C6 for
deployments — it supplies C6 for *releases*, since October 2025, and enforcement
of *entry* to a deployment. That is not a reason to abandon guard 4; it is a
reason to stop describing the Deployments API as attestation, and it is why
guard 5 — reading the answer back out of the running system — has no bypass.

* Part 2 — deployment semantics by artifact type

** The assumption, stated so it can be tested

The claim under test, as these notes were asked to state it: *our model is
implicitly a single-live-version model, and guards 4b and 5 are the ones that
break first when that assumption goes.* The first half is right, and it is worth
decomposing before testing the second, because the six guards do not all rest on
the same part of it. Five axioms, none of them written down in =spec.org=:

| # | Axiom | Which guards rest on it |
|---+-------+-------------------------|
| *A1* | There is exactly *one production surface*, and holding it is exclusive | guard 1 |
| *A2* | At any instant *exactly one build* is served from it | guard 5 |
| *A3* | Everything that ships, ships *together, from one trunk* | guards 0, 4b |
| *A4* | Deployment is *instantaneous* relative to the guard's evaluation | guard 5 ("after deploy"), guard 1's 30-minute quantum |
| *A5* | Deployment is *undoable* by redeploying the previous build | the rollback sha; =non_fast_forward= + =deletion= |

=spec.org= §What this model gets wrong, on purpose is candid that A1 is an
architectural defect being simulated rather than endorsed. *A2, A4 and A5 are
not mentioned anywhere*, and A5 is the one that costs most when it fails.

The four shapes, drawn by what "the deployed version" denotes:

** 1 — Libraries and packages

*** What the ecosystems actually guarantee

Every major registry has converged on the same contract, and it is the *opposite*
of ours: the artifact is immutable and the adoption decision belongs to the
consumer. [E]

| Registry | Immutability, verbatim | Un-ship? |
|----------+------------------------+----------|
| SemVer §3 | "Once a versioned package has been released, the contents of that version MUST NOT be modified. Any modifications MUST be released as a new version." | n/a |
| npm | "Registry data is immutable, meaning once published, a package cannot change." Unpublish only within 72 h, with no dependents; otherwise "we recommend deprecating the package. This allows the package to be downloaded but publishes a clear warning message." | barely |
| PyPI | "PyPI does not allow for a filename to be reused, even once a project has been deleted and recreated." Deletion "is permanent and irreversible, without exception." Yanking: "always ignored by an installer, unless it is the only release that matches a version specifier" | no |
| Maven Central | "Once a component has been released and published to the Central Repository, it cannot be altered." | no |
| crates.io | =cargo yank= "does not delete any data, and the crate will still be available for download via the registry's download link." "Existing lock files or direct downloads are not affected" | no |

*Rollback does not exist in this world, and the ecosystems know it.* Yank and
deprecate are *hints to a resolver*, not recalls, and they do not reach a
consumer with a lockfile. That is why OSV exists (§Part 1): when you cannot
un-ship, the only remediation is a machine-readable revocation of the verdict.

*** Guard by guard

| Guard | Status | Why |
|-------+--------+-----|
| *0* =B(c) = T= | *restated as policy, not safety* | Nothing forces a release off the trunk tip. Google SRE branches at a revision on purpose. Guard 0 becomes a choice about which line you are cutting from |
| *1* berth singleton | *vacuous* | There is no shared surface to hold. The registry enforces a *uniqueness constraint on (name, version)* instead — strictly stronger, and free. npm: "If you've ever published a package called 'bob' at version 1.1.0, no other package can ever be published with that name at that version. This is true even if that package is unpublished." |
| *2* gates green on =H(c)= | *meaningful, and it is the whole thing* | There is no staging to catch it later and no rollback to undo it. C2 carries all the weight |
| *4* =staged(H(c))= | *survives, as a registry primitive* | Maven Central's Publisher Portal has a literal state machine: =PENDING → VALIDATING → VALIDATED → PUBLISHING → PUBLISHED=, where "VALIDATED: A deployment has passed validation and is waiting on a user to manually publish". =VALIDATED= *is* =staged(H(c))=, and =DELETE= drops it. npm =dist-tags= and PEP 440 pre-releases are the softer form |
| *4b* divergence class | *survives literally, with the subject restated* | See below |
| *5* =served_build = H(c)= | *vacuous as an observation; survives as provenance* | There is no server to ask. The purpose — "the thing we authorized is the thing being used" — becomes "the published digest equals the digest we gated", which is exactly the in-toto =release= predicate |

*** Guard 4b is not vacuous here, and this is where the claim needs correcting

The tempting reading is that with no shared production surface there is nothing
for guard 4b to protect. That is wrong, and the counterexample is the oldest bug
in release management:

#+begin_example
main:  ... --- A --- B ---[hotfix H]--- C ...
                 \
release branch:   \--- cut at A --- publish 1.3.0
#+end_example

=1.3.0= is published from a base predating =H=. Every consumer who upgrades from
=1.2.4= (which contained =H=) *loses the hotfix*. That is guard 4b's predicate,
unmodified: =∀m ∈ merges(B(c), T) : class(m) ∈ {inert, pipeline}=, with
=class(H) = hotfix=. The failure mode is identical to scenario D4. What differs
is the recovery:

- on a shared surface, you redeploy and it is over in minutes;
- in a registry, *the bad version is permanent*, the regression propagates on
  each consumer's own upgrade schedule, and the remediation is a new version
  plus an advisory that the consumer may never read.

*Guard 4b is not weaker for libraries. It is stronger, because it is the last
chance.* [I]

The *restatement* it needs is about its subject. Guard 4b compares the base
against =T=, the trunk tip. A library maintaining a =1.x= line while =2.x= is on
main has =B(c)= deliberately and permanently behind =T=, and guard 4b as written
would fire forever. The correct subject is *the tip of the line being released
from*, not the trunk tip: [I]

: 4b' | ∀m ∈ merges(B(c), tip(line(c))) : class(m) ∈ {inert, pipeline}

For this repo =line(c) = main= and 4b' collapses to 4b, which is why the
distinction has never come up. It is the same generalisation
=release-strategies.org= needed for the train (the subject moved from N changes
to one merge commit): *guard 4b's predicate is stable and its subject is the
thing that varies by shape.*

*** Which axioms fail

*A1, A2 and A5.* There is no surface; "the deployed version" is a set of size N
chosen by consumers; and nothing can be undone. A3 holds only within a line.
A4 holds trivially — publishing is atomic from the publisher's side and
irrelevant from the consumer's, since adoption is their event and not ours.

** 2 — Sites and SPAs where =main= is production

This is our shape, and all six guards mean something. The interesting part is
that *even here A2 is only approximately true.*

The reference implementation of the axioms is Netlify, which sells them by
name [E]:

- atomic deploy: "Make updates available only when they are complete and totally
  in place." (A4)
- immutable deploy: "Guarantee the integrity of previous deploys by insulating
  them from future actions." (A5 — rollback is a pointer swap because the old
  artifact was never destroyed)

Two leaks that guard 5 cannot see, both [I]:

1. *The CDN holds a version.* Guard 5 issues one request per route. An edge with
   a live TTL can answer from cache, so a green guard 5 is consistent with part
   of the world still being served the old bytes. §GitHub Pages below makes this
   concrete with a measured =max-age=600=.
2. *The client holds a version.* An SPA's running code is in browsers that
   loaded it minutes or hours ago. =served_build(production) = H(c)= is a
   statement about *the origin*, and the field is running =H(c-1)= against an
   API that just changed. This is the same shape as the rolling-deploy problem
   (§3) with the old replicas living in users' tabs instead of in a cluster —
   and unlike replicas, *you cannot drain them.*

So the honest restatement for this shape: *A2 is a property of the origin, not
of the system.* Guard 5 is correct about what it measures and the model should
not claim more. A site whose front end and API ship together — which is this
repo's monorepo shape — has a window in which an old bundle talks to a new
backend, and nothing in the six guards mentions it. [I]

** 3 — Long-lived services with rolling deploys

=release-strategies.org= §Services deployed continuously over time already
restated guard 5 for a roll, gave C6 a convergence interval, and found guard 4b
needs a third evaluation point. *That is not repeated here.* Three things it did
not have:

*** The overlap is the default configuration, not an edge case

Kubernetes =RollingUpdateDeployment=, verbatim: =maxSurge= "Defaults to 25%…
the total number of old and new pods do not exceed 130% of desired pods";
=maxUnavailable= "Defaults to 25%… the old ReplicaSet can be scaled down to 70%
of desired pods immediately when the rolling update starts." [E]

And the SRE canon's most-recommended safety practice *requires* the overlap:
"We define canarying as a partial and time-limited deployment of a change in a
service and its evaluation… The part of the service that receives the change is
'the canary,' and the remainder of the service is 'the control.'" [E]

*Two versions serving simultaneously is not a transient to be tolerated; it is
the design, and in one case it is the safety mechanism.* Guard 5 as written
forbids the thing the industry does to be safe. That is a boundary on the model,
not an error in it — but it should be stated in =spec.org= rather than
discovered by whoever first tries to canary.

*** Cloudflare Workers models it correctly and GitHub does not

The two targets =spec.org= §Targets names diverge here, and the divergence is
in the platform's *data model*, not its features. [E]

| | Model of "what is deployed" |
|--+-----------------------------|
| Cloudflare Workers | "A deployment determines which *version(s)* of your Worker are actively serving traffic." "A deployment can reference one version (serving 100% of traffic) or *two versions* (with traffic split between them during a gradual deployment)." |
| GitHub Deployments | one deployment object per request; =auto_inactive= marks prior ones inactive so that exactly one is =ACTIVE= per environment; GraphQL offers =Environment.latestCompletedDeployment=, singular |

*GitHub's deployment model has A2 baked into it.* There is no schema position
for "these two shas are both serving, 90/10". Cloudflare's has one. A port of
this model to a rolling-deploy target on GitHub would have to represent the
convergence interval *outside* the deployment record, which is the point at
which the record stops being the source of truth. [I]

*** A5 is the axiom that actually breaks, and nothing in the model mentions state

The repo protects the rollback target at the *git* layer: =non_fast_forward= and
=deletion= ruleset rules, whose stated purpose is "the recorded production SHA
stays reachable". That is necessary and it is not sufficient, in two ways:

1. *The artifact is not the sha.* Kubernetes =revisionHistoryLimit= is "The
   number of old ReplicaSets to retain to allow rollback… Defaults to 10." [E]
   Past that depth the rollback target is garbage-collected — the commit is
   reachable and the built thing is gone. GitHub Pages is worse: the artifact
   that =deploy-pages= consumes has =retention-days= defaulting to *1* [E].
   *Git reachability is not artifact reachability.*
2. *State is one-way.* The standard zero-downtime schema technique is
   ParallelChange / expand-and-contract — "a pattern to implement
   backward-incompatible changes to an interface in a safe manner, by breaking
   the change into three distinct phases: expand, migrate, and contract" [E].
   After the contract phase, redeploying the previous sha produces *a tree that
   was never validated against the current schema.* It is a new, untested change
   created during an incident, which =release-strategies.org= already identified
   as the worst possible moment to be creating untested trees — there for
   batching, here for state.

*Nothing in the six guards has a state dimension.* Guard 2 verifies a content
hash; guard 4 verifies that hash survived staging; guard 5 verifies that hash is
serving. There is no predicate over the schema the hash expects. For a static
site that is correct and free. For any stateful service it is the largest gap in
the model, and it is larger than anything guard 4b covers. [I]

*** And guard 1's arithmetic changes

ADR-0001 quantizes the change schedule at 30 minutes — "48 slots per day per
berth". A rolling deploy plus a canary bake period holds the path to production
for *hours*, not for one quantum. The ceiling ADR-0001 computes is therefore a
ceiling for atomic-swap artifacts, and re-deriving it for a rolling target would
move every number in that ADR. [I] Not a defect; a scope statement the ADR does
not make.

** 4 — GitHub Pages, specifically

The repo's =targets/github= uses Pages. Four findings, one of which refutes a
sentence in =spec.org=.

*** Guard 5 is unimplementable as written on this target [E]

=spec.org= §Targets: "Both targets must emit =x-build-sha= on every response, or
guard 5 cannot distinguish a fresh deploy from a stale one." And
=ci-portability.org= C8: "the app must emit its build SHA, and *the target must
preserve the header*."

*GitHub Pages cannot set custom response headers.* GitHub staff (Yoann Chaudet),
on the community discussion "HTTP Headers (e.g. Content-Security-Policy) on
Pages", 2023-05-02: "We don't support this feature today so a =meta= tag
unfortunately is the only way." Re-asked 2024-07-10: "This is not an area that
is being prioritized at the moment unfortunately." A live =curl -sSI= against a
Pages origin on 2026-09-13 returns a fixed header set (=server=, =cache-control=,
=expires=, =access-control-allow-origin=, Fastly =via=/=x-served-by=/=x-cache=)
with no injection point. The Pages REST API's site-configuration parameters cover
source, build type, CNAME and HTTPS enforcement — nothing about headers.

*This is a documented absence, which is the one thing a vendor doc is
authoritative about*, corroborated empirically. It is [E], and it means the
=github= target as specified cannot satisfy guard 5.

*The fix that keeps the guard*, and its cost: serve the build sha *as content* —
=/_build.json=, or a =<meta name="build-sha">= — and have =gates/health.sh=
fetch and compare it. This is implementable today. It is weaker in one specific
way and the weakness should be written down: *a header is emitted by the serving
layer per response; a file is content, and content is cacheable.* A stale edge
returns a stale stamp at precisely the moment guard 5 exists to catch a stale
deploy. Cache-busting the stamp request (a query string, =Cache-Control:
no-cache= on the request) mitigates but does not eliminate this. [I]

*** The Pages deployment record attests serving, not provenance [E]

There *is* a Pages deployments API — =POST /repos/{owner}/{repo}/pages/deployments=
— and it is meaningfully better than a generic deployment status, because GitHub
actually serves the bytes and validates the caller:

- =oidc_token= is *required*: "The OIDC token issued by GitHub Actions certifying
  the origin of the deployment", decoded server-side to check the ref claim
  against branch protection.
- =GET …/pages/deployments/{id}= returns a status; =POST …/cancel= exists.

But =pages_build_version= is *required and caller-supplied*: "A unique string
that represents the version of the build for this deployment. Default:
=GITHUB_SHA=." *Nothing verifies that the uploaded artifact was built from that
sha.*

So the record attests two different things with different strength, and the
distinction is exactly =spec.org='s:

| Claim | Who attests |
|-------+-------------|
| "this artifact is now the one Pages serves" | *GitHub* — it does the serving |
| "this artifact was built from sha X" | *the caller* — a string in a request body |

That is a genuinely useful, genuinely partial C6. Guard 4's "artifact X reached
environment Y" is attested; the identity of X is not. Which is another reason
guard 5 — reading the sha back out of the served bytes — is the guard with no
bypass.

*** Rollback: there is no primitive [E]

The Pages REST surface is: get/create/update/delete a site; list builds; request
a build; get latest build; get a build; *create* a deployment; get a deployment's
status; *cancel* a deployment; DNS health check. There is no list-deployments, no
activate-previous, no promote, no rollback. GitHub's own guidance:

#+begin_quote
"Unpublishing your GitHub Pages site removes your current deployment. To make
your site available again, *you can create a new deployment.*"
#+end_quote

In principle one could re-=POST= an older =artifact_id=; in practice
=actions/upload-pages-artifact= defaults =retention-days= to *1*, so yesterday's
artifact is gone. *Rollback on Pages is "re-run the workflow at the old commit",
which is a build, not a pointer swap.* Contrast Netlify's immutable deploys,
where rollback is a pointer swap precisely because the old artifact still exists.

The consequence for =spec.org= §Health check and release is concrete: "On =rc=7=:
roll back to the previous production SHA from the deployment record" assumes a
rollback that takes seconds. On Pages it takes a build — and it takes a build
*while production is unhealthy*, with a documented 10-minute deployment timeout.
=targets/github/rollback.sh= is specified but not written; when it is, this is
the thing it has to confront. [I]

*** Limits, and one limit that does /not/ bind

[E] "Published GitHub Pages sites may be no larger than 1 GB." "GitHub Pages
deployments will timeout if they take longer than 10 minutes." "…a soft
bandwidth limit of 100 GB per month." "…a soft limit of 10 builds per hour."

*The builds-per-hour limit does not apply to us*, and it is worth recording that
it does not, because it is the obvious thing to worry about: "This limit does not
apply if you build and publish your site with a custom GitHub Actions workflow" —
which is what =targets/github= does. The binding constraint is the *10-minute
deployment timeout*, which bounds a single deploy and therefore a berth hold.

And the CDN: the measured =cache-control: max-age=600= means "deployment
succeeded" and "every visitor sees the new bytes" are *separate events up to ten
minutes apart*. GitHub documents no atomicity guarantee and no cache-invalidation
semantics for the Pages swap; that silence is [H], not a promise either way.

** Verdict on the claim

*** Axiom by shape

| Axiom | Library | SPA / site | Rolling service | GitHub Pages |
|-------+---------+------------+-----------------+--------------|
| *A1* one surface | *fails* — no surface | holds | holds | holds |
| *A2* one live build | *fails* — N adopted versions | *approximate* — origin yes, CDN and clients no | *fails by design* — maxSurge 25%, canary | approximate; CDN lag ~10 min |
| *A3* one trunk | holds within a line | holds | holds | holds |
| *A4* atomic | trivially | *approximate* | *fails* — the roll is the window | *unknown* [H]; not documented |
| *A5* undoable | *fails absolutely* | holds, if the artifact is kept | *fails* after a contract-phase migration | *fails as a primitive* — rollback is a rebuild |

*** Guard by shape

| Guard | Library | SPA / site | Rolling service | GitHub Pages |
|-------+---------+------------+-----------------+--------------|
| *0* | restated (policy, not safety) | holds | holds | holds |
| *1* | *vacuous* — registry uniqueness replaces it | holds | *restated* — the hold is hours, not one quantum | holds |
| *2* | holds, and carries all the weight | holds | holds | holds |
| *4* | *restated* — =VALIDATED= in a publisher portal | holds | holds | holds; the record's /identity/ half is self-reported |
| *4b* | *holds literally*; subject → tip of the line | holds | *restated* — a third evaluation point mid-roll | holds |
| *5* | *vacuous as observation*; → provenance | holds at the origin only | *false by construction* during the roll | *unimplementable as written* [E] |

*** Confirmed, refuted, and the thing neither side said

*Confirmed: guard 5 breaks first, in every non-SPA shape, for three unrelated
reasons.* No server to ask (library); multi-valued by design (rolling); no place
to put the header (Pages). Three different failures of one predicate is strong
evidence that the predicate is over-specified — it conflates *what we want*
("the authorized artifact is the one in use") with *one particular way to check
it* ("a single response header equals a single expected string").

*Refuted: guard 4b is not the second to break.* It survives libraries with its
predicate untouched and its subject generalised from "trunk tip" to "tip of the
line"; it survives rolling deploys with the third evaluation point
=release-strategies.org= already named. Guard 4b turns out to be the *most*
portable guard in the set, because it is a statement about commit ancestry and
divergence class — and those exist wherever there is a version control system,
independent of what the artifact is or how it ships.

*The second to go vacuous is guard 1.* The berth is an exclusive lease on a
shared surface, and a library has no surface. This is not a weakness of the
model; it is *ADR-0001's Option A arriving from a different direction.* Option A
says: split the surface and guard 1, guard 0 and guard 4b become unstateable.
Part 2 says: change the artifact type to one with no shared surface and guard 1
becomes unstateable *and the registry gives you a stronger constraint for free*
— name-plus-version uniqueness, enforced by the platform, with no queue, no
lease and no forfeiture. The library ecosystems are living in ADR-0001's
recommended world, and they got there by having a different artifact rather than
by doing the engineering.

*And the thing neither the claim nor the model said: A5.* The model assumes
deployment is undoable and never writes that down. It fails absolutely for
libraries, fails after a one-way migration for stateful services, and fails as a
*primitive* on the repo's own default target, where rollback is a rebuild and
yesterday's artifact has a one-day retention. =spec.org='s controls protect the
rollback *commit*; nothing protects the rollback *artifact*, and nothing in the
model mentions state at all.

*Read the "covers our case?" column as a whole and the picture is unambiguous:

the second half.

* What we should adopt

Short, because the honest answer is "very little, and none of it on authority".

1. *Adopt nothing on DORA's authority, and stop reaching for it.* Keep measuring
   =validations per shipped change=. It has no standard name, no published
   benchmark, and it is the number that moved 23× between architectures. If a
   name is wanted, the 2025 report points at VSM's "ratio of value-add to wait
   time" — which is at least a phrase someone else has used. Do *not* add a
   DORA-shaped dashboard and expect it to show the contention; it cannot.

2. *Borrow OpenTelemetry's nouns for guard 5, not its telemetry.* Restate guard
   5 set-valued, in =service.version= / =service.instance.id= /
   =deployment.environment.name=. The vocabulary is Stable and standardised and
   it expresses the thing we cannot currently write down. Recording that OTel is
   self-reported keeps the evidence claim honest.

3. *Fix guard 5 on the =github= target, or stop claiming the target implements
   it.* =spec.org= §Targets says both targets must emit =x-build-sha=; Pages
   cannot. Either serve the sha as content and say so, or mark the =github=
   target as not conforming on guard 5. Leaving the sentence as written means
   the spec asserts something false about its own default target. This is the
   one concrete correction in this file.

4. *Correct the deployment-record row in §Domain model.* The entity table maps
   "platform-attested statement that artifact X reached environment Y" to "the
   Deployments API". GitHub's documentation says the opposite in as many words.
   The Pages deployments endpoint is a *partial* C6 — attested for serving,
   self-reported for provenance — and that is the accurate mapping.

5. *If a deployment record ever needs a schema, use CDEvents' shape.*
   =dev.cdevents.service.deployed= with ={artifactId (purl), environment}= is the
   only standard vocabulary that names the thing. Use it knowing it carries no
   authenticity model; the signature, if we want one, has to come from wrapping
   it as an in-toto predicate, which nobody has proposed and which we would be
   inventing.

6. *Write down A5, or admit the model assumes stateless artifacts.*
   =spec.org= §What this model gets wrong, on purpose is the right home. The
   guards protect the rollback *commit* and not the rollback *artifact*, and
   they have no state dimension at all. For a static storefront that is free.
   Anyone porting this model to a service with a database needs to be told,
   in the spec, that expand-and-contract is outside it.

7. *Keep the epistemics.* The one thing in this whole survey that a standards
   body states as plainly as =spec.org= does is CycloneDX's "declared and
   observed formulas" and SLSA's untrusted-=externalParameters= /
   trusted-=internalParameters= split. Both are the same idea as "manifest is
   derived, never asserted" and "attested, not self-reported". *That idea is the
   portable part of this repo*, and it is the part with the best external
   support.

What we should *not* do: adopt ITIL's release/deployment split as structure.
Noticing that all six guards are deployment-management guards is worth a
sentence in =spec.org=; building a release-management practice to fill the gap
would be ceremony by §The balance's own test — the queue would pay and
production would gain nothing.

* Refutation conditions

In the repo's house style, what would falsify the claims above:

1. *A DORA metric, capability or survey item that records an event which
   consumed pipeline capacity and produced no production deployment.* Would
   refute §The direct answer. The 2014/2015 reports were not searched and are
   the obvious place to look.
2. *A SLSA track, in any spec version or accepted proposal, whose subject is an
   environment rather than an artifact.* Would refute §SLSA explicitly does not
   cover deployment.
3. *An in-toto predicate, vetted or widely deployed, that binds an artifact
   digest to an environment and a time.* Would refute §The gap, stated, and
   would be the standard we are missing.
4. *A GitHub mechanism by which the platform, rather than the deploying job,
   observes and records what an environment is serving.* Would refute
   §A Deployment is self-reported. Custom deployment protection rules are the
   nearest candidate and they gate entry, not outcome.
5. *Any way to set a response header on GitHub Pages.* Would refute
   §Guard 5 is unimplementable as written, and would restore =spec.org=
   §Targets as written.
6. *An artifact type with no shared production surface for which guard 1 is
   still stateable.* Would refute §The second to go vacuous is guard 1.
7. *A library-shaped release in which guard 4b's predicate is genuinely
   vacuous* — i.e. where publishing from a base predating a hotfix cannot harm
   any consumer. Would refute §Guard 4b is not vacuous here.
8. *A rolling deployment arrangement in which redeploying the previous sha is a
   complete rollback after a contract-phase migration.* Would refute §A5 is the
   axiom that actually breaks.
