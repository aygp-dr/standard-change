* What this is

An inventory, not a repair. Every finding below is left in place on purpose:
the point of the exercise was to establish what is wrong, and a list of
defects half of which have been quietly fixed is a list nobody can audit.

=gates/shellcheck.sh= reports *0 findings* over 42 scripts. That is the floor.
This review is about what a static checker of shell syntax structurally cannot
see: a pipeline that discards the verdict it was carrying, a guard that reports
green because it could see nothing, a success message that measured nothing, and
a =|| true= on the one write that was the whole point of the step.

** How to read an entry

Every finding carries a =file:line=, what it does, what it should do, and a
*failure direction*:

| direction | meaning |
|-----------+---------|
| *OPEN*    | proceeds when it should refuse. The unsafe direction. |
| *CLOSED*  | refuses when it should proceed, or refuses for the wrong stated reason. Safe, still a defect — an operator sent to the wrong fix loses the same hour. |
| *NEUTRAL* | reporting only; no verdict moves. |

Evidence is marked =[E]= where it was reproduced on hydra in this session and
=[H]= where it is read off the source and not executed. Every =[E]= below was
run on FreeBSD 14.4-RELEASE-p6, =/bin/sh=, in this session.

46 tracked shell scripts. =change/= (24), =gates/= (10), =targets/= (4),

* The reproductions

** Exit status destroyed by a pipe

#+begin_example
$ cat t1.sh
#!/bin/sh
set -eu
die() { echo "DIE FIRED"; exit 1; }
false | sed 's/^/  /' || die "should have fired"
echo "REACHED: the die did not fire; pipeline status was $?"

$ /bin/sh t1.sh
REACHED: the die did not fire; pipeline status was 0
exit=0
#+end_example

=[E]= Under =#!/bin/sh= there is no =pipefail=. The =||= binds to the
*pipeline*, whose status is =sed='s. The =die= is unreachable code that looks
like a guard.

The same shape with =cut=, which is how every short SHA in this repo is made:

#+begin_example
$ sh -c 'set -eu; head=$(false | cut -c1-7); echo "head=[$head] survived"'
head=[] survived
#+end_example

=[E]= =set -e= does not fire, and the variable the rest of the script is *about*
is the empty string.

** grep -c prints 0 and exits 1, so =|| echo 0= appends a second zero

#+begin_example
$ sh -c 'last=$(printf "a\nb\n" | grep -c "zzz" || echo 0); printf "last=[%s]\n" "$last"'
last=[0
0]
#+end_example

=[E]= The variable is a two-line string. Interpolated into a message it is
cosmetic; fed to =$(( ))= it is fatal (=variable conversion error=), which is
finding [[#f39]].

** curl already prints 000, so =|| echo 000= makes 000000

#+begin_example
$ sh -c 'code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 2 http://127.0.0.1:1/ 2>/dev/null || echo 000); printf "code=[%s]\n" "$code"'
code=[000000]
#+end_example

=[E]= =change/marker.sh:70-73= documents this as found and fixed. The unfixed
copy is still in =change/soak.sh:34=.

** An empty expected value makes a health probe agree with silence

#+begin_example
$ sh -c 'got=$(curl -sI --max-time 2 http://127.0.0.1:1/ | tr -d "\r" | awk "..."); want="";
         if [ "$got" = "$want" ]; then echo "RETURN 0 -- deploy reported success with nothing deployed"; fi'

** 1. A deploy that placed nothing returns success
:PROPERTIES:
:CUSTOM_ID: f1
:END:

=change/driver.sh:41-42=, reached from =change/driver.sh:53=.

#+begin_src sh :eval no
  got=$(curl -sI --max-time 2 "http://127.0.0.1:$port/" | tr -d '\r' | awk '...x-build-sha...')
  [ "$got" = "$2" ] && return 0
#+end_src

*What it does.* =deploy()= polls the front for 60 seconds and returns 0 when the
served SHA equals the wanted SHA. Both sides can be the empty string at once. An
unreachable front produces =got=""=; and =$2= is =""= whenever =sha= is empty,
which line 53 arranges:

#+begin_src sh :eval no
  sha=$(gh pr view "$PR" --repo "$R" --json headRefOid -q '.headRefOid' | cut -c1-7)
#+end_src

The pipeline's status is =cut='s, so a forge failure is invisible and =sha= is
=""=. =git checkout --detach ""= then fails, but =deploy()= is called as
=deploy staging "$sha" || fail ...=, which *suspends* =set -e= for the whole
function, so execution continues to the poll — which passes on the first
iteration. The caller then writes =staging:deployed=.

*What it should do.* Refuse an empty SHA at line 53 (assign, then =cut=; assert
=[ -n "$sha" ]=), and assert =[ -n "$got" ]= before comparing.

*Direction.* OPEN. Nothing is deployed, the estate is unreachable, and the
change is labelled deployed and proceeds to =gates/health.sh=.

*Evidence.* =[E]= reproduced above.

** 2. Guard 4 reports green when it can see nothing
:PROPERTIES:
:CUSTOM_ID: f2
:END:

=change/guard4.sh:141=

#+begin_src sh :eval no
  bad=$(gh api "repos/$repo/commits/$head/check-runs" \
    --jq '[.check_runs[]|select(.name|test("^(gate-selftest|lint|test|e2e)$"))]|group_by(.name)|map(max_by(.started_at))|map(select(.conclusion!="success"))|length')
  ...
  elif [ "$bad" -eq 0 ]; then printf '  ok    %-16s %s\n' "check runs" "green on $short"
#+end_src

*What it does.* Fetches one page, filters to four names, counts the ones that are
not =success=, and calls zero "green". Zero is also what an empty page yields,
what a truncated page yields, and what a page containing none of the four names
yields. The guard cannot distinguish /all four passed/ from /I saw none of them/.

*What it should do.* Assert *presence*: all four names must appear exactly once
after the =max_by= collapse, and a missing name must return 4 (=I could not
check=, which blocks — =docs/exit-codes.org=).

*Direction.* OPEN.

*Evidence.* =[E]= for the page size; =[H]= that this SHA has ever exceeded it —
no network read was made. The sibling at =change/activate.sh:200= has the same
unpaginated read and fails *CLOSED*, because it additionally requires
=SELF -ge 1= — a positive assertion, which is exactly the repair this line needs.

** 3. Three identical API calls, and only the dangerous one defaults to zero
:PROPERTIES:
:CUSTOM_ID: f3
:END:

=change/guard4.sh:134-139=

#+begin_src sh :eval no
  lok=$(gh api ".../status"  --jq '[...select(.state=="success")]|length' 2>/dev/null || echo 0)
  lbad=$(gh api ".../status" --jq '[...select(.state!="success")]|length' 2>/dev/null || echo 0)
  lself=$(gh api ".../status" --jq '[...gate-selftest...]|length'          2>/dev/null || echo 0)
  if [ "$lbad" -eq 0 ] && [ "$lok" -ge 3 ] && [ "$lself" -ge 1 ]; then ... ok
#+end_src

*What it does.* Three round trips for one fact. =lok= and =lself= defaulting to 0
on error fails closed — the test needs them high. =lbad= defaulting to 0 fails
*open* — the test needs it low. So a transient error on the *second* call alone,
with the first and third succeeding, produces =lbad=0, lok>=3, lself>=1= and
prints =ok gates=. The same three defaults, one of which is the wrong way round.

*What it should do.* One call, one parse, and no default at all: a read that
failed must return 4.

*Direction.* OPEN. Same construct at =change/activate.sh:181-185=, where the
=LOK -ge 3= requirement saves it.

** 4. "I could not ask" is rounded up to "approved"
:PROPERTIES:
:CUSTOM_ID: f4
:END:

=change/guard4.sh:112-123=

#+begin_src sh :eval no
  if reviews=$(gh api "repos/$repo/pulls/$pr/reviews" --jq '.' 2>/dev/null); then
    ...
  else
    printf '  ok    %-16s %s\n' "review" "APPROVED (head unconfirmed: reviews unreadable)"
  fi
#+end_src

*What it does.* When the reviews endpoint cannot be read — rate limit, auth,
404, offline fixture — the guard prints =ok= and the approval stands unpinned to
any build. The comment above it argues this correctly separates /could not ask/
from /the head moved/, and it does; but it then resolves the third value into
*yes*.

=spec.org= defect class 1 states the rule this violates: "the third must refuse
*differently* from the second". Refusing differently is not the same as
accepting.

*What it should do.* Exit 4. An approval whose build cannot be confirmed has not
been established.

*Direction.* OPEN, and deliberately so, which is why it is worth listing: the
comment records the decision, so this is a policy to revisit rather than a
mistake to fix.

** 7. A failed issue read destroys the estate issue body
:PROPERTIES:
:CUSTOM_ID: f7
:END:

=change/lock.sh:31=

#+begin_src sh :eval no
  write() {
    _new=$(body | awk -v o="$OPEN" -v c="$CLOSE" 'index($0,o){skip=1} !skip{print} index($0,c){skip=0}')
    printf '%s\n%s\n%s\n%s\n' "$_new" "$OPEN" "$1" "$CLOSE" | gh issue edit "$ISSUE" --repo "$R" --body-file -
  }
#+end_src

*What it does.* =body()= is =gh issue view ... -q .body=. In a pipeline its
status is =awk='s, which is 0 on empty input. So a transient read failure makes
=_new= empty, and the =printf= then *replaces the entire issue body* with four
lines of lock block. The lock lives in the estate issue, which
=gates/preflight.sh= reads for the estate.

*What it should do.* Capture =body()= into a variable with its status checked,
refuse to write when the read failed, and require the two markers to have been
present in what was read.

*Direction.* OPEN and destructive: the loss is silent and the next reader sees a
well-formed lock in a document that no longer contains anything else.

** 9. An unparseable timestamp makes every lock stale
:PROPERTIES:
:CUSTOM_ID: f9
:END:

=change/lock.sh:35=, consumed at =:48=

#+begin_src sh :eval no
  age_min() {
    _t=$(date -u -j -f %Y-%m-%dT%H:%M:%SZ "$1" +%s 2>/dev/null || date -u -d "$1" +%s 2>/dev/null || echo 0)
    echo $(( ($(date -u +%s) - _t) / 60 ))

*What it does.* =|| echo 0= turns an unparseable or *empty* =started_at= into

* The shebang question
:PROPERTIES:
:CUSTOM_ID: shebang
:END:

Asked directly: should the 42 =#!/bin/sh= scripts become =#!/usr/bin/env sh=
for FreeBSD portability?

*No.* The honest answer is the opposite of the request, and the evidence is on
this host.

** What is actually on the tree

#+begin_example
$ git ls-files '*.sh' '*.py' | while read -r f; do head -1 "$f"; done | sort | uniq -c | sort -rn
  42 #!/bin/sh
  25 #!/usr/bin/env python3
   1 #!/usr/bin/env python3.11
   1 #!/usr/bin/env bash
#+end_example

** Why =#!/bin/sh= should stay

=/bin/sh= is the one interpreter path POSIX guarantees. It is not the same risk
as =#!/bin/bash=, and conflating the two is what makes "use env everywhere"
sound like a rule.

#+begin_example
$ ls -l /bin/sh
-r-xr-xr-x  1 root wheel 169288 Jun 21 18:10 /bin/sh
$ uname -a
FreeBSD hydra 14.4-RELEASE-p6 FreeBSD 14.4-RELEASE-p6 GENERIC amd64
#+end_example

=[E]= A real binary at the guaranteed path — not even a symlink that could be
swapped. There is no host in this project's matrix where =/bin/sh= is absent and
=env sh= would find a shell that =/bin/sh= would not. So the change buys nothing,
and costs two things:

1. *=env= form loses the ability to pass a shell option in the shebang.*
   =#!/usr/bin/env sh -e= does not work: most kernels hand the =env= form a
   single argument, so ="sh -e"= is looked up as one program name and the exec
   fails. A direct-path shebang can carry an option. Nothing here relies on that
   today — every script says =set -eu= on its own line, which is better — but
   giving up a capability for no gain is not portability.
2. *=env= resolves through =PATH=.* Irrelevant in this repo, because nothing is
   setuid and the =PATH= is the operator's own. It is stated because it is the
   reason =env= is not *strictly* safer than a direct path, and a rule argued as
   "env is always safer" is a rule that will be applied where it is not.

** Where =env= IS load-bearing

The other half of the rule is the one that matters, and this repo already
follows it:

#+begin_example
$ ls -l /bin/bash
ls: /bin/bash: No such file or directory
$ command -v bash
/usr/local/bin/bash
#+end_example

=[E]= =bash= is at =/usr/local/bin/bash= on FreeBSD and =/bin/bash= on Linux.
A non-POSIX interpreter has *no* guaranteed path, so hardcoding one is the
portability defect that actually bites.

=.github/config/apply.sh= is the only =#!/usr/bin/env bash= in the tree and it
is *correct*. It genuinely needs bash — =[E]= nine SC3xxx findings under
=-s sh=: =set -o pipefail=, =BASH_SOURCE=, arrays, =local=, four process
substitutions, =$'..'=. Converting it to =#!/bin/sh= would break it; hardcoding
=#!/bin/bash= would break it on this host.

** The one real hazard, and it is not the shell

=targets/bastille/app.py:1= is =#!/usr/bin/env python3.11=.

A version-pinned shebang works everywhere until it works nowhere. =python3= on
hydra is 3.11.15 today, so the pin is invisible; the first =pkg upgrade= that
moves =python3= to 3.12 turns it into an exec failure with no warning in
between, and =env= is powerless to help because the *name* being asked for is
the thing that will not exist.

This is the only shebang in the repository that needed changing and it is
changed in its own commit.

*The shebang change does not reach the pin.* =app.py= is not executed through
its shebang on the deploy path — it is passed to a named interpreter:

#+begin_src sh :eval no
  # targets/bastille/deploy.sh:30
  sudo jexec "$j" sh -c 'pkill -f "python3.11 app.py" 2>/dev/null; pkill nginx 2>/dev/null; true'
  # targets/bastille/deploy.sh:36
  ROUTES='$routes' nohup python3.11 app.py >/var/log/$app.log 2>&1 &
#+end_src

Both are still pinned, and they are *coupled*: =:30='s =pkill -f= pattern is a
literal match on =:36='s command line, so changing one without the other leaves
a kill that silently stops matching — which makes finding [[f-kill]] worse rather
than better. That change needs the bastille estate to test, the bastille estate
is not present on this host (=change/activate.sh:59= refuses for exactly that
reason), and an untested edit to a production deploy script's process-matching
is not a change to make while the estate is in use. *Left alone, deliberately,
and recorded here.* The trigger to revisit is the first host where =python3= is
not 3.11.

** The rule, made executable

Two forms, no others:

| form | for |
|------+-----|
| =#!/bin/sh= | a POSIX shell script. The guaranteed path. |
| =#!/usr/bin/env <name>= | every other interpreter. The path is not guaranteed, so ask. Unpinned. |

=gates/shebang.sh= enforces it and =gates/shebang.sh --selftest= proves it can
refuse — six fixtures, one per refusal class, plus three that must be accepted.
A lint rule nobody has watched reject something is a hypothesis.

*And the first version of that selftest was itself the defect it was written to
refute.* It asserted only that each =fail/= fixture was *refused*. Deleting the
absolute-path rule outright left =#!/bin/bash= falling through to the catch-all
and reported as "no shebang" — still a refusal, so the suite still passed:

#+begin_example
$ sed "s|^    '#!'\*)|    '#!NEVERMATCH'*)|" gates/shebang.sh > mutant
$ ./mutant --selftest
  shebang --selftest: 9/9 fixtures, 0 failure(s)      <-- MUTANT SURVIVED
#+end_example

=[E]= That is =spec.org= class 7 — a check satisfied by something other than the
thing it is about — reproduced inside the check written to demonstrate the
opposite, by the reviewer, in the same hour as writing up thirty instances of
it. It was found by mutation and could not have been found by reading.

The selftest now asserts the *reason*, not the refusal, and asserts its own case
count. Re-run against the whole matrix:

#+begin_example
  unmutated baseline                         exit=0 (must be 0)
  1. classify() always accepts               KILLED   (selftest exit 1)
  2. version-pin rule removed                KILLED   (selftest exit 1)
  3. env-sh rule removed                     KILLED   (selftest exit 1)
  4. absolute-path rule removed              KILLED   (selftest exit 1)
  5. env-with-option rule removed            KILLED   (selftest exit 1)

#+end_example

=[E]= Seven of seven. That is the difference between a rule and a control.

The hardening also surfaced a second defect in the suite: the case table was
