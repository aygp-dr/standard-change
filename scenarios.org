* What this is

The executable test plan for =spec.org= §Labels and §Promotion pipeline. Each
scenario names its setup, the labels and guard outcomes it expects, and the one
assertion that makes it a test rather than a demonstration.

These are *not* a demo script. Scenario D4 below refuted the pipeline as
specified at 0.2 and forced an amendment (§The gap D4 found). That is what the
catalogue is for.

Status: every scenario is [H] — written, none run. Nothing exists to run them
against yet.

* Part A — labeller scenarios

The labeller runs =sync-labels: true=, so it *owns* =app:*= and
=change:{standard,normal}=: it adds them and it takes them away. These
scenarios check both directions, because a labeller that only ever adds is the
classic checker that cannot fail.

| id  | WIP diff touches                            | expect labels                              | checks                     |
|-----+---------------------------------------------+--------------------------------------------+----------------------------|
| L1  | =apps/core/src/pages/index.js=              | =app:core=, =change:standard=              | basic attach               |
| L2  | =apps/pdp/= and =apps/checkout/=            | =app:pdp=, =app:checkout=, =change:standard= | multi-group attach       |
| L3  | all four app dirs                           | four =app:*=, =change:standard=            | full fan-out               |
| L4  | =router/nginx.conf.tmpl= only               | =change:normal=, *no* =app:*=              | normal with no group       |
| L5  | =apps/plp/= and =.github/workflows/gate.yml= | =app:plp=, =change:normal=                | normal wins over standard  |
| L6  | =README.org= only                           | none                                       | no-op diff labels nothing  |

** Removal (the half that proves ownership)

| id  | sequence                                                    | expect                                          |
|-----+-------------------------------------------------------------+-------------------------------------------------|
| L9  | L2, then push removing all =apps/checkout/= changes          | =app:checkout= *gone*; =app:pdp= remains         |

L10 is the ownership assertion: the =app:*= set is a /derived/ artifact of the

** D1 — several changes to the same app, in sequence

Three PRs, all touching =apps/pdp/=. The point is the queue and the rebase loop.

| step | action                                    | expected                                                            |
|------+-------------------------------------------+---------------------------------------------------------------------|
|    1 | PR-P1, PR-P2, PR-P3 opened; gates green   | each gets =app:pdp=, =change:standard=                              |
|    2 | =deploy:staging= on PR-P1                 | guard 0 pass, guard 1 pass → claims staging                         |
|    3 | =deploy:staging= on PR-P2 (while P1 holds) | *guard 1 fails*: =blocked:queue=, =deploy:staging= removed, comment naming #P1 |
|    4 | P1 staging e2e passes                     | =staging:passed= → promote adds =deploy:production=                 |
|    5 | P1 production healthy                     | =production:healthy=, PIR, merge, =release.sh= frees labels          |
|    6 | release comments on PR-P2, PR-P3          | both told to rebase                                                 |
|    7 | =deploy:staging= on PR-P2 *without rebase* | *guard 0 fails* (=BEHIND=): label removed, comment                  |
|    8 | rebase PR-P2 onto main, re-add label      | claims staging                                                      |

*Assertion:* at no point do two PRs carry =deploy:staging=, and step 7 is
refused. Step 7 is the whole reason guard 0 exists — without it PR-P2 deploys a
=apps/pdp/= tree that predates P1 and silently reverts it.

** D2 — mixed apps

| step | action                                              | expected                                       |
|------+-----------------------------------------------------+------------------------------------------------|
|    1 | PR-M1 touches =apps/core/= + =apps/plp/=            | =app:core=, =app:plp=                          |
|    2 | PR-M2 touches =apps/pdp/= only                      | =app:pdp=                                      |
|    3 | =deploy:staging= on PR-M1                           | claims; =groups.sh= prints exactly =core plp=  |
|    4 | staging deploys                                     | core + plp from PR SHA; pdp + checkout from production SHA |
|    5 | e2e runs                                            | core and plp journeys, *plus* =tests/e2e/= cross-app journeys touching them |
|    6 | =deploy:staging= on PR-M2                           | =blocked:queue= — staging is global, not per-app |

*Assertion:* step 4's untouched groups serve the /production/ SHA, not the PR
SHA. This is the mixed-app trap: if the deploy script rebuilds all four from
the PR, staging stops being a test of "this change against current production"
and the cross-app journeys prove nothing.

*Assertion:* step 6 refuses even though the app sets are disjoint. Staging is a
singleton by design; disjointness is not a safe exception while the four apps
share one router and one mock backend.

** D4 — emergency interrupts a standard change already in staging

The scenario the catalogue was written for.

| step | action                                                    | expected                                                    |
|------+-----------------------------------------------------------+-------------------------------------------------------------|
|    1 | PR-S holds staging, =staging:passed= on SHA =s1=          | =deploy:production= added by promote                        |
|    2 | Incident. PR-E opened with =change:emergency=             | labeller sets =app:*=; PR-E does *not* request staging      |
|    3 | =deploy:production= on PR-E                               | guard 1 not consulted — the emergency path never touches the staging queue |
|    4 | both PRs now hold =deploy:production=                     | =concurrency: production, cancel-in-progress: false= serializes them |
|    5 | PR-E deploys, healthy, *merges to main*                   | main now contains the hotfix                                |
|    6 | PR-S is now =BEHIND= main — *but it already passed staging* | ← see below                                               |

*This is where 0.2 as specified was wrong.* Guard 0 runs in =queue.sh claim=,
at staging-request time. At step 6 PR-S never re-requests staging: it already
holds =staging:passed= from SHA =s1= and already has =deploy:production=.
Nothing in the specified pipeline re-examines its relationship to =main= after
=main= moves. PR-S deploys a tree that predates the hotfix and *silently
reverts the emergency fix* — while every gate is green, because =s1='s gates
were green and no push invalidated them.

The SHA binding does not help: it invalidates =staging:passed= when the *PR*
moves, and here the PR did not move — =main= did.

*Assertion (post-amendment):* at step 5, merging PR-E removes =staging:passed=
and =deploy:production= from every open PR now behind main, including PR-S, and
comments telling it to rebase. PR-S must rebase onto main and re-run staging
before it can reach production.

*Assertion:* the re-run is a real re-run. PR-S rebased onto the hotfix is a
tree nobody has tested; its previous staging pass describes a tree that no
longer exists.

** D9 — a change deploys outside its release window

Run live 2026-09-13 at 22:37Z against *#44*, whose reservation is
=CHG-20260914T0900-44.1= — *the following morning at 09:00Z*. Eleven hours out.

*** What refused, and what did not

=gates/preflight.sh 44= refused correctly:

: NO   I am NOT on the calendar. No open window for #44 on staging covers now.
:                                                            preflight exit=4

*Nothing else on the deploy path checks the window at all.* Grepped:

| script | consults the schedule |
|--------+-----------------------|
| =change/queue.sh= | no |
| =targets/node/deploy.sh= | no |
| =change/soak.sh= | no |
| =change/guard4.sh= | no |
| =change/settle.sh= | yes — at the END, to redline the window |

So guard 3 exists at exactly one site, on an *advisory* path. =preflight= is a
checklist a person runs; nothing downstream re-asks, and =settle= only reads the
schedule to close a window it assumes was honoured. A caller who skips
=preflight= — or whose =preflight= exit code is discarded, which is the shape of
every =cmd | sed= bug in this repo — deploys outside every window and no guard
notices.

*** The worse finding: =queue.sh claim= reports success having done nothing

: $ ./change/queue.sh claim 44
: claimed
:   exit=0

#44 held no =deploy:staging= label before this and holds none after. The word is
wrong in a way that matters: *=queue.sh= is a VALIDATOR, not a claimer.* It is
invoked after something else has added the label, it *removes* the label when
guard 0 or guard 1 refuses, and it echoes =claimed= when they pass.

Asked to claim a berth for a change that holds no claim, it validated the
absence of a claim and reported success. A caller reading =claimed= / exit 0
reasonably believes it holds the berth. It holds nothing, and the next change
will take staging out from under it.

*** Why #44 was not blocked for a second reason either

#44 still carried =itil:emergency= from the break-glass exercise earlier the
same session, so guard 0 and guard 1 would have exempted it regardless. *A
classification outlived the test that set it.* Nothing expires a class, and
nothing reconciles "this was declared an emergency two hours ago for a
different purpose" with "this is an ordinary change now".

*** What this is a case of

All three are the same shape as =docs/interfaces.org= §8: a guard that is
*checked once* rather than *re-derived at reliance*. The window is checked at
the top of preflight and never again; the class is set once and never expires;
and =queue.sh= answers about a state it never verified it was asked about.

*** Decision: 1 is DEFERRED. 2 and 3 are defects.

*Deferred — guard 3 on the deploy path.* A person reads the calendar, sees
their window, and deploys. =preflight= is the checklist they run, and a
checklist a human follows is a real control; enforcing the window a second time
inside every target would be a second implementation of guard 3, which is the
defect this repo has already hit twice (guard 2 in preflight vs activate, the
calendar in preflight vs =current=). Building it now buys nothing and costs a
divergence.

*The trigger that forces the revisit:* *the first deployment initiated by
automation rather than by a person.* At that moment nothing reads the calendar
at all — there is no checklist, and =preflight='s exit code is advice nobody
receives. Any of these counts: a workflow that calls a target directly, a
scheduled job, an agent driving =deploy.sh= unattended, or =change/activate.sh=
being revived.

Until then this is a *known, accepted gap*, not an open bug, and it is written
down so nobody rediscovers it and treats it as one.

*Still defects, and small:*

1. =queue.sh claim= must refuse when the PR holds no =deploy:staging=, rather
   than echoing =claimed=. "Nothing to validate" is not "validated", and the
   caller cannot tell the difference from the output.
2. An =itil:*= classification must be re-confirmed when a change is activated,
   not trusted from whenever it was last written. #44 carried =itil:emergency=
   for two hours after the exercise that set it, and would have been exempted
   from guard 0 and guard 1 on that basis.

Nothing was deployed. The berth was not taken; the estate was untouched.

** D10 — pre-authorised auto-scheduling. SPECIFIED, NOT BUILT.

*Read this before assuming any of it exists.* Nothing in this repo
auto-schedules anything. Every window on the calendar today was booked by a
person typing =./change/schedule.sh block=, and the one attempt to write an
=autoschedule.sh= was deleted rather than shipped, because a half-built
scheduler that looks present is worse than an absent one.

This section is a *requirement for the 001 rebuild*, written so a later agent
does not read the surrounding repo as more capable than it is.

*** Why it is defensible at all

=docs/adr/0003= says scheduling is owned by a person and there is no
auto-scheduler. That is over-broad rather than wrong, and ITIL supplies the
correction: *a standard change is PRE-AUTHORISED BY DEFINITION.* Booking one is
not a scheduler exercising judgement — it is honouring an authorisation granted
once, when the change model was accepted. The judgement is in the model, not in
the booking.

So the scope is narrow and must stay narrow: *book pre-authorised, demonstrably
low-risk changes; never deploy, never merge, never choose an hour a person
asked for.*

*** Eligibility — every condition must hold

Each is here because its absence broke something during the grind:

| condition | why |
|-----------+-----|
| exactly one =itil:= label, and it is =itil:standard= | two classes leaves the class undefined and every rule branches on it; none satisfies every such rule by default. Five of eight booked changes were unclassified at once |
| =APPROVED= | booking an unapproved change reserves the path to production for something that cannot use it |
| not a draft | the author's own statement, and the one input the pipeline does not second-guess |
| exactly one =app:*= group | blast radius of one. =shared/**= fans out to four and is not low risk whatever its diff looks like |
| touches no =gates/ change/ targets/ router/ shared/ sim/ tla/ .github/= | control-plane changes alter how every FUTURE change is verified; proven by use across later deployments, never by a booking |
| holds no open window | a change with two reservations double-books the berth against itself — observed twice on 2026-09-13 |
| the estate is open | pre-authorisation is *not* an exemption from a freeze. Only =itil:emergency= is |

Anything failing any condition is *reported and left alone*, never forced.

*** What it must not do

- *Not deploy.* Booking is an entitlement to the path; something still has to
  drive the change through it.
- *Not choose an hour.* A designated slot is usually a developer saying they
  will be present. Auto-booking takes next-available only.
- *Not clear a refusal.* A guard refusing is the system working.

*** The measurement this is really about

The reason to specify it is *the manual cost it would remove*, and that cost is
the thing being ground out here. Every booking today cost: read the calendar,
pick a duration that clears the floor, check for a clash, book, watch it not be
driven, reap it, re-book. See =docs/time-spent.org=.

*An implementation is only worth it if that cost is measured first.* 001 should
build the harness before the scheduler.

** D11 — a branch old enough cannot be verified at all

Hit live on *#2 =feat/pdp-price== at 23:18Z, seven minutes into its window.

=gates/preflight.sh 2= → *exit 1*: twelve check runs not passing on =47518d6=,
because CI has not scheduled a job since issue #34. The documented fallback is a
host-measured =local/= status from =gates/report.sh= — and *that script does not
exist in the branch's tree*. It was added in =06fc71f=; #2 is *81 commits
behind* its merge base.

*Guard 2 needs evidence about this build, and the instrument that produces that
evidence is not in this build.*

*** Why neither workaround is available

- Running =main='s =report.sh= against the old tree is refused by design: it
  resolves its own repo root and will not report unless the working tree IS the
  PR head. That refusal was added the same afternoon, after it gated =main=
  while printing a line that read as though it had gated #42.
- Rebasing is the real fix, but it moves the head, voiding the approval and any
  status it might earn — and 81 commits does not fit inside a ten-minute window.

*** What this is a case of

=change/divergence.sh= asks /did main change how you are verified?/ and classes
that =pipeline=. This is the same question one step further: *main changed
WHETHER you can be verified.* The control plane moved forward and took the
instrument with it.

It gets worse monotonically with branch age, and every long-lived branch in this
repo has it. It is invisible until the window opens, because nothing checks
"can this change even be measured" until guard 2 asks for the measurement.

*** What 001 should do about it

Not obvious, and worth stating rather than inventing:

1. =report.sh= could run from =main= against a named worktree, with the head
   check comparing the WORKTREE's head to the PR's rather than its own. That
   makes the reporter portable across branch ages, at the cost of it no longer
   being obvious which tree produced a result — the field that says so becomes
   load-bearing.
2. Or guard 0 could refuse earlier and louder: "you are N commits behind and
   cannot be verified until you rebase" is a better message at booking time
   than exit 1 at activation time.
3. Or accept it: a branch this old is a rebase away from everything, and the
   forfeit is the system telling the truth.

*Nothing is implemented.* #2 forfeited its window, the estate was untouched, and
the finding is recorded rather than worked around.

** D12 — a scheduler that books faster than anything drives

Self-inflicted on 2026-09-13 and worth keeping.

A five-minute loop was given: /if no window covers now, book the next approved
unscheduled PR/. It fired every tick, booked one, and drove none — and each
booking took next-available, which chained forward. *Twenty-five windows on
2026-09-19*, with #6, #28 and #42 repeating every thirty minutes.

The bug is not the rate. *Booking and driving have to be the same loop.* A loop
that can do one without the other will fill the calendar indefinitely, and every
individual booking looks correct.

The tell was visible on the dashboard immediately — a wall of identical future
rows — which is the second time the board surfaced something no script noticed.

** D13 — settlement reported a merge that did not happen

Hit live on *#40* at 00:44Z, and it is the finding that justifies the whole
manual overlay: *an autonomous loop would have reported seven successes that
night.*

*** What happened

: gh         "not mergeable: the merge commit cannot be cleanly created"
: PR state   OPEN, mergeable=CONFLICTING
: settle.sh  "settled: #40 merged -- the forge is the record now"

=change/settle.sh= had =gh pr merge ... && ok=. The merge refused, the =&&=
short-circuited, *and execution continued*: the PIR was posted, the window was
redlined =passed=, the validation labels were cleared, and the summary claimed
success. Production had already been cut over to =43646f9=.

*** Why it is the worst shape

The change was *deployed and not merged*. That is the state with no name: the
front serves a build =main= does not contain, and the next change branches from
a =main= without it and reverts it on promotion. Reached by a script that
reported the opposite, with every downstream step destroying the working state
that would have shown it.

Same shape as the =gate | sed= defect the same afternoon — a step failed, its
status was never checked, the summary asserted the opposite. *Settlement is the
one place that must never do this.*

*** The conflict underneath

#40 and #44 each add one row to =apps/core='s =PANELS= object literal. #44
landed at 00:22, #40 tried at 00:44. The agent that scaffolded the twenty tiny
PRs had already written this down — /"PANELS is a seam that admits one change at
a time"/ — and capped core at four changes because of it. *The warning existed
and nothing consumed it.*

*** Two oracles I got wrong while diagnosing

Recorded because the diagnosis was nearly as instructive as the defect:

1. I reported all seven changes as "not on main" using
   =git merge-base --is-ancestor=. *GitHub squash-merges*, so a branch SHA is
   never an ancestor even when the change landed. Six had shipped fine. The
   right oracle is the CONTENT — =PANELS= on main had =/account= and not
   =/cart=.
2. I twice called a rebase failure a "conflict" without reading git's message.
   One was a *dirty index* in a worktree; one was my own lookup matching two
   worktree paths and handing =git -C= a two-line string. Only #21's conflict
   was real.

*** Fixed

=settle.sh= now exits 8 on a failed merge and runs nothing after it, printing
=mergeable= / =mergeStateStatus= and the recovery. The rollback to a colour
whose build IS on main is named in the message, because that is the action the
operator needs and it is not obvious under pressure.

** D14 — a deliberately broken change, and the window that expired refusing it

Injected on purpose on *#56* (=tiny/plp-no-category-label=) at 02:2xZ. *Not to be
fixed.* The point was to watch the pipeline refuse, and to watch the
change-control window lapse while it was refused.

*** The injection, and what it took to make one

First attempt: change the copy the PR exists to change — =(no category)= became
=BROKEN-ON-PURPOSE=. *24 tests passed.*

That is the finding, and it arrived before the scenario did. *#56's own change is
asserted by nothing.* The PR could ship inverted and no gate would notice, and
several of the twenty scaffolded changes are probably in the same position — a
one-line copy tweak whose only verification is that the file still parses.

To get a failure at all, the break had to hit a *pre-existing* assertion:
=render()= returning =app: 'BROKEN-ON-PURPOSE'= instead of =meta.app=. *3 tests
fail.* The change under test is untestable; the app's identity is not.

*** What 001 must reproduce

1. *A change whose diff is covered by no assertion is a change the pipeline
   cannot judge.* Every gate is green and the verdict means nothing. This is the
   =gate-selftest= rule — a suite that cannot fail produces no verdict — applied
   to a single change rather than to a suite.
2. *The refusal must come from CI's own verdict on THIS head*, not from a local
   run, and not from a stale run: see D15 below on superseded check runs.
3. *A refused change must still lose its window.* Refusal is not a hold. The
   reaper closes it =expired=, =change:scheduled= comes off, and the change is
   left approved-and-unbooked — eligible, not failed, and owed nothing.

*** The validation, stated as a test the rebuild must pass

: GIVEN  a change whose head fails its unit tests
: WHEN   its window opens
: THEN   preflight refuses on guard 2 with the failing head named
: AND    nothing is deployed to staging
: AND    the window lapses and is reaped `expired`, not `failed`
: AND    change:scheduled is cleared and the change stays approved

A rebuild that ships a change with red tests has failed. A rebuild that marks
the lapsed window =failed= has also failed — nothing was attempted, so nothing
failed.

** D15 — superseded check runs counted as current

Found at 01:57Z, minutes after Actions came back, and it would have blocked all
sixteen queued changes.

GitHub keeps *every* check run attached to a SHA. The billing-era runs from
23:20 — one =failure=, three =skipped= — were still there beside three fresh
successes, and guard 2 reported =4 not passing, self-test 3= on a commit whose
gates were entirely green.

*A re-run supersedes.* A guard that counts history refuses on evidence that has
been replaced. Fixed in all five queries across =gates/preflight.sh= and
=change/guard4.sh=:

: group_by(.name) | map(max_by(.started_at))

Companion to /did not run is not red/ — the same rule about a different axis.
*Unreachable is not falsified; superseded is not current.*

*** Why it matters for 001

Both rules exist because a check run has three independent properties the API
flattens into one field: *did it run*, *when did it run*, and *what did it
conclude*. Any rebuild that reads =conclusion= alone will reproduce both defects,
and both are silent — they refuse changes that should pass, so nothing breaks
loudly enough to investigate.

** D16 — the driver walked past a refusal into production

02:12Z, on *#54*. Guard 4 printed =NOT authorized= and the change was deployed
to the idle colour and the front cut over to it anyway.

*** The line

: ./change/guard4.sh "$PR" | tail -1

A pipeline's exit status is its LAST command's. =tail= always succeeds, so
=set -e= saw zero and execution continued through the production deploy, the
idle-colour e2e, and the cutover.

*** Why it is the finding rather than a bug

*This is the same defect as =change/activate.sh='s =gate | sed=, fixed eight
hours earlier the same day, and then rebuilt from scratch in the driver written
to replace it.* Knowing the rule did not prevent writing the code. The shape is
too ordinary: piping a command to trim its output is the obvious thing to type,
and it silently converts a guard into a print statement.

Four more instances were in the same file — the soak, the UAT, the idle-colour
e2e, and the staging walk. All five now capture the output, test the status, and
print afterwards.

*** What guard 4 was actually refusing

=staging:uat= — *the label was absent while the observation record existed.*
Guard 4 checks both on purpose: the record proves a measurement was taken, the
label proves nobody has since withdrawn acceptance. A missing label with a
present record means somebody withdrew it, and the guard is right to refuse.

So the guard was correct, its verdict was correct, and the driver ignored it.

*** Recovery, and what it cost

Production was rolled back to =9583730= (#53, merged and authorized). #54's
change is one CSS rule, so the blast radius was nil — but the estate served an
*unmerged, unauthorized* build for roughly ninety seconds, and nothing in the
pipeline would have said so. The driver reported the cutover as success.

*** For 001

A rebuild must not be able to express this. Any step whose verdict gates a later
step has to be *unpipeable* — the runner captures, tests, then formats. Stated
as a rule: *formatting happens after the verdict is in hand, never in the same
expression that produces it.*

** D17 — guard 0 has never fired, because the forge never says BEHIND

*Measured 2026-09-14, after 163 commits landed on =main= in one night.*

=change/queue.sh= implements guard 0 — /up to date with main/ — and the whole
of its behind-detection sits inside one condition:

: state=$(gh pr view "$pr" --json mergeStateStatus -q .mergeStateStatus)
: if [ "$state" = "BEHIND" ]; then
:     ... ./change/divergence.sh ... inert | pipeline | artifact ...
: fi

The careful part — classifying what landed under you, granting the berth for an
=inert= docs merge and refusing for =pipeline= or above — only executes when the
forge returns exactly =BEHIND=.

*It never has.* Across the repository's life:

| query | count |
|-------+-------|
| PRs whose comments say =BEHIND relative to main= | *0* |
| PRs that got the =`main` moved by a <class>= refusal | *0* |
| open PRs reporting =BEHIND= after 163 commits to main | *0 of 14* |

The 14 were measured directly: 8 =CLEAN=/=UNSTABLE=, 6 =DIRTY=, none =BEHIND= —
while every one of them was demonstrably behind trunk.

*** Why

=main= has branch protection with =required_status_checks.strict = true= — the
"require branches to be up to date" flag — but =contexts: []= and =checks: []=.
Strict mode with nothing required. GitHub appears to compute =BEHIND= only when
there is a required check for being up-to-date to gate, so with an empty list
the state is simply never produced. *[H] — inferred from the observation and the
configuration; not verified by adding a required check and re-measuring.*

*** Why it matters more than it looks

This is class 7 — /a check that cannot fail produces no verdict/ — and it is the
*second measured instance in the same repository*, which is the finding. The
first is guard 6: =gates/production-first.sh=, 484 runs, never once triggered by
a label. Two guards, both carefully written, both reasoned about in ADRs, and
neither has ever refused anything.

Both fail the same way: the guard is correct, and its *trigger condition is
supplied by an oracle that does not produce that value in this configuration*.
Reviewing the guard body finds nothing, because there is nothing wrong with it.

*** What is NOT dead

=change/divergence.sh= is still reachable — =change/release.sh= (guard 4b at the
merge) fires on =BEHIND= *or* =DIRTY=, and =DIRTY= does occur. So the classifier
runs; it is guard 0's entry to it that is unreachable.

*** The rebuild test

A pipeline cannot be graded on whether its guards are written correctly. It must
be graded on *whether each guard has ever refused anything, and if not, why not*.
A guard with zero lifetime refusals is a hypothesis, not a control — and the
question to ask of it is not "is the logic right" but "can the oracle it reads
ever emit the value it tests for".

** D18 — an approved change is refused on entry to staging by the acceptance it did not update

*Observed 2026-09-14 on the mini, with =gates/uat.sh= on the day it was written.*

The case a change calendar cannot see, and the reason automating one is
harder than it looks. A change alters the flow or the navigation of the
storefront — #71 makes "Ready to continue to payment." a link; #40 and #52
give the cart page a cart. Its unit tests are green, its reviewer approved
it, its window is booked. On entry to staging the *acceptance* suite — the
browser journey pinned as it was last accepted — refuses it, because nobody
told the acceptance that the flow was going to change.

*** What each layer does

| layer | what it says | right? |
|-------+--------------+--------|
| gates (lint, test, e2e) | green on the head | yes — nothing it measures changed |
| review | approved | yes — the change is what was asked for |
| schedule | window booked, berth claimed at activation | yes — every guard passed at the claim |
| =gates/uat.sh= on staging | *REFUSED: the journey is not what was accepted* | *yes* — acceptance is a record of what was accepted, and the flow is different |
| the window | spent; the berth is released; the change goes back to needing a window | correct, and expensive |

The refusal is the pipeline working. The cost is that the window was spent
discovering something that was knowable at review time, and *no scheduler
can know it*: the calendar sees a booked change with green gates, and the
thing that will refuse it runs only against a deployed estate.

*** What was actually observed

PR #71 (=fc2ee1b=) deployed to block 1 and =gmake uat url=http://127.0.0.1:9010=
refused it in 1.1 s — but at the *category page*, not at the payment link
the PR changes. The branch predates plp's named product links, so the first
page that differed from acceptance was one the PR never touched. Two lessons
in one run:

1. Acceptance refuses on the *first* difference, which is not necessarily the
   *intended* one. The message names a page; the reader has to work out
   whether that page is the change or the drift.
2. This is D17's silent guard 0 seen from the other side. The forge never
   said BEHIND, =queue.sh= never classified the drift, and the change reached
   the estate carrying a category page from before the search feature. The
   acceptance suite caught it by accident of ordering.

*** The rule this suggests

*A change to the flow carries its acceptance.* The PR that changes the
navigation also changes =gates/uat/journey.spec.mjs=, and the reviewer reads
the two diffs together: what the code does, and what a person will now
accept. Then the suite is green on staging for the right reason, and the
window is spent deploying rather than discovering. This is a review
convention, not a guard — a guard would need to know which PRs change the
flow, and the honest answer is "the ones whose acceptance diff is empty and
should not be", which only a reviewer can judge.

For an automated change calendar the consequence is plain: a booked, green,
approved change can still forfeit its window on entry to staging, so the
calendar must model *forfeit on entry* as an ordinary outcome, not an
incident — which =schedule.sh close <id> failed= and the reaper already do.
What the calendar cannot do is prevent it; only the PR can.

*** Reproducing

: gmake dev                                      # block 0 on main
: gmake uat url=http://127.0.0.1:9000            # accepted, as-is journey held
: git worktree add worktrees/pr71 origin/tiny/checkout-payment-link
: (cd worktrees/pr71 && gmake port-alloc && gmake dev)      # block 1, :9010
: gmake uat url=http://127.0.0.1:9010            # REFUSED at the category page

* The gap D4 found

Writing D4 refuted =spec.org= 0.2. Recorded here because the path is the value,
and amended there rather than left as a note:

- *Observation.* Guard 0 is evaluated once, at staging-claim time. =staging:passed=
  is invalidated by pushes to the PR but not by movement of =main=.
- *Consequence.* Any merge to =main= while another PR holds a staging pass
  leaves that pass describing a tree that no longer composes with main. The
  emergency path makes this routine rather than rare, because an emergency is
  precisely a merge to main that jumps the queue.
- *Amendment.* A =main=-push workflow invalidates =staging:passed= and
  =deploy:production= on every open PR that is now behind, and guard 4
  re-checks =mergeStateStatus= at production time. See =spec.org=
  §Promotion pipeline §Guard 4b.
- *Generalization.* Guards evaluated at request time expire. Any guard whose
  subject can change after it is checked must be re-checked at the moment it is
  relied on — guard 0 at claim time is a convenience, guard 4b is the real one.
