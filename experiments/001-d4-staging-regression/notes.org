Writing scenario D4 in =scenarios.org= by hand was what surfaced this; the

* 2026-09-12 — first TLC run: tooling, not findings

Two failures that were mine, not the spec's:

1. =NoPR == CHOOSE x : x \notin PRs= — TLC: "attempted to evaluate an unbounded
   CHOOSE". Fixed by making =NoPR= a CONSTANT and a model value, with
   =ASSUME NoPR \notin PRs=.
2. =Error: Deadlock reached= on the positive run. Not a violation: the terminal
   state where every PR has merged has no successor. Added
   =CHECK_DEADLOCK FALSE=, since termination is the expected end of a pipeline.

Recording these because both /looked/ like the model finding something. A
tooling error that resembles a result is the most expensive kind, and next time
the reflex should be to read the error class before the trace.

* Lesson

Generalised into =spec.org= §Guard 4b, because it is worth more than the
instance: *a guard whose subject can change after it is checked must be
re-checked at the moment it is relied on.* Guard 0 at claim time is a
convenience that gives fast feedback. Guard 4b is the one that is load-bearing.

Corollary for the rest of the pipeline: audit every other guard for the same
shape. Guard 2 (gates green) is re-checked at promote time against the head SHA
— fine. Guard 3 (lock/freeze) is checked at deploy time — fine. Guard 1
(singleton) is checked only at claim; a second holder cannot appear without
claiming, so it is safe, but that is an argument and not yet a checked property.
